## The feature: loading a level's textures

When the player enters a level, the engine uploads its textures to the GPU: tiles, the hero sprite sheet, enemy sprites. The graphics API is a C library, like OpenGL, SDL or Vulkan. You ask for a texture and get back an integer id. When you are done you must hand the id back, or that GPU memory stays used until the game quits.

Our stand-in API, used in every example in this lesson:

```cpp
int  gpu_create_texture(const char* file);   // returns an id
void gpu_destroy_texture(int id);            // must be called exactly once per id
```

## The careless version: manual cleanup

```cpp
#include <cstdio>
#include <cstring>

int g_textures = 0;   // textures currently alive on the GPU
int gpu_create_texture(const char*) { return ++g_textures; }
void gpu_destroy_texture(int) { --g_textures; }

bool load_level(const char* music_file) {
    int tiles = gpu_create_texture("tiles.png");
    int hero = gpu_create_texture("hero.png");
    if (std::strlen(music_file) == 0) {
        std::printf("no music, abort load\n");
        return false;                    // forgot to destroy tiles and hero
    }
    // ... play the level ...
    gpu_destroy_texture(hero);
    gpu_destroy_texture(tiles);
    return true;
}

int main() {
    for (int attempt = 0; attempt < 3; ++attempt) load_level("");
    std::printf("textures still on the GPU: %d\n", g_textures);
}
```
```text
no music, abort load
no music, abort load
no music, abort load
textures still on the GPU: 6
```

## What went wrong

The happy path cleans up. The early return does not, so every failed load leaks two textures. Three retries, six textures gone. On a real GPU each one might be 16 MB.

The cleanup is written once, at the bottom, but there are many ways out of the function: every `return`, every `break` out of a loading loop, and every exception thrown by anything called inside. Each exit needs its own copy of the cleanup, in the right order, and the next person to add an early return will forget.

## The fix: RAII

Wrap the id in a class. The constructor creates the texture. The destructor destroys it. Now cleanup is not a line you write; it is something the compiler does at every exit of the scope.

```cpp
#include <cstdio>
#include <cstring>

int g_textures = 0;
int gpu_create_texture(const char*) { return ++g_textures; }
void gpu_destroy_texture(int) { --g_textures; }

class Texture {
public:
    explicit Texture(const char* file) : id_(gpu_create_texture(file)) {}
    ~Texture() { gpu_destroy_texture(id_); }
    Texture(const Texture&) = delete;              // one owner per id
    Texture& operator=(const Texture&) = delete;
    int id() const { return id_; }
private:
    int id_;
};

bool load_level(const char* music_file) {
    Texture tiles("tiles.png");
    Texture hero("hero.png");
    if (std::strlen(music_file) == 0) return false;    // both freed here
    return true;                                       // and here
}

int main() {
    for (int attempt = 0; attempt < 3; ++attempt) load_level("");
    std::printf("textures still on the GPU: %d\n", g_textures);
}
```
```text
textures still on the GPU: 0
```

The copy operations are deleted: if two `Texture` objects held the same id, both destructors would destroy it. The rule of 0/3/5 lesson covers this.

## Reverse order, every exit

Locals are destroyed in reverse order of construction when they leave scope, whether that is via `return`, the end of the block, or an exception unwinding the stack. Reverse order matters: an object built later may use one built earlier (a sprite that refers to its texture), so it must be destroyed first.

## Exceptions: the exit you cannot see

The level file parser throws when it finds a bad tile. With manual cleanup, an exception skips every line below it. With RAII, unwinding destroys every fully built local on the way out:

```cpp
#include <cstdio>
#include <stdexcept>

int g_textures = 0;
int gpu_create_texture(const char*) { return ++g_textures; }
void gpu_destroy_texture(int) { --g_textures; }

class Texture {
public:
    explicit Texture(const char* f) : id_(gpu_create_texture(f)) {}
    ~Texture() { gpu_destroy_texture(id_); }
    Texture(const Texture&) = delete;
    Texture& operator=(const Texture&) = delete;
private:
    int id_;
};

void parse_map() { throw std::runtime_error("level2.map: unknown tile 'Q'"); }

void load_level() {
    Texture tiles("tiles.png");
    Texture hero("hero.png");
    parse_map();                              // throws
}

int main() {
    try { load_level(); }
    catch (const std::exception& e) { std::printf("load failed: %s\n", e.what()); }
    std::printf("textures still on the GPU: %d\n", g_textures);
}
```
```text
load failed: level2.map: unknown tile 'Q'
textures still on the GPU: 0
```

## Scope guards: undo anything

Sometimes there is no resource class, just an action to undo. During a cutscene the game disables player input; it must turn input back on however the cutscene ends (finished, skipped, or an error). A **scope guard** is a tiny RAII object whose destructor runs any code you give it:

```cpp
#include <cstdio>
#include <utility>

template <class F>
struct ScopeExit {
    F f;
    ~ScopeExit() { f(); }
};
template <class F> ScopeExit(F) -> ScopeExit<F>;

bool g_input_enabled = true;

void play_cutscene(bool skipped) {
    g_input_enabled = false;
    ScopeExit restore{[] { g_input_enabled = true; }};
    if (skipped) { std::printf("skipped\n"); return; }
    std::printf("cutscene played\n");
}

int main() {
    play_cutscene(true);
    std::printf("input enabled: %d\n", g_input_enabled);
}
```
```text
skipped
input enabled: 1
```

(The `[] { ... }` is a **lambda**: an unnamed function written inline. The containers module covers lambdas fully. The line after the struct is a deduction guide so the template argument is worked out from the lambda.)

## When to use it, and when not

- Use RAII for **everything** that must be released: memory, textures, files, sockets, locks, audio channels, "input disabled" flags. In good C++ code, you almost never see a bare release call outside a destructor.
- Use the standard ones first: `std::vector`, `std::unique_ptr` (also with custom deleters for C APIs, next module), `std::lock_guard`, `std::fstream`, `std::jthread`.
- Use a scope guard for one-off undo actions. If the same guard appears in three places, make it a named class.
- A destructor should not throw. It may run during unwinding from another exception, and two exceptions in flight terminate the program.
