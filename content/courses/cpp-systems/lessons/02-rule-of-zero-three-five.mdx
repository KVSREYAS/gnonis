## The feature: sprite sheets

A sprite sheet is one image with every animation frame of a character packed in a grid. The image decoder hands us a raw `new[]`-allocated pixel buffer, and our `SpriteSheet` class owns it. Enemies of the same kind each get their own copy so they can be tinted (red slime, blue slime).

The first version has a destructor, because the buffer must be freed. It does not have anything else.

## The careless version: destructor only

```cpp
#include <cstdio>

class SpriteSheet {
public:
    explicit SpriteSheet(int bytes) : bytes_(bytes), pixels_(new unsigned char[bytes]{}) {}
    ~SpriteSheet() { delete[] pixels_; }
    void tint_red() { pixels_[0] = 255; }
private:
    int bytes_;
    unsigned char* pixels_;
};

int main() {
    SpriteSheet slime(64 * 64 * 4);
    SpriteSheet red_slime = slime;     // compiler-written copy: copies the pointer
    red_slime.tint_red();              // also tints the original
    std::printf("level exit\n");
}                                      // both destructors delete[] the same buffer
```
```text
==1==ERROR: AddressSanitizer: attempting double-free on 0x529000000200 in thread T0:
SUMMARY: AddressSanitizer: double-free ../../../../src/libsanitizer/asan/asan_new_delete.cpp:155 in operator delete[](void*)
```

## What went wrong

The compiler wrote a copy constructor for us. It copies each member: `bytes_`, and the pointer `pixels_`. So `red_slime.pixels_` and `slime.pixels_` hold the **same address**. This is a **shallow copy**.

Two bugs follow:

1. Tinting the copy also tints the original, because there is only one buffer.
2. At the end of `main`, both destructors run `delete[]` on the same buffer. That is a double free: undefined behaviour, here caught by AddressSanitizer, in a normal build often a crash on level exit.

The destructor was right. The problem is that a class whose destructor frees something **cannot use the generated copy**.

![Shallow copy: two objects pointing at the same heap block, versus deep copy and move](/diagrams/cpp-systems/01-lifetime/02-rule-of-zero-three-five.png)

## The fix, part 1: rule of three

If a class needs a destructor to free something, it also needs a **copy constructor** and **copy assignment** that make a **deep copy**: a new buffer with the same contents.

```cpp
#include <algorithm>
#include <cstdio>

class SpriteSheet {
public:
    explicit SpriteSheet(int bytes) : bytes_(bytes), pixels_(new unsigned char[bytes]{}) {}
    ~SpriteSheet() { delete[] pixels_; }
    SpriteSheet(const SpriteSheet& o) : bytes_(o.bytes_), pixels_(new unsigned char[o.bytes_]) {
        std::copy(o.pixels_, o.pixels_ + bytes_, pixels_);
    }
    SpriteSheet& operator=(const SpriteSheet& o) {
        if (this != &o) {
            unsigned char* fresh = new unsigned char[o.bytes_];
            std::copy(o.pixels_, o.pixels_ + o.bytes_, fresh);
            delete[] pixels_;
            pixels_ = fresh;
            bytes_ = o.bytes_;
        }
        return *this;
    }
    void tint_red() { pixels_[0] = 255; }
    int first() const { return pixels_[0]; }
private:
    int bytes_;
    unsigned char* pixels_;
};

int main() {
    SpriteSheet slime(64 * 64 * 4);
    SpriteSheet red_slime = slime;
    red_slime.tint_red();
    std::printf("slime %d, red slime %d\n", slime.first(), red_slime.first());
}
```
```text
slime 0, red slime 255
```

The ASan build is now clean: each object frees its own buffer once.

## The fix, part 2: rule of five

Deep copies are correct but slow: 16 KB copied each time. When the level loader builds a sheet and hands it to the renderer, nobody needs the old one. A **move** steals the pointer instead and leaves the source empty. But there is a catch: declaring a destructor or a copy operation **removes the compiler-generated moves**, so a "move" silently copies:

```cpp
#include <cstdio>
#include <utility>
#include <vector>

int g_copies = 0;
struct Sheet {
    std::vector<unsigned char> px = std::vector<unsigned char>(16384);
    Sheet() = default;
    Sheet(const Sheet& o) : px(o.px) { ++g_copies; }   // user-declared copy...
    ~Sheet() {}                                        // ...and destructor
};

int main() {
    Sheet loaded;
    Sheet for_renderer = std::move(loaded);            // wants a move
    std::printf("copies: %d, loaded still has %zu bytes\n", g_copies, loaded.px.size());
}
```
```text
copies: 1, loaded still has 16384 bytes
```

So a resource-owning class writes all five: destructor, copy constructor, copy assignment, **move constructor** and **move assignment**. The move module explains moves in detail.

## Rule of zero: the real goal

The best fix is to not own the raw buffer at all. `std::vector<unsigned char>` already owns a buffer correctly, with deep copies and cheap moves. Build `SpriteSheet` out of it and write **none** of the five:

```cpp
#include <cstdio>
#include <utility>
#include <vector>

class SpriteSheet {
public:
    explicit SpriteSheet(int bytes) : pixels_(bytes) {}
    void tint_red() { pixels_[0] = 255; }
    int first() const { return pixels_[0]; }
    std::size_t bytes() const { return pixels_.size(); }
private:
    std::vector<unsigned char> pixels_;   // owns, copies and moves itself
};

int main() {
    SpriteSheet slime(64 * 64 * 4);
    SpriteSheet red_slime = slime;               // deep copy, generated
    red_slime.tint_red();
    SpriteSheet moved = std::move(red_slime);    // cheap move, generated
    std::printf("slime %d, moved %d, %zu bytes, source now %zu\n",
                slime.first(), moved.first(), moved.bytes(), red_slime.bytes());
}
```
```text
slime 0, moved 255, 16384 bytes, source now 0
```

Even under AddressSanitizer: no leaks, no double free, and no special members written.

## When to use it, and when not

- **Rule of zero** for almost every class: `Player`, `Level`, `Inventory`, `SpriteSheet`. Members are `std::vector`, `std::string`, `std::unique_ptr`, other rule-of-zero classes.
- **Rule of five** only in the one small class whose whole job is owning a raw resource that no standard type covers: a GPU texture id, a file descriptor, a buffer from a C library. Keep that class tiny.
- If a resource cannot sensibly be copied (a GPU texture, a window), `= delete` the copies and write only the moves. That is still "thinking about all five".
- If you see a destructor in a class review, look for the other four.
