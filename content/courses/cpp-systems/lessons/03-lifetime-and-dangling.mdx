## The feature: the boss health bar

When the boss appears, the HUD shows its name above a health bar. The name is built at spawn time ("Slime King, Lv 12"). The HUD stores it in a `std::string_view`, a cheap read-only view of text.

`std::string_view` is just a pointer to characters and a length. It does not own the text. It is great for passing text to functions without copying, and dangerous to store.

## The careless version: a view of a temporary

```cpp
#include <cstdio>
#include <string>
#include <string_view>

std::string boss_title(int level) {
    return "Slime King, Lv " + std::to_string(level);
}

struct Hud {
    std::string_view boss_name;     // non-owning
};

int main() {
    Hud hud;
    hud.boss_name = boss_title(12);   // view of a temporary string
    std::string label(hud.boss_name); // the HUD copies the text to draw it
    std::printf("%s\n", label.c_str());
}
```
```text

READ of size 17 at 0x503000000040 thread T0
```

## What went wrong

`boss_title(12)` returns a temporary `std::string`. Its text lives in a heap buffer (the title is too long for the small-string buffer inside the string object). The view points into that buffer.

The temporary dies at the end of the full expression, the `;` on that line. Its destructor frees the buffer. One line later the HUD reads freed memory. In a normal build the bar might show the right name, garbage, or the name of whatever was allocated next. AddressSanitizer reports the exact line.

The general rule: a **non-owning** thing (`T&`, `T*`, `std::string_view`, `std::span`, an iterator) must never outlive the object it refers to. Nothing in the language checks that for you.

![A string_view pointing into a std::string's heap buffer that has been freed](/diagrams/cpp-systems/01-lifetime/03-lifetime-and-dangling.png)

## The fix: own what you store

Views are for **parameters** and short local use. Members that must stay valid store an owning `std::string`:

```cpp
#include <cstdio>
#include <string>
#include <string_view>

std::string boss_title(int level) { return "Slime King, Lv " + std::to_string(level); }

void draw_label(std::string_view text) {       // view as a parameter: fine
    std::printf("[%.*s]\n", int(text.size()), text.data());
}

struct Hud {
    std::string boss_name;                     // owns its copy
};

int main() {
    Hud hud;
    hud.boss_name = boss_title(12);            // moved into the member
    draw_label(hud.boss_name);
}
```
```text
[Slime King, Lv 12]
```

During the call `draw_label(hud.boss_name)`, the string is alive for the whole call, so the view is safe.

## The second bug: a reference into a growing vector

The homing missile locks onto an enemy by keeping a reference to it. Then the spawner adds more enemies:

```cpp
#include <cstdio>
#include <vector>

struct Enemy { int id; float x; };

int main() {
    std::vector<Enemy> enemies = {{1, 5.0f}, {2, 9.0f}};
    Enemy& target = enemies[0];            // missile locks on enemy 1
    enemies.push_back({3, 12.0f});         // spawner adds one: vector grows
    std::printf("missile flies to x=%.1f\n", target.x);
}
```
```text
==1==ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000014 at pc 0x555e5a8536c0 bp 0x7ffc4ae18490 sp 0x7ffc4ae18488
READ of size 4 at 0x502000000014 thread T0
SUMMARY: AddressSanitizer: heap-use-after-free game.cpp:10 in main
```

A `std::vector` keeps its elements in one block. When it is full and you `push_back`, it allocates a bigger block, moves every element there, and frees the old block. Every pointer, reference and iterator to an element now points into freed memory.

## The fix: refer by id

Things that can move or die should be referred to by a stable **id**, looked up when needed. The lookup can fail, and the code must handle that (the target died: the missile flies straight).

```cpp
#include <cstdio>
#include <vector>

struct Enemy { int id; float x; };

Enemy* find(std::vector<Enemy>& v, int id) {
    for (auto& e : v) if (e.id == id) return &e;
    return nullptr;
}

int main() {
    std::vector<Enemy> enemies = {{1, 5.0f}, {2, 9.0f}};
    int target_id = 1;                     // missile stores the id
    enemies.push_back({3, 12.0f});
    if (Enemy* t = find(enemies, target_id))   // look up each frame
        std::printf("missile flies to x=%.1f\n", t->x);
    enemies.erase(enemies.begin());        // enemy 1 dies
    if (!find(enemies, target_id)) std::printf("target gone, fly straight\n");
}
```
```text
missile flies to x=5.0
target gone, fly straight
```

The pointer from `find` is used immediately and never stored, so it cannot go stale. (The ownership module shows `std::weak_ptr`, which does the same job for heap objects.)

## Temporaries and lifetime extension

A **temporary** normally dies at the `;` that ends its full expression. One exception: binding a temporary **directly** to a `const T&` (or `T&&`) local extends its life to the end of that reference's scope:

```cpp
const std::string& title = boss_title(12);   // OK: temporary lives as long as title
std::string_view view = boss_title(12);      // dangles: a view is not a reference
```

The extension only applies to that direct binding. It does not pass through a function that takes a reference and returns it.

## Return by value

When in doubt, return owning values: `std::string boss_title()`, not `const std::string&` or `std::string_view`. The move module shows why that is cheap: the compiler builds the result directly in the caller (copy elision) or moves it.

Sources: [cppreference: reference initialization, lifetime](https://en.cppreference.com/w/cpp/language/reference_initialization), Core Guidelines F.43, [CppCon 2018: Nicolai Josuttis, string_view](https://www.youtube.com/watch?v=sVIi9y_sZ5o)

## When to use it, and when not

- **Views and references as parameters**: yes. The caller keeps the object alive for the whole call.
- **Views and references as members, or stored across frames**: only when you can prove the owner outlives the holder (a reference to the `Game` object that owns everything). Otherwise store an owning value or an id.
- **Pointers to vector elements**: only between changes to the vector. Call `reserve()` up front if you must, or use indices.
- **Pointers to things that can die** (enemies, projectiles): store an id or a `std::weak_ptr`.
