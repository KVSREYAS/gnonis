## The feature: switching levels

When the player walks through a door, the loader builds the next `Level` and hands it to the `World`. The world stores it as the current level, and the loader's copy is never used again.

```cpp
struct Level {
    std::string name;
    std::vector<unsigned char> tiles;   // 512 x 512 = 262,144 bytes
};
```

The first version of `World::set_level` takes a `const Level&` and copies it in.

## The careless version: always copy

```cpp
#include <cstdio>
#include <string>
#include <vector>

int g_tile_bytes_copied = 0;
struct Tiles {
    std::vector<unsigned char> v;
    explicit Tiles(int n) : v(n) {}
    Tiles(const Tiles& o) : v(o.v) { g_tile_bytes_copied += int(v.size()); }
    Tiles(Tiles&&) noexcept = default;
    Tiles& operator=(const Tiles& o) { v = o.v; g_tile_bytes_copied += int(v.size()); return *this; }
    Tiles& operator=(Tiles&&) noexcept = default;
};
struct Level { std::string name; Tiles tiles{512 * 512}; };

class World {
public:
    void set_level(const Level& l) { current_ = l; }    // copies everything
private:
    Level current_;
};

Level load_level(const char* name) { Level l; l.name = name; return l; }

int main() {
    World w;
    for (const char* door : {"cave", "forest", "castle"}) {
        Level next = load_level(door);
        w.set_level(next);              // next is thrown away right after
    }
    std::printf("tile bytes copied: %d\n", g_tile_bytes_copied);
}
```
```text
tile bytes copied: 786432
```

(`Tiles` wraps the vector only so we can count copied bytes. It behaves exactly like a vector.)

## What went wrong

Three doors, 768 KB copied, and every copy was pointless: `next` dies at the end of each loop step. On a console with a 16.6 ms frame budget, copying a large level at the moment the door opens is a visible hitch.

`set_level` has no way to know that the caller is done with its level. A `const Level&` parameter accepts anything and promises only "I will not change it". So it must copy.

We need a second kind of reference that means "this object is expiring, you may take its insides".

## lvalues and rvalues

Every expression in C++ has a **value category**:

- **lvalue**: names an object you can refer to again: `next`, `w`, `levels[2]`, `*ptr`. You can take its address with `&`.
- **rvalue**: a temporary with no name (`load_level("cave")`, `a + b`, `42`), or an object you have explicitly marked as expiring with `std::move(next)`.

There are two reference types to match:

- `Level&` (and `const Level&`) binds to lvalues. `const Level&` also accepts rvalues.
- `Level&&`, an **rvalue reference**, binds only to rvalues.

If a function has both overloads, the compiler picks `Level&&` for rvalues and `const Level&` for lvalues.

## The fix: a move overload and std::move

Add an overload that takes `Level&&` and moves from it. The caller says "I am done with this" by writing `std::move(next)`:

```cpp
#include <cstdio>
#include <string>
#include <utility>
#include <vector>

int g_tile_bytes_copied = 0;
struct Tiles {
    std::vector<unsigned char> v;
    explicit Tiles(int n) : v(n) {}
    Tiles(const Tiles& o) : v(o.v) { g_tile_bytes_copied += int(v.size()); }
    Tiles(Tiles&&) noexcept = default;
    Tiles& operator=(const Tiles& o) { v = o.v; g_tile_bytes_copied += int(v.size()); return *this; }
    Tiles& operator=(Tiles&&) noexcept = default;
};
struct Level { std::string name; Tiles tiles{512 * 512}; };

class World {
public:
    void set_level(const Level& l) { current_ = l; }             // lvalues: copy
    void set_level(Level&& l) { current_ = std::move(l); }       // rvalues: move
    const std::string& level_name() const { return current_.name; }
private:
    Level current_;
};

Level load_level(const char* name) { Level l; l.name = name; return l; }

int main() {
    World w;
    for (const char* door : {"cave", "forest", "castle"}) {
        Level next = load_level(door);
        w.set_level(std::move(next));    // "I am done with next"
    }
    w.set_level(load_level("boss room"));    // a temporary is already an rvalue
    std::printf("in %s, tile bytes copied: %d\n", w.level_name().c_str(), g_tile_bytes_copied);
}
```
```text
in boss room, tile bytes copied: 0
```

## The trap inside the && overload

Look at the `Level&&` overload again: it says `current_ = std::move(l);`. Why `std::move` again, when `l` is already an rvalue reference?

Because **a named rvalue reference is an lvalue**. The type of `l` is `Level&&`, but the expression `l` has a name, so it is an lvalue, and `current_ = l;` picks copy assignment. This rule is deliberate: a name can be used twice, and moving out of it silently on the first use would be dangerous.

```cpp
#include <cstdio>
#include <utility>

void take(const int&) { std::printf("copy-overload "); }
void take(int&&)      { std::printf("move-overload "); }

void set_level(int&& l) {
    take(l);              // l has a name: lvalue
    take(std::move(l));   // cast back to rvalue
}

int main() { set_level(42); std::printf("\n"); }
```
```text
copy-overload move-overload 
```

## What std::move actually is

`std::move(x)` does not move anything. It is a cast: it turns the lvalue `x` into an rvalue (an **xvalue**, an expiring value), so that overload resolution picks the `&&` version. The moving happens inside the move constructor or move assignment that receives it.

So `std::move(level);` on a line by itself does nothing at all, and moving from a `const Level` silently copies, because `const Level&&` cannot bind to the move constructor's `Level&&` and falls back to `const Level&`.

## Bug: use after move

The loader logs the level name after handing the level to the world:

```cpp
#include <cstdio>
#include <string>
#include <utility>
#include <vector>

struct Level { std::string name; std::vector<unsigned char> tiles; };

int main() {
    Level next{"forest of extremely long names", std::vector<unsigned char>(1024)};
    Level current = std::move(next);
    std::printf("loaded '%s' with %zu tiles\n", next.name.c_str(), next.tiles.size());
}
```
```text
loaded '' with 0 tiles
```

The log line reads the moved-from object. With libstdc++ the string and vector were left empty, so the log is wrong. Another library could leave something else; the standard only promises a **valid but unspecified state**. Read from the destination instead, or log before the move.

## When to use it, and when not

- Write `std::move(x)` when you hand off a local you will not use again: giving a level to the world, pushing a big object into a container, returning a member out of a dying object.
- Add a `T&&` overload (or take by value and move, next lesson) for functions that store their argument.
- Do **not** write `std::move` on `return local;`: it blocks copy elision (next lesson).
- Do **not** `std::move` from a `const` object: it silently copies.
- Do **not** move small types like `int`, `Vec2`, `Tile`. Moving them is a copy anyway, and the extra `std::move` only adds noise.

Sources: [cppreference: value categories](https://en.cppreference.com/w/cpp/language/value_category), Scott Meyers, *Effective Modern C++*, Items 23–25
