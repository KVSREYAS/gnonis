## The feature: streaming chunks

The world is split into chunks of 256 by 256 tiles (64 KB each). As the player walks, the streamer loads chunks ahead of them and appends each one to `std::vector<Chunk> chunks`. Nobody knows in advance how many will be loaded.

A `std::vector` keeps its elements in one block. When it is full, `push_back` allocates a bigger block (libstdc++ doubles it), transfers every existing element, and frees the old block. "Transfers" is the interesting word.

## The careless version: a hand-written move without noexcept

`Chunk` owns its tile buffer by hand and has a working move constructor. It just forgot one keyword.

```cpp
#include <cstdio>
#include <cstring>
#include <vector>

long g_bytes_copied = 0;

struct Chunk {
    unsigned char* tiles;
    static constexpr int kBytes = 256 * 256;
    Chunk() : tiles(new unsigned char[kBytes]{}) {}
    Chunk(const Chunk& o) : tiles(new unsigned char[kBytes]) {
        std::memcpy(tiles, o.tiles, kBytes);
        g_bytes_copied += kBytes;
    }
    Chunk(Chunk&& o) : tiles(o.tiles) { o.tiles = nullptr; }   // no noexcept
    Chunk& operator=(const Chunk&) = delete;
    ~Chunk() { delete[] tiles; }
};

int main() {
    std::vector<Chunk> chunks;
    for (int i = 0; i < 100; ++i) chunks.emplace_back();      // the player explores
    std::printf("chunks: %zu, KB copied while growing: %ld\n", chunks.size(), g_bytes_copied / 1024);
}
```
```text
chunks: 100, KB copied while growing: 8128
```

## What went wrong

The vector grew from 1 to 128 slots in doublings (1, 2, 4, ..., 128). At each step it transferred every existing chunk: 1 + 2 + 4 + ... + 64 = 127 chunks, and it **copied** each one, 64 KB at a time, even though `Chunk` has a perfectly good move constructor.

Why: if the vector moved chunks and the tenth move threw an exception, the first nine old chunks would already be gutted and the vector could not go back to its old state. Vector promises the strong guarantee for `push_back`, so it only moves when the move is promised not to throw. It checks `std::is_nothrow_move_constructible`, and our move constructor promised nothing.

## The fix: noexcept

```cpp
#include <cstdio>
#include <cstring>
#include <type_traits>
#include <vector>

long g_bytes_copied = 0;

struct Chunk {
    unsigned char* tiles;
    static constexpr int kBytes = 256 * 256;
    Chunk() : tiles(new unsigned char[kBytes]{}) {}
    Chunk(const Chunk& o) : tiles(new unsigned char[kBytes]) {
        std::memcpy(tiles, o.tiles, kBytes);
        g_bytes_copied += kBytes;
    }
    Chunk(Chunk&& o) noexcept : tiles(o.tiles) { o.tiles = nullptr; }
    Chunk& operator=(const Chunk&) = delete;
    ~Chunk() { delete[] tiles; }
};
static_assert(std::is_nothrow_move_constructible_v<Chunk>);   // guard against regressions

int main() {
    std::vector<Chunk> chunks;
    for (int i = 0; i < 100; ++i) chunks.emplace_back();
    std::printf("chunks: %zu, KB copied while growing: %ld\n", chunks.size(), g_bytes_copied / 1024);
}
```
```text
chunks: 100, KB copied while growing: 0
```

Stealing a pointer cannot fail, so the promise is true. The `static_assert` makes the build fail if someone later adds a member whose move can throw.

## Two more ways to lose your moves

**1. Declaring a destructor or copy.** Someone adds `~Chunk() { log("chunk unloaded"); }` to a rule-of-zero `Chunk` whose only member is a `std::vector`. The implicit moves disappear, every "move" is a copy, and vector growth copies again. Fix: `Chunk(Chunk&&) noexcept = default;` and `Chunk& operator=(Chunk&&) noexcept = default;`.

**2. Members whose moves can throw.** A defaulted move constructor is `noexcept` only if every member's move is. Standard containers and `std::string` are fine. A member type with a throwing move, or a hand-written move missing `noexcept`, poisons the whole class.

Both are silent: everything still compiles and works, only slower. The `static_assert(std::is_nothrow_move_constructible_v<Chunk>)` line catches both.

## reserve: skip the growth entirely

If you know how many chunks you will load (a level file lists them), call `reserve(n)` first. One allocation, no transfers at all:

```cpp
#include <cstdio>
#include <vector>

int main() {
    std::vector<int> grown, reserved;
    int grown_reallocs = 0, reserved_reallocs = 0;
    reserved.reserve(1000);
    for (int i = 0; i < 1000; ++i) {
        auto c1 = grown.capacity();    grown.push_back(i);    grown_reallocs += grown.capacity() != c1;
        auto c2 = reserved.capacity(); reserved.push_back(i); reserved_reallocs += reserved.capacity() != c2;
    }
    std::printf("reallocations: %d without reserve, %d with reserve\n", grown_reallocs, reserved_reallocs);
}
```
```text
reallocations: 11 without reserve, 0 with reserve
```

## Returning big objects: copy elision

The loader returns a fresh `Level` by value. Is that a copy? No:

```cpp
#include <cstdio>
#include <utility>

struct Level {
    Level() { std::printf("build "); }
    Level(const Level&) { std::printf("copy "); }
    Level(Level&&) noexcept { std::printf("move "); }
};

Level load_temp() { return Level(); }                   // prvalue: guaranteed elision
Level load_named() { Level l; return l; }               // NRVO: usually elided
Level load_bad() { Level l; return std::move(l); }      // blocks NRVO

int main() {
    std::printf("temp:  "); Level a = load_temp();  std::printf("\n");
    std::printf("named: "); Level b = load_named(); std::printf("\n");
    std::printf("moved: "); Level c = load_bad();   std::printf("\n");
}
```
```text
temp:  build 
named: build 
moved: build move 
```

- Returning a temporary (a **prvalue**) of the same type is **guaranteed** since C++17 to build directly in the caller's variable: no copy, no move.
- Returning a named local is usually elided too (**NRVO**). If the compiler cannot, it moves automatically.
- `return std::move(l);` turns the return into an xvalue, which **forbids** NRVO, so you pay a move you did not need. g++ warns with `-Wpessimizing-move`.

So: return locals by value, plainly.

## When to use it, and when not

- Mark every hand-written move constructor and move assignment `noexcept` (they almost always only swap pointers). Add a `static_assert` for types stored in vectors.
- Prefer the rule of zero, where defaulted moves get `noexcept` for free.
- `reserve` when the count is known. Do not `reserve` in a loop with growing sizes: it can disable the doubling and make things slower.
- Return by value. Never `return std::move(local);`.
- If an element type is expensive to move as well (a big array inside the object), store `std::unique_ptr<T>` in the vector instead, so growth moves only pointers.

Sources: [cppreference: std::move_if_noexcept](https://en.cppreference.com/w/cpp/utility/move_if_noexcept), [cppreference: copy elision](https://en.cppreference.com/w/cpp/language/copy_elision), Core Guidelines C.66
