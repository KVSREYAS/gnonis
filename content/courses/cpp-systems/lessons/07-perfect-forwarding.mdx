## The feature: a spawn function

The world keeps every entity in one list. Spawning should be one call that works for every entity type, with that type's own constructor arguments:

```cpp
world.spawn<Slime>("green slime", 30);
world.spawn<Bat>("cave bat", 12, std::move(bat_brain));   // bat_brain is a std::unique_ptr
world.spawn<Chest>(loot_table);                           // big vector, the caller keeps it
```

One function template, any entity type, any arguments, and no copies the caller did not ask for.

## The careless version: take everything by value

```cpp
#include <cstdio>
#include <memory>
#include <string>
#include <vector>

int g_copies = 0;
struct Name {                       // a string that counts its copies
    std::string s;
    Name(const char* c) : s(c) {}
    Name(const Name& o) : s(o.s) { ++g_copies; }
    Name(Name&&) noexcept = default;
};

struct Entity { virtual ~Entity() = default; };
struct Slime : Entity {
    Name name; int hp;
    Slime(Name n, int h) : name(n), hp(h) {}
};

std::vector<std::unique_ptr<Entity>> world;

template <class T, class... Args>
T& spawn(Args... args) {                          // every argument copied in
    auto p = std::make_unique<T>(args...);        // and copied again here
    T& ref = *p;
    world.push_back(std::move(p));
    return ref;
}

int main() {
    Name n("green slime");
    spawn<Slime>(n, 30);
    std::printf("copies for one spawn: %d\n", g_copies);
}
```
```text
copies for one spawn: 3
```

## What went wrong

One spawn, three copies of the name: into spawn's parameter, into Slime's constructor parameter, into the member. The last one is Slime's own fault (`name(n)` should be `name(std::move(n))`). The first two are the spawn function's fault.

Worse, the bat line does not compile at all: `std::unique_ptr` cannot be copied, and `spawn(Args... args)` tries to copy it. And inside `spawn`, even with `Args&&...`, the parameters have names, so they are lvalues and get copied when passed on.

We want each argument to arrive at `T`'s constructor exactly as the caller passed it: lvalues as lvalues (copy, because the caller still needs them), rvalues as rvalues (move).

## Variadic templates

`template <class T, class... Args>` declares a **parameter pack** `Args`: zero or more types. `Args... args` declares one function parameter per type. `args...` expands the pack back into a comma-separated list.

```cpp
#include <cstdio>

template <class... Args>
int count_args(Args... args) { return sizeof...(args); }

template <class... Args>
void log_spawn(const char* type, Args... args) {
    std::printf("spawn %s with %d arguments\n", type, count_args(args...));
}

int main() {
    log_spawn("slime", "green slime", 30);
    log_spawn("bat", "cave bat", 12, 2.5f);
    log_spawn("marker");
}
```
```text
spawn slime with 2 arguments
spawn bat with 3 arguments
spawn marker with 0 arguments
```

`sizeof...(args)` is the number of arguments. A **fold expression** like `(std::printf("%d ", args), ...)` repeats an expression for each argument.

## Forwarding references

In a template where `T` is **deduced** from the argument, `T&&` is a **forwarding reference** (Scott Meyers called it a universal reference). It is not a plain rvalue reference:

- pass an lvalue `Name n`: `T` is deduced as `Name&`, and the parameter becomes `Name&`
- pass an rvalue `Name("x")`: `T` is deduced as `Name`, and the parameter becomes `Name&&`

So it binds to anything, and `T` records what it was.

## Reference collapsing

How does `T&&` become `Name&` when `T = Name&`? The parameter type is written `Name& &&`, a reference to a reference, and the compiler collapses it:

| written | becomes |
| --- | --- |
| `T& &` | `T&` |
| `T& &&` | `T&` |
| `T&& &` | `T&` |
| `T&& &&` | `T&&` |

Any `&` wins. Only `&& &&` stays an rvalue reference.

## The fix: std::forward

`std::forward<T>(x)` casts `x` back to an rvalue **only if** `T` says the caller passed an rvalue. It is essentially `static_cast<T&&>(x)`, and the collapsing table does the rest.

```cpp
#include <cstdio>
#include <memory>
#include <string>
#include <utility>
#include <vector>

int g_copies = 0;
struct Name {
    std::string s;
    Name(const char* c) : s(c) {}
    Name(const Name& o) : s(o.s) { ++g_copies; }
    Name(Name&&) noexcept = default;
};

struct Entity { virtual ~Entity() = default; };
struct Slime : Entity {
    Name name; int hp;
    Slime(Name n, int h) : name(std::move(n)), hp(h) {}
};
struct Bat : Entity {
    Name name; std::unique_ptr<int> brain;
    Bat(Name n, std::unique_ptr<int> b) : name(std::move(n)), brain(std::move(b)) {}
};

std::vector<std::unique_ptr<Entity>> world;

template <class T, class... Args>
T& spawn(Args&&... args) {
    auto p = std::make_unique<T>(std::forward<Args>(args)...);
    T& ref = *p;
    world.push_back(std::move(p));
    return ref;
}

int main() {
    Name n("green slime");
    spawn<Slime>(n, 30);                         // lvalue: copied once (caller keeps n)
    std::printf("lvalue name: %d copy\n", g_copies);
    g_copies = 0;
    spawn<Slime>(Name("blue slime"), 30);        // rvalue: moved all the way
    auto brain = std::make_unique<int>(7);
    Bat& b = spawn<Bat>("cave bat", std::move(brain));   // move-only argument works
    std::printf("rvalue names: %d copies, bat brain %d, entities %zu\n", g_copies, *b.brain, world.size());
}
```
```text
lvalue name: 1 copy
rvalue names: 0 copies, bat brain 7, entities 3
```

`std::make_unique` and `emplace_back` are written exactly this way internally.

## std::move vs std::forward

- `std::move(x)`: "I own x and I am done with it." Always casts to an rvalue. Use it on locals and on parameters you took by value or by `T&&` with a concrete type (like `Level&&`).
- `std::forward<T>(x)`: "pass x on as it was given to me." Use it only on forwarding references (`T&&` with deduced `T`), and only once per argument: after forwarding an rvalue, `x` is moved-from.

Mixing them up is a classic bug: `std::move` on a forwarding reference steals the caller's lvalue (their `Name n` comes back empty); forgetting `std::forward` copies every rvalue.

## When to use it, and when not

- Use forwarding for **factory and wrapper** functions that pass arguments through to a constructor or another function: `spawn`, `make_*`, `emplace`, event dispatch, logging wrappers.
- Do not use `T&&` templates for ordinary functions that just want to read a value. `const T&` is clearer and works with everything.
- For a function that **stores** one argument of a known type, taking it **by value and moving** is simpler than forwarding: `void set_name(std::string n) { name_ = std::move(n); }` costs one extra move at most.

Sources: [cppreference: std::forward](https://en.cppreference.com/w/cpp/utility/forward), Meyers, *Effective Modern C++*, Items 24–30
