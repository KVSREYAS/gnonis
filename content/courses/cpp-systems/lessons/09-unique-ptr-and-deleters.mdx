## The feature: the enemy spawner

The spawner creates enemies on the heap (they are polymorphic: slimes, bats, turrets) and the world keeps them in a list. Each frame the update loop runs every enemy. Enemies that die are removed and destroyed. A dying enemy can also hand its "soul" to the boss, which absorbs it.

With raw pointers, every one of those steps needs a matching `delete`, written by hand, in the right place, exactly once.

## The careless version: raw owning pointers

```cpp
#include <cstdio>
#include <vector>

struct Enemy {
    int hp;
    explicit Enemy(int h) : hp(h) {}
    virtual ~Enemy() = default;
};

std::vector<Enemy*> world;

void remove_dead() {
    std::vector<Enemy*> alive;
    for (Enemy* e : world) {
        if (e->hp <= 0) continue;      // removed from the list... not deleted
        alive.push_back(e);
    }
    world = alive;
}

void on_arrow_hit(Enemy* e) { e->hp -= 50; if (e->hp <= 0) delete e; }   // deletes too

int main() {
    world = {new Enemy(30), new Enemy(10), new Enemy(40)};
    world[1]->hp = 0;
    remove_dead();                     // leaks the dead one
    Enemy* bat = world[0];
    on_arrow_hit(bat);                 // arrow 1 kills and deletes the bat
    on_arrow_hit(bat);                 // arrow 2, same frame: use after free
    std::printf("never reached cleanly\n");
}
```
```text
==1==ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000010 at pc 0x563f50f363db bp 0x7fff21f46140 sp 0x7fff21f46138
SUMMARY: AddressSanitizer: heap-use-after-free game.cpp:21 in on_arrow_hit(Enemy*)
```

## What went wrong

ASan stops at the first error it sees, the use after free. Two different functions both thought they owned enemies. `remove_dead` took enemies out of the list without deleting them (leak). `on_arrow_hit` deleted an enemy that the world list still pointed at, and the second arrow used it (use after free). Neither function's signature said anything about ownership: they all take or hold `Enemy*`.

The fix is to put the answer to "who deletes this?" into the type, so the compiler enforces it.

## The fix: std::unique_ptr

`std::unique_ptr<Enemy>` owns one enemy and deletes it in its destructor. It cannot be copied, only moved, so there is always exactly one owner.

```cpp
#include <cstdio>
#include <memory>
#include <vector>

struct Enemy {
    int hp;
    explicit Enemy(int h) : hp(h) {}
    virtual ~Enemy() = default;
};

std::vector<std::unique_ptr<Enemy>> world;        // the world owns

void remove_dead() {
    std::erase_if(world, [](const std::unique_ptr<Enemy>& e) { return e->hp <= 0; });
}                                                 // erasing a unique_ptr deletes the enemy

void on_arrow_hit(Enemy& e) { e.hp -= 50; }       // observes; cannot delete

int main() {
    world.push_back(std::make_unique<Enemy>(30));
    world.push_back(std::make_unique<Enemy>(10));
    world.push_back(std::make_unique<Enemy>(40));
    world[1]->hp = 0;
    remove_dead();
    on_arrow_hit(*world[0]);
    on_arrow_hit(*world[0]);
    remove_dead();
    std::printf("enemies left: %zu, no leaks, no double delete\n", world.size());
}
```
```text
enemies left: 1, no leaks, no double delete
```

The arrow handler now takes `Enemy&`: it can hurt the enemy but has no way to delete it. Only `remove_dead`, which owns the list, removes enemies, and removing a `unique_ptr` from the vector deletes the enemy. The ASan run is clean.

## Moving ownership around

```cpp
#include <cstdio>
#include <memory>
#include <utility>
#include <vector>

struct Soul { int power = 10; ~Soul() { std::printf("soul freed\n"); } };

struct Boss {
    std::vector<std::unique_ptr<Soul>> absorbed;
    void absorb(std::unique_ptr<Soul> s) { absorbed.push_back(std::move(s)); }  // takes ownership
};

std::unique_ptr<Soul> make_soul() { return std::make_unique<Soul>(); }         // gives ownership

int main() {
    Boss boss;
    auto s = make_soul();
    // boss.absorb(s);          // error: use of deleted copy constructor
    boss.absorb(std::move(s));  // explicit hand-off
    std::printf("caller still has a soul: %d, boss has %zu\n", s != nullptr, boss.absorbed.size());
}
```
```text
caller still has a soul: 0, boss has 1
soul freed
```

Signatures now tell the story:

- `std::unique_ptr<T> make_x()`: you get ownership.
- `void absorb(std::unique_ptr<T> s)` (by value): I take ownership; the caller must write `std::move`.
- `void hit(T& t)` or `T*`: I only look.

## How big is it?

On x86-64 with libstdc++ or libc++, a `unique_ptr<T>` with the default deleter is 8 bytes, exactly a raw pointer. The deleter is stored using the empty-base trick, so a deleter with no data takes no space. A world list of 10,000 enemies pays nothing for safety.

## Custom deleters: wrapping a C library

Windowing, audio and graphics libraries (SDL, OpenAL, Vulkan) are C APIs: you get a handle from a create function and must pass it to a destroy function. A custom deleter makes `unique_ptr` call the right one:

```cpp
#include <cstdio>
#include <memory>

// stand-in for a C windowing library
struct Window { int w, h; };
Window* window_create(int w, int h) { std::printf("window %dx%d opened\n", w, h); return new Window{w, h}; }
void window_destroy(Window* win) { std::printf("window closed\n"); delete win; }

struct WindowDeleter { void operator()(Window* w) const { window_destroy(w); } };
using WindowPtr = std::unique_ptr<Window, WindowDeleter>;

int main() {
    WindowPtr win(window_create(1280, 720));
    std::printf("game running in %dx%d, handle is %zu bytes\n", win->w, win->h, sizeof(win));
}
```
```text
window 1280x720 opened
game running in 1280x720, handle is 8 bytes
window closed
```

The deleter is an empty struct, so `WindowPtr` is still 8 bytes. A function pointer as the deleter (`std::unique_ptr<Window, void(*)(Window*)>`) works too but stores the pointer in every object: 16 bytes.

## When to use it, and when not

- Use `unique_ptr` for every heap object with one clear owner: entities in the world list, a level's physics body, the game's renderer, C library handles.
- Create with `std::make_unique<T>(args...)`. A bare `new` in game code is a code-review red flag.
- Take `unique_ptr` by value only in functions that take ownership. Everything else takes `T&` (must exist) or `T*` (may be null).
- Do not use a smart pointer for objects that can just live by value: a `Vec2`, a small struct, a member that is never shared. `std::vector<Enemy>` is better than `std::vector<std::unique_ptr<Enemy>>` when there is no inheritance.
