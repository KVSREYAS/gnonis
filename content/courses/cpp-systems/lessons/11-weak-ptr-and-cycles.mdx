## The feature: squads and homing missiles

Two new things in Slime Siege:

1. **Slime squads.** A squad leader keeps a list of its members so it can give orders. Each member keeps a pointer to its leader so it can follow.
2. **Homing missiles.** A turret fires a missile that steers toward a target enemy until it hits.

Both need a pointer from one game object to another. And both go wrong if that pointer is a `shared_ptr`.

## The careless version: everyone owns everyone

```cpp
#include <cstdio>
#include <memory>
#include <vector>

struct Slime {
    int id;
    std::shared_ptr<Slime> leader;                 // member -> leader
    std::vector<std::shared_ptr<Slime>> members;   // leader -> members
    Slime(int i, std::shared_ptr<Slime> l) : id(i), leader(std::move(l)) {}
    ~Slime() { std::printf("slime %d freed\n", id); }
};

int main() {
    {
        auto boss = std::make_shared<Slime>(1, nullptr);
        for (int i = 2; i <= 3; ++i) {
            auto m = std::make_shared<Slime>(i, boss);
            boss->members.push_back(m);
        }
        std::printf("squad of 3 formed\n");
    }   // the level ends
    std::printf("level unloaded\n");
    std::fflush(stdout);   // show our output before the leak report
}
```
```text
squad of 3 formed
level unloaded
==1==ERROR: LeakSanitizer: detected memory leaks
SUMMARY: AddressSanitizer: 224 byte(s) leaked in 4 allocation(s).
```

## What went wrong

When `boss` went out of scope, its strong count dropped from 3 to 2, not 0: both members still own it. The members are owned by the boss. Nobody outside holds any of them, but every count is above zero, so nothing is freed. The destructors never ran, and LeakSanitizer reports the memory as leaked at exit.

In a real game this happens every level. Each squad leaks, memory use climbs level by level, and any cleanup in the destructors (removing the slime from the physics world, stopping its sound) never runs.

## The fix: std::weak_ptr

A `std::weak_ptr` points at an object managed by `shared_ptr` but does **not** own it. It increments the weak count, not the strong count, so it never keeps the object alive.

To use the object, call `lock()`. It returns a `shared_ptr` that keeps the object alive while you use it, or an empty `shared_ptr` if the object is already gone. This is a check and a grab in one step, so there is no gap where the object could die between them.

The rule for cycles: pick one direction to own (the leader owns members), and make the other direction weak.

```cpp
#include <cstdio>
#include <memory>
#include <vector>

struct Slime {
    int id;
    std::weak_ptr<Slime> leader;                   // member -> leader: does not own
    std::vector<std::shared_ptr<Slime>> members;   // leader -> members: owns
    Slime(int i, std::shared_ptr<Slime> l) : id(i), leader(l) {}
    ~Slime() { std::printf("slime %d freed\n", id); }
};

int main() {
    {
        auto boss = std::make_shared<Slime>(1, nullptr);
        for (int i = 2; i <= 3; ++i) {
            auto m = std::make_shared<Slime>(i, boss);
            boss->members.push_back(m);
        }
        if (auto l = boss->members[0]->leader.lock())
            std::printf("slime 2 follows slime %d\n", l->id);
    }
    std::printf("level unloaded\n");
}
```
```text
slime 2 follows slime 1
slime 1 freed
slime 2 freed
slime 3 freed
level unloaded
```

The boss dies first (strong count 0), its destructor destroys the `members` vector, and the members die with it.

## Homing missiles: pointing at something that may die

The missile needs its target's position every frame. But the missile should not keep the target alive: if the player's sword kills the bat first, the bat must die. With a `weak_ptr`, the missile checks each frame:

```cpp
#include <cstdio>
#include <memory>

struct Enemy { const char* name; float x; };

struct Missile {
    std::weak_ptr<Enemy> target;
    float x = 0;
    bool update() {                                 // false: target gone, missile fizzles
        auto t = target.lock();
        if (!t) return false;
        x += (t->x - x) * 0.5f;
        std::printf("missile at %.1f chasing %s at %.1f\n", x, t->name, t->x);
        return true;
    }
};

int main() {
    auto bat = std::make_shared<Enemy>(Enemy{"bat", 10});
    Missile m{bat};
    m.update();
    m.update();
    bat.reset();                                    // the player's sword got there first
    if (!m.update()) std::printf("target gone, missile fizzles\n");
}
```
```text
missile at 5.0 chasing bat at 10.0
missile at 7.5 chasing bat at 10.0
target gone, missile fizzles
```

## When to use it, and when not

- Use `weak_ptr` for back-pointers in a structure the other direction owns (member to leader, child to parent), and for "I want to use this if it still exists" references (missile targets, an AI's current enemy, a cache that should not keep things alive).
- If the referenced object always outlives the referrer (a child that is destroyed with its parent), a raw pointer or reference is simpler and has no cost. Use `weak_ptr` when it may die first.
- `weak_ptr` only works with objects owned by `shared_ptr`. It cannot observe a `unique_ptr` object.
- `lock()` is an atomic operation. Locking once per frame per missile is fine; locking inside a tight inner loop is not. Lock once, keep the `shared_ptr` for the loop.
