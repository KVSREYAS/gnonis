## The feature: damage for any enemy type

The engine has several unrelated enemy types (`Slime`, `Bat`, `Turret`) that are not in one class hierarchy: they live in separate arrays for speed. A template `damage_all(list, dmg)` should work on a list of any of them.

A new teammate calls it on the level's tile list by mistake.

## The careless version: an unconstrained template

```cpp
#include <vector>

struct Slime { int hp = 20; void take_damage(int d) { hp -= d; } bool alive() const { return hp > 0; } };
struct Tile  { int kind = 0; };

template <class List>
int damage_all(List& list, int dmg) {
    int kills = 0;
    for (auto& e : list) {
        e.take_damage(dmg);
        if (!e.alive()) ++kills;
    }
    return kills;
}

int main() {
    std::vector<Slime> slimes(3);
    std::vector<Tile> tiles(100);
    damage_all(slimes, 25);
    damage_all(tiles, 25);           // oops
}
```
```text
game.cpp:10: error: 'struct Tile' has no member named 'take_damage'
game.cpp:11: error: 'struct Tile' has no member named 'alive'
```

## What went wrong

The template accepted `std::vector<Tile>` without complaint. Only when the compiler instantiated the body did it find that `Tile` has no `take_damage`, so the errors point inside `damage_all` (lines 10 and 11), at code the caller never wrote. Here that is two lines; with real engine templates calling templates several levels deep, it becomes pages, and the caller has to read the library's internals to find out what it wanted.

The template had requirements all along (each element needs `take_damage(int)` and `alive()`), but they were only written implicitly, in the body.

## The fix: a concept

A **concept** names those requirements, and the template states them up front:

```cpp
#include <concepts>
#include <vector>

struct Slime { int hp = 20; void take_damage(int d) { hp -= d; } bool alive() const { return hp > 0; } };
struct Tile  { int kind = 0; };

template <class T>
concept Damageable = requires(T e, int dmg) {
    e.take_damage(dmg);
    { e.alive() } -> std::convertible_to<bool>;
};

template <class List>
    requires Damageable<typename List::value_type>
int damage_all(List& list, int dmg) {
    int kills = 0;
    for (auto& e : list) {
        e.take_damage(dmg);
        if (!e.alive()) ++kills;
    }
    return kills;
}

int main() {
    std::vector<Slime> slimes(3);
    std::vector<Tile> tiles(100);
    damage_all(slimes, 25);
    damage_all(tiles, 25);           // oops
}
```
```text
game.cpp:28: error: no matching function for call to 'damage_all(std::vector<Tile>&, int)'
game.cpp:15: note: constraints not satisfied
game.cpp:9: note: the required expression 'e.take_damage(dmg)' is invalid
game.cpp:10: note: the required expression 'e.alive()' is invalid
```

Now the error is at the call (line 28), says the constraints are not satisfied, and lists exactly which requirements `Tile` does not meet.

## requires-expressions and overloads

A `requires(params) { ... }` expression lists expressions that must compile. `{ expr } -> concept<...>` also checks the result type.

Concepts also choose overloads. The engine can have a general `knockback(e)` and a special one for things that can fly:

```cpp
#include <concepts>
#include <cstdio>

struct Slime { const char* name = "slime"; };
struct Bat   { const char* name = "bat"; void fly_up() {} };

template <class T> concept Enemy  = requires(T e) { e.name; };
template <class T> concept Flying = Enemy<T> && requires(T e) { e.fly_up(); };

void knockback(Enemy auto& e)  { std::printf("%s slides back\n", e.name); }
void knockback(Flying auto& e) { std::printf("%s is thrown upward\n", e.name); }

int main() {
    Slime s; Bat b;
    knockback(s);
    knockback(b);     // both match; Flying includes Enemy, so it is more specific
}
```
```text
slime slides back
bat is thrown upward
```

`Flying` is defined as `Enemy<T> && ...`, so it **subsumes** `Enemy`: anything Flying is also an Enemy. When both overloads match, the more constrained one wins.

## When to use it, and when not

- Constrain templates that other people call: engine APIs, utility headers. The error moves to the caller and names the problem.
- Use the standard ones first: `std::integral`, `std::floating_point`, `std::ranges::range`, `std::invocable`.
- Do not write a concept for every template. A small private helper used in two places does not need one.
- A concept checks that code compiles, not that it is correct. `Damageable` accepts a `take_damage` that heals.
