## The feature: removing dead enemies

After the damage step, the frame removes every enemy with `hp <= 0` from the list, so later systems (AI, drawing) only see live ones. A fireball just killed two slimes standing next to each other.

## The careless version: erase in an index loop

```cpp
#include <cstdio>
#include <vector>

struct Enemy { int id; int hp; };

int main() {
    std::vector<Enemy> enemies{{1, 20}, {2, 0}, {3, 0}, {4, 15}};
    for (std::size_t i = 0; i < enemies.size(); ++i)
        if (enemies[i].hp <= 0) enemies.erase(enemies.begin() + i);
    for (const auto& e : enemies) std::printf("enemy %d hp %d\n", e.id, e.hp);
}
```
```text
enemy 1 hp 20
enemy 3 hp 0
enemy 4 hp 15
```

## What went wrong

Enemy 3 is dead but still in the list. When `erase` removed enemy 2 at index 1, every later element shifted down one place: enemy 3 moved to index 1. Then `++i` moved on to index 2, which is now enemy 4. Enemy 3 was never checked.

The game symptom: a dead slime with 0 hp keeps walking and attacking for a frame, or forever if the next fireball kills its neighbour again. With iterators instead of indices it is worse: `erase` invalidates the iterator you are holding, and the loop's `++it` is undefined behaviour.

Also, each `erase` in the middle moves every later element. Removing k enemies from n this way costs O(n·k).

## The fix: std::erase_if

C++20's `std::erase_if` removes every matching element in one pass. It moves the survivors forward once and shrinks the vector at the end:

```cpp
#include <cstdio>
#include <vector>

struct Enemy { int id; int hp; };

int main() {
    std::vector<Enemy> enemies{{1, 20}, {2, 0}, {3, 0}, {4, 15}};
    auto removed = std::erase_if(enemies, [](const Enemy& e) { return e.hp <= 0; });
    std::printf("removed %zu\n", removed);
    for (const auto& e : enemies) std::printf("enemy %d hp %d\n", e.id, e.hp);
}
```
```text
removed 2
enemy 1 hp 20
enemy 4 hp 15
```

Before C++20 the same thing was written as the **erase-remove idiom**: `v.erase(std::remove_if(v.begin(), v.end(), pred), v.end());`. `remove_if` moves survivors to the front and returns the new end; `erase` cuts off the rest.

If order does not matter (it usually does not for enemies), there is an even cheaper trick: swap the dead enemy with the last one and `pop_back`. That is O(1) per removal.

## How a vector grows

When `push_back` finds the vector full, it allocates a bigger buffer (libstdc++ doubles it), moves every element across, and frees the old one. Doubling makes the average cost per `push_back` constant, but each growth invalidates every pointer, reference and iterator into the vector.

![Vector capacity doubling 1→2→4→8 with old buffers freed; an iterator left pointing at the freed block](/diagrams/cpp-systems/05-stl/01-containers-and-invalidation.png)

If you know how many enemies a wave spawns, `reserve(n)` allocates once up front.

## Choosing a container

Sources: [cppreference: containers library, iterator invalidation](https://en.cppreference.com/w/cpp/container), Bjarne Stroustrup, [Why you should avoid linked lists (GoingNative 2012)](https://www.youtube.com/watch?v=YQs6IC-vgmo)

- Use `std::vector` for anything iterated every frame: enemies, particles, bullets.
- Use `std::unordered_map` or `std::map` for lookup by key: inventory by item name, entity id to index.
- Use a node container (`std::list`, `std::map`) only when you need element addresses that never change and cannot use ids. You pay a cache miss per element when iterating.
- Never keep a pointer into a vector across anything that may push or erase.
