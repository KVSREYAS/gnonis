## The feature: turret targeting

Each turret picks the nearest live enemy within range and fires at it. If there is none, it waits.

## The careless version: a hand-written search

```cpp
#include <cstdio>
#include <vector>

struct Enemy { int id; float dist; int hp; };

int pick_target(const std::vector<Enemy>& enemies, float range) {
    int best = 0;                       // index of best so far
    for (std::size_t i = 1; i < enemies.size(); ++i)
        if (enemies[i].hp > 0 && enemies[i].dist < enemies[best].dist && enemies[i].dist <= range)
            best = static_cast<int>(i);
    return enemies[best].id;
}

int main() {
    std::vector<Enemy> wave{{1, 2.0f, 0}, {2, 4.0f, 30}, {3, 12.0f, 30}};
    std::printf("turret targets enemy %d\n", pick_target(wave, 5.0f));
    std::vector<Enemy> far{{7, 50.0f, 30}};
    std::printf("turret targets enemy %d\n", pick_target(far, 5.0f));
}
```
```text
turret targets enemy 1
turret targets enemy 7
```

## What went wrong

Two bugs, both from starting the search at element 0 without checking it:

1. Enemy 1 is dead but closest. It was taken as the starting "best", and no live enemy beat its distance, so the turret shoots a corpse.
2. Enemy 7 is out of range, but as the only element it is returned anyway. There is also no way to say "no target"; and an empty list would read `enemies[0]` out of bounds.

Raw loops mix the *what* (nearest live enemy in range) with the *how* (indices, a best-so-far variable, a start value). Each detail is a place for a bug.

## The fix: filter, then min_element

```cpp
#include <algorithm>
#include <cstdio>
#include <optional>
#include <ranges>
#include <vector>

struct Enemy { int id; float dist; int hp; };

std::optional<int> pick_target(const std::vector<Enemy>& enemies, float range) {
    auto valid = enemies | std::views::filter([range](const Enemy& e) {
        return e.hp > 0 && e.dist <= range;
    });
    auto it = std::ranges::min_element(valid, {}, &Enemy::dist);
    if (it == valid.end()) return std::nullopt;
    return it->id;
}

int main() {
    std::vector<Enemy> wave{{1, 2.0f, 0}, {2, 4.0f, 30}, {3, 12.0f, 30}};
    std::vector<Enemy> far{{7, 50.0f, 30}};
    for (const auto* w : {&wave, &far}) {
        if (auto t = pick_target(*w, 5.0f)) std::printf("turret targets enemy %d\n", *t);
        else std::printf("turret waits\n");
    }
}
```
```text
turret targets enemy 2
turret waits
```

Each line says one thing: which enemies qualify, and that we want the one with the smallest `dist`. `min_element` on an empty range returns `end()`, which we turn into "no target" with `std::optional` (its own lesson comes soon).

## Lazy pipelines

`views::filter` did not build a new vector. Views are **lazy**: they compute each element only when something iterates over them. Chains like `filter | transform | take` allocate nothing.

## Algorithms worth knowing

Useful algorithms for games: `sort` and `stable_sort` (draw order by y), `partition` (live enemies to the front), `nth_element` (k-th smallest), `partial_sort` (top k), `accumulate` (total damage), `any_of` / `all_of` (is any enemy alive?).

## When to use it, and when not

- Use algorithms when one exists for what you mean. The name documents the intent, and they handle the empty case.
- A plain `for` loop is fine when the body does several unrelated things per element. Do not force it into a five-stage pipeline.
- `views::filter` is re-evaluated each time you iterate the view. Iterate it once, or store the results.
- Pass projections (`&Enemy::dist`) instead of writing comparison lambdas by hand.
