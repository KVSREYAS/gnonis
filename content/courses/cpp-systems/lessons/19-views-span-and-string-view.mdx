## The feature: one damage function for every hp array

Slimes keep their hp in a `std::vector<int>`. The boss has a fixed `int armor[4]` (one per body part). The particle system has a raw buffer from the frame allocator. All of them need "subtract damage from these hp values".

## The careless version: pointer plus count

```cpp
#include <cstdio>

struct Boss { int armor[4] = {50, 50, 50, 50}; int hp = 500; };

void apply_damage(int* hp, int count, int dmg) {
    for (int i = 0; i < count; ++i) hp[i] -= dmg;
}

int main() {
    Boss* boss = new Boss;
    int slime_hp[8] = {20, 20, 20, 20, 20, 20, 20, 20};
    apply_damage(slime_hp, 8, 5);
    apply_damage(boss->armor, 8, 5);    // copy-pasted the 8 from the line above
    std::printf("boss hp %d\n", boss->hp);
    delete boss;
}
```
```text
==1==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x503000000054 at pc 0x55c869b44297 bp 0x7ffe7b1468d0 sp 0x7ffe7b1468c8
SUMMARY: AddressSanitizer: heap-buffer-overflow game.cpp:6 in apply_damage(int*, int, int)
```

## What went wrong

The function got a pointer and a separate count, and nothing connected the two. The second call passed 8 for a 4-element array. The fifth write landed on `hp`, right after `armor` in the same object: the boss lost 5 hp from an attack that should only hit armour. ASan cannot see that one, because it is still inside the `Boss` allocation. It caught the sixth write, past the end of the object. Without ASan, writes six to eight would silently corrupt whatever lives next on the heap.

The count is information the compiler already had, for both the vector and the array. Passing it by hand is where the bug came in.

## The fix: std::span

`std::span<int>` is a pointer and a size **in one object**, built from the container itself:

```cpp
#include <cstdio>
#include <span>
#include <vector>

struct Boss { int armor[4] = {50, 50, 50, 50}; int hp = 500; };

void apply_damage(std::span<int> hp, int dmg) {
    for (int& h : hp) h -= dmg;
}

int main() {
    Boss boss;
    std::vector<int> slime_hp(8, 20);
    apply_damage(slime_hp, 5);           // size from the vector
    apply_damage(boss.armor, 5);         // size from the array type: 4
    apply_damage(std::span(slime_hp).first(2), 10);   // only the first two slimes
    std::printf("armor[3] %d, boss hp %d, slime 0: %d, slime 7: %d\n",
                boss.armor[3], boss.hp, slime_hp[0], slime_hp[7]);
}
```
```text
armor[3] 45, boss hp 500, slime 0: 5, slime 7: 15
```

No count to get wrong. `first(n)`, `last(n)` and `subspan(off, n)` make smaller views of the same data.

`span<int>` lets the function write; `span<const int>` makes it read-only. A `span<int>` converts to `span<const int>`, not the other way.

## string_view for names

`std::string_view` is the same idea for text: a `const char*` and a length. A function like `bool is_boss(std::string_view name)` accepts a `std::string`, a string literal, or part of a larger string, with no allocation.

The danger is the same as every view: the text must outlive it. `std::string_view name = make_name();` (a function returning `std::string`) dangles at the semicolon. The lifetime module covered this bug in detail.

## When to use it, and when not

- Use `std::span<T>` / `std::span<const T>` for function parameters that read or write a contiguous sequence they do not own.
- Use `std::string_view` for read-only text parameters.
- Do not store a span or string_view in an object that may outlive the data (a member of a long-lived class, a lambda saved for later). Store a `std::vector` or `std::string` there.
- A span cannot grow. If the function must add elements, take `std::vector<T>&`.
