## The feature: the enemy component

Each enemy has a small "state" component the AI updates every frame. A wave can hold 50,000 of them, and the AI walks all of them every frame.

## The careless version

```cpp
#include <cstddef>
#include <cstdio>

struct EnemyState {
    bool     aggro;      // chasing the player?
    double   last_seen;  // time the player was last seen
    bool     stunned;
    int      target_id;
    bool     fleeing;
    short    path_step;
};

int main() {
    std::printf("sizeof %zu, alignof %zu\n", sizeof(EnemyState), alignof(EnemyState));
    std::printf("offsets: aggro %zu, last_seen %zu, stunned %zu, target_id %zu, fleeing %zu, path_step %zu\n",
        offsetof(EnemyState, aggro), offsetof(EnemyState, last_seen), offsetof(EnemyState, stunned),
        offsetof(EnemyState, target_id), offsetof(EnemyState, fleeing), offsetof(EnemyState, path_step));
    std::printf("useful bytes: %zu\n", sizeof(bool) * 3 + sizeof(double) + sizeof(int) + sizeof(short));
}
```
```text
sizeof 32, alignof 8
offsets: aggro 0, last_seen 8, stunned 16, target_id 20, fleeing 24, path_step 26
useful bytes: 17
```

## What went wrong

17 useful bytes take 32. `aggro` sits at 0, but `last_seen` is a `double`, which must start at a multiple of 8: 7 bytes of padding. `target_id` must start at a multiple of 4: 3 more. At the end, the size rounds up to a multiple of 8. Nearly half the struct is padding, so 50,000 enemies drag 750 KB of nothing through the cache every frame.

The second problem shows up later: someone writes the save file with `fwrite(&state, sizeof state, 1, f)`. The padding bytes contain whatever was in memory, and adding a member shifts every offset, so old save files no longer load.

## The fix: order by alignment

```cpp
#include <cstdio>

struct EnemyState {
    double   last_seen;   // 8-byte members first
    int      target_id;   // then 4
    short    path_step;   // then 2
    bool     aggro;       // then 1
    bool     stunned;
    bool     fleeing;
};

int main() {
    std::printf("sizeof %zu\n", sizeof(EnemyState));
}
```
```text
sizeof 24
```

Same members, 24 bytes instead of 32. Only 7 bytes of padding are left (at the end, so arrays stay 8-aligned).

## Why alignment exists

A misaligned load can be slower, can span two cache lines, and on some CPUs faults. SIMD loads like `_mm256_load_ps` require 32-byte alignment. The compiler pads so that every member of every object is aligned without you thinking about it.

Sources: [cppreference: object alignment](https://en.cppreference.com/w/cpp/language/object#Alignment), [The Lost Art of Structure Packing (Eric S. Raymond)](http://www.catb.org/esr/structure-packing/)

## When to use it, and when not

- Reorder members in structs you store by the thousand. Check with `sizeof` and a `static_assert(sizeof(EnemyState) == 24)` so a later edit cannot silently grow it.
- Do not use `#pragma pack` or `__attribute__((packed))` to remove padding in hot structs: misaligned members are slower to read, and taking their address is dangerous. Use packing only for file and network formats, and even there prefer explicit serialization.
- Smaller types help too: an `int` hp that never exceeds 1,000 fits in a `short`.
