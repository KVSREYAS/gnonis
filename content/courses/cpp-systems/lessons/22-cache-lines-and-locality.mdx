## The feature: updating every enemy each frame

Each frame, every enemy moves by its velocity. That is two additions per enemy: no real work. The question is only how fast we can walk over the enemies.

## The careless version: a list of heap nodes

A list looks natural for enemies: they are added and removed all the time, and a list does that without moving anything. Here 1,000,000 enemies are updated as a `std::list` (one heap node each, allocated in a shuffled order as they would be after a few minutes of spawning and dying) and as a `std::vector`:

```cpp
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <list>
#include <memory>
#include <random>
#include <vector>

struct Enemy { float x, y, vx, vy; };

template <class C>
double update_ms(C& enemies) {
    auto t0 = std::chrono::steady_clock::now();
    for (int frame = 0; frame < 10; ++frame)
        for (auto& e : enemies) { e.x += e.vx; e.y += e.vy; }
    return std::chrono::duration<double, std::milli>(std::chrono::steady_clock::now() - t0).count() / 10;
}

int main() {
    const int N = 1'000'000;
    std::vector<Enemy> vec(N, Enemy{0, 0, 1, 1});
    // build the list by inserting at random positions, so its nodes are scattered in memory
    std::list<Enemy> lst;
    std::vector<std::list<Enemy>::iterator> its;
    std::mt19937 rng(1);
    for (int i = 0; i < N; ++i) {
        auto pos = its.empty() ? lst.end() : its[rng() % its.size()];
        its.push_back(lst.insert(pos, Enemy{0, 0, 1, 1}));
    }
    std::printf("list:   %.2f ms per frame\n", update_ms(lst));
    std::printf("vector: %.2f ms per frame\n", update_ms(vec));
}
```
```text
list:   49.38 ms per frame
vector: 0.84 ms per frame
```

(One run on the course machine; your numbers will differ, but the list stays many times slower.)

## What went wrong

Both loops do the same two additions per enemy. The list version spends its time waiting for memory. Each node is a separate heap block, and after random inserts, the next node is somewhere unrelated in memory. Every `++it` is a load whose address depends on the previous load, so the CPU cannot fetch ahead, and most of those loads miss the cache.

The vector's enemies are packed back to back: one 64-byte cache line holds four 16-byte enemies, and the prefetcher sees the sequential pattern and loads lines before the loop needs them. The list also wastes memory: each 16-byte enemy carries two 8-byte pointers plus the allocator's header.

At 60 FPS the frame budget is 16.7 ms. On this run the list version alone used about three frames' worth of time for two additions per enemy.

## Cache lines

Memory moves between DRAM and the CPU in **cache lines** of 64 bytes. A miss to DRAM costs around 100 ns; a hit in L1 about 1 ns. The rule that follows: **use all of each line you load, and load lines in an order the prefetcher can predict.**

## Traversal order

For a 2D array `float a[N][N]` (or a tile map `tiles[y * W + x]`), `a[i][j]` and `a[i][j+1]` are neighbours in memory, while `a[i+1][j]` is N×4 bytes away. Walk the last index in the inner loop.

Sources: Ulrich Drepper, [What Every Programmer Should Know About Memory](https://people.freebsd.org/~lstewart/articles/cpumemory.pdf), Scott Meyers, [CPU Caches and Why You Care](https://www.youtube.com/watch?v=WDIkqP4JbkE)

## When to care, and when not

- Store anything iterated every frame in contiguous arrays (`std::vector`, `std::array`). Remove by swapping with the last element, or by `erase_if` once per frame.
- Use ids or indices to refer between objects, not pointers to separately allocated nodes.
- A `std::list` or `std::map` is fine for small or rarely walked collections (the list of open menus).
- Locality matters most when the data does not fit in cache. For 100 enemies, everything is in L1 anyway.
