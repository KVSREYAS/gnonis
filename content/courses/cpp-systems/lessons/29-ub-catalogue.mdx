## The feature: wall auto-tiling

Walls connect to their neighbours: a wall tile picks its sprite from which of its 8 neighbours are also walls. The map editor runs this for every wall tile.

## The careless version: no edge check

```cpp
#include <cstdio>
#include <vector>

struct Map {
    int w, h;
    std::vector<int> tiles;                   // 1 = wall
    int at(int x, int y) const { return tiles[y * w + x]; }
};

int wall_neighbours(const Map& m, int x, int y) {
    int n = 0;
    for (int dy = -1; dy <= 1; ++dy)
        for (int dx = -1; dx <= 1; ++dx)
            if ((dx || dy) && m.at(x + dx, y + dy) == 1) ++n;
    return n;
}

int main() {
    Map m{4, 4, std::vector<int>(16, 1)};
    std::printf("centre tile: %d wall neighbours\n", wall_neighbours(m, 1, 1));
    std::printf("corner tile: %d wall neighbours\n", wall_neighbours(m, 0, 0));
}
```
```text
==1==ERROR: AddressSanitizer: heap-buffer-overflow on address 0x50600000000c at pc 0x561da76cc44b bp 0x7fff69f730d0 sp 0x7fff69f730c8
SUMMARY: AddressSanitizer: heap-buffer-overflow game.cpp:7 in Map::at(int, int) const
```

## What went wrong

For the corner tile at (0, 0), the loop reads (-1, -1), which is index -5: before the start of the vector's buffer. ASan reports a heap buffer overflow at the first bad read.

Without ASan, nothing reports anything. The read returns whatever bytes sit before the buffer (allocator bookkeeping, another object), so the corner's sprite depends on the heap layout: different on different machines, different between debug and release. Tiles at the left edge also read the previous row's last tile (x = -1 wraps into row y - 1), which is a valid index and gives a quietly wrong answer that no tool will catch.

The fix is a bounds check in `at`, treating outside-the-map as a wall (or as empty, whichever looks right). The coding task below asks for exactly that.

## The catalogue

These are the kinds testers find in release builds:

- **Out of bounds**: reading or writing past an array, as above.
- **Use after free / dangling**: the lifetime and STL modules.
- **Signed overflow**: score, timers, coordinates. The optimizer deletes overflow checks written after the fact.
- **Null dereference**: and the optimizer deletes null checks placed after the dereference.
- **Uninitialized reads**: `int hp;` with no initializer, read before assignment.
- **Data races**: the concurrency module.
- **Bad shifts**: `1 << 32` for a 32-bit `int`, or shifting a negative number left.

## Uninitialized values

An uninitialized local holds whatever was in that memory before. It can change between runs, with optimization level, and when you add a line of logging:

```cpp
#include <cstdio>

struct Enemy { int hp; bool stunned; };   // no initializers

int main() {
    Enemy e;                              // hp and stunned are indeterminate
    e.hp = 30;                            // forgot stunned
    if (e.stunned) std::printf("enemy skips its turn\n");
    else           std::printf("enemy attacks\n");
}
```
```text
$ g++ -std=c++20 -O2 -Wall game.cpp
game.cpp:8: warning: 'e.Enemy::stunned' is used uninitialized [-Wuninitialized]
$ ./game
enemy attacks
```

The output above is whatever this build happened to produce, which is the problem: the language does not say what it prints. `-Wall` caught it here, but not every case. The fix is default member initializers: `struct Enemy { int hp = 0; bool stunned = false; };`.

## When to worry

- Treat every UB kind as a real bug even if the program "works". It works with this compiler, these flags, this heap layout.
- Turn on warnings (`-Wall -Wextra`) and fix them: many UB cases are caught at compile time.
- Run tests under ASan + UBSan. The next lessons cover aliasing and the sanitizers in detail.
