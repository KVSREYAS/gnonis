## The feature: packets and save files

Multiplayer sends packets: a byte buffer with a header (a 4-byte message tag) followed by fields. The save system does the same thing on disk. Both need to put `int`s and `float`s into a buffer of bytes and get them back.

## The careless version: cast the buffer pointer

The packet writer reuses one buffer slot. It writes the tag, and then a later field writer overwrites the same 4 bytes with a float (a bug in the offset table, but an innocent-looking one):

```cpp
#include <cstdint>
#include <cstdio>
#include <cstring>

__attribute__((noinline)) std::uint32_t write_fields(std::uint32_t* tag, float* speed) {
    *tag = 0x534C494D;          // 'SLIM'
    *speed = 1.0f;              // offset table bug: same 4 bytes
    return *tag;                // what tag did we send?
}

int main() {
    alignas(4) unsigned char packet[4];
    std::uint32_t sent = write_fields(reinterpret_cast<std::uint32_t*>(packet),
                                      reinterpret_cast<float*>(packet));
    std::uint32_t actual; std::memcpy(&actual, packet, 4);
    std::printf("log says tag %08X, packet holds %08X\n", sent, actual);
}
```

Debug build (`-O0`):

```text
log says tag 3F800000, packet holds 3F800000
```


Release build (`-O2`), same source:

```text
log says tag 534C494D, packet holds 3F800000
```

## What went wrong

The strict aliasing rule says a `float*` and a `uint32_t*` cannot point to the same object. So at `-O2` the compiler reasoned: writing through `speed` cannot change `*tag`, so `return *tag` must return the value just stored, `0x534C494D`, without reading memory again. The log now says the packet carried a tag it did not carry. In the debug build, the value was re-read and the overlap was visible.

The offset bug was real, but the aliasing violation hid it: the release build's own log disagreed with the bytes it sent.

## The legal ways

- `std::memcpy(&value, buffer + offset, sizeof value)`: copies bytes. Legal for any trivially copyable type, works at any alignment, and compiles to a single load.
- `std::bit_cast<To>(from)` (C++20): reinterprets an object's bits as another type of the same size. Also `constexpr`.
- Access through `unsigned char*`, `char*` or `std::byte*` is always allowed.

```cpp
#include <bit>
#include <cstdint>
#include <cstdio>
#include <cstring>

void put_f32(unsigned char* buf, std::size_t off, float v) { std::memcpy(buf + off, &v, 4); }
float get_f32(const unsigned char* buf, std::size_t off) { float v; std::memcpy(&v, buf + off, 4); return v; }

int main() {
    unsigned char packet[16] = {};
    put_f32(packet, 5, 3.75f);                  // offset 5: not 4-aligned, still fine
    std::printf("speed back: %.2f\n", get_f32(packet, 5));
    std::printf("bits of 1.0f: %08X\n", std::bit_cast<std::uint32_t>(1.0f));
}
```
```text
speed back: 3.75
bits of 1.0f: 3F800000
```

## When to use it, and when not

- Use `memcpy` to read and write fields in packets, save files and any byte buffer.
- Use `std::bit_cast` to look at the bits of a value (hashing floats, compressing positions).
- Never `reinterpret_cast` a buffer to `int*` or `float*` and dereference it, and never pun through a union in C++.
- Byte order matters for files shared between machines; `memcpy` keeps the host's order. Almost all game platforms today are little-endian, but a file format should say which it uses.

## Coding task: compress positions

Sources: [cppreference: std::bit_cast](https://en.cppreference.com/w/cpp/numeric/bit_cast), [type aliasing rules](https://en.cppreference.com/w/cpp/language/reinterpret_cast#Type_aliasing)

The replay system stores thousands of positions per second. Keeping only the top 16 bits of each float (bfloat16) halves the file size, with about 2-3 significant digits left.
