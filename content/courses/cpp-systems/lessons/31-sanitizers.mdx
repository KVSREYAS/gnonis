## The feature: the test build

The test build of Slime Siege gets a second configuration: same code, compiled with sanitizers, run by the automated tests and by testers on a few machines. It is slower, but every memory error stops the game with the exact line.

## The careless version: a bug that looks fine

The inventory has 8 slots. Picking up an item when the bag is full has an off-by-one:

```cpp
#include <cstdio>

struct Bag {
    int slots[8] = {};
    int count = 0;
    int gold = 100;
    void pick_up(int item) { if (count <= 8) slots[count++] = item; }   // should be < 8
};

int main() {
    Bag* bag = new Bag;
    for (int i = 1; i <= 9; ++i) bag->pick_up(i);
    std::printf("items: %d, gold: %d\n", bag->count, bag->gold);
    delete bag;
}
```

Normal `-O2` build:

```text
items: 9, gold: 100
```

## What went wrong

The ninth item was written to `slots[8]`, which does not exist. In this build, that memory is `count`: `count++` had just made it 9, and the stray write stored item 9 there, so it is 9 again by coincidence. Nothing crashed, and the output looks exactly right, even though the bag claims 9 items in 8 slots. Change the struct layout, or the compiler, and the same write lands on `gold` instead.

The same program under `-fsanitize=address,undefined`:

```cpp
#include <cstdio>

struct Bag {
    int slots[8] = {};
    int count = 0;
    int gold = 100;
    void pick_up(int item) { if (count <= 8) slots[count++] = item; }   // should be < 8
};

int main() {
    Bag* bag = new Bag;
    for (int i = 1; i <= 9; ++i) bag->pick_up(i);
    std::printf("items: %d, gold: %d\n", bag->count, bag->gold);
    delete bag;
}
```
```text
game.cpp:7:59: runtime error: index 8 out of bounds for type 'int [8]'
```

UBSan's bounds check knows `slots` has 8 elements and stops at the bad index, naming the line. ASan alone would not catch this one: `slots[8]` is still inside the `Bag` allocation. That is why the two are used together.

## Which sanitizer finds what

![Three sanitizers (ASan, UBSan, TSan) checking memory, arithmetic and threads, with slowdown factors](/diagrams/cpp-systems/08-ub/03-sanitizers.png)

- **ASan** (`-fsanitize=address`): reads and writes outside heap, stack and global objects; use after free; double free; leaks at exit.
- **UBSan** (`-fsanitize=undefined`): signed overflow, out-of-bounds indexing of arrays with known size, null dereference, bad shifts, misaligned pointers.
- **TSan** (`-fsanitize=thread`): data races between threads. Separate build: it cannot be combined with ASan.

Build with `-g` for line numbers, and `-O1` keeps it reasonably fast while keeping the stack traces readable.

## When to use them, and when not

- Run the whole test suite under ASan + UBSan in CI, on every change.
- Run the multithreaded code (asset loader, job system) under TSan in a separate job.
- Give testers a sanitizer build for a day before each release.
- Do not ship sanitizer builds to players: they are slower, use more memory, and abort on the first error.
- A clean sanitizer run proves only that the code paths you ran were clean. Test the edge cases (full inventory, empty level, last enemy).

Sources: [Clang AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html), [ThreadSanitizer](https://clang.llvm.org/docs/ThreadSanitizer.html), [UBSan](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html). (Every reference solution in this course is tested under ASan+UBSan.)
