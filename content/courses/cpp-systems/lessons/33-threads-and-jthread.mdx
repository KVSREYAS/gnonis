## The feature: a loader you can cancel

The level loader runs on its own thread. If the player opens the menu and picks "Quit to title" while it runs, the game should stop loading and leave promptly.

## The careless version: std::thread and an early return

```cpp
#include <chrono>
#include <cstdio>
#include <thread>

void load_level() { std::this_thread::sleep_for(std::chrono::milliseconds(50)); }

bool player_quit() { return true; }       // the player hit "Quit to title"

int run_level() {
    std::thread loader(load_level);
    if (player_quit()) {
        std::printf("returning to title screen\n");
        std::fflush(stdout);
        return 0;                          // loader is still joinable here
    }
    loader.join();
    return 1;
}

int main() { run_level(); }
```
```text
returning to title screen
terminate called without an active exception
Aborted
[exit code 134]
```

## What went wrong

Leaving `run_level` destroyed `loader` while it was still **joinable** (started and not yet joined or detached). `std::thread`'s destructor then calls `std::terminate`, which aborts the whole game (exit code 134 is 128 + SIGABRT). Every early return, `break` and exception between creating a `std::thread` and joining it has this bug.

Calling `detach()` instead would let the loader keep running after `run_level` returned, possibly writing into a level object that no longer exists.

## The fix: std::jthread and a stop token

`std::jthread` (C++20) is RAII for threads. Its destructor calls `request_stop()` and then `join()`. If the thread function takes a `std::stop_token` as its first parameter, it can check `stop_requested()` and give up early:

```cpp
#include <chrono>
#include <cstdio>
#include <stop_token>
#include <thread>

void load_level(std::stop_token st) {
    for (int file = 1; file <= 100; ++file) {
        if (st.stop_requested()) { std::printf("loader: stopped after %d files\n", file - 1); return; }
        std::this_thread::sleep_for(std::chrono::milliseconds(2));   // load one file
    }
    std::printf("loader: all files loaded\n");
}

int run_level() {
    std::jthread loader(load_level);
    std::this_thread::sleep_for(std::chrono::milliseconds(15));
    std::printf("returning to title screen\n");
    return 0;                       // ~jthread: request_stop(), then join()
}

int main() { run_level(); std::printf("title screen\n"); }
```
```text
returning to title screen
loader: stopped after 8 files
title screen
```

The exact number of files depends on timing; the order of the messages does not. The loader finished its current file, saw the stop request, and returned before `run_level` did.

## When to use it, and when not

- Use `std::jthread` for every thread you start. Plain `std::thread` has no advantage in new code.
- Check the stop token at natural break points (between files, between chunks). Stopping is cooperative: nothing interrupts a thread in the middle of a file read.
- Do not start a thread per small task (per enemy, per particle batch): starting one costs tens of microseconds. Use a fixed pool of workers, built in the building-blocks module.
- Pass data to a thread by value or by moving it in. Capturing locals by reference in a thread that outlives them is the lambda-capture bug again, with a thread on top.
