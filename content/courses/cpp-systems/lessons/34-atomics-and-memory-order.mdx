## The feature: "level ready" and the progress bar

The loader thread builds the next `Level` and then signals that it is ready. Meanwhile it bumps a "files loaded" counter that the main thread draws as a progress bar.

## The careless version: a plain flag

```cpp
#include <chrono>
#include <cstdio>
#include <thread>
#include <vector>

struct Level { std::vector<int> tiles; };

Level* next_level = nullptr;
bool ready = false;                       // plain bool
int files_loaded = 0;                     // plain int

int main() {
    std::thread loader([] {
        for (int i = 0; i < 10; ++i) ++files_loaded;
        next_level = new Level{std::vector<int>(1024, 1)};
        ready = true;
    });
    for (int frame = 0; frame < 1000 && !ready; ++frame)       // main loop: draw progress
        std::this_thread::sleep_for(std::chrono::microseconds(100));
    if (ready) std::printf("level has %zu tiles\n", next_level->tiles.size());
    loader.join();
    delete next_level;
}
```

## What went wrong

ThreadSanitizer reports a **data race**: one thread writes `ready` while the other reads it, with nothing ordering the two. That is undefined behaviour, and in practice it breaks in two ways:

1. **Reordering.** The compiler or CPU may make `ready = true` visible before the writes that built the level. The main thread then reads `next_level` while it is still null or half-built.
2. **Hoisting.** In a loop like `while (!ready) {}`, the compiler may read `ready` once and never again, because nothing in the loop could change a plain `bool`. The main thread then waits forever.

The output line may print correctly here. That is luck, not correctness, and TSan tells you so.

## The fix: atomics with release and acquire

```cpp
#include <atomic>
#include <chrono>
#include <cstdio>
#include <thread>
#include <vector>

struct Level { std::vector<int> tiles; };

Level* next_level = nullptr;
std::atomic<bool> ready{false};
std::atomic<int> files_loaded{0};

int main() {
    std::jthread loader([] {
        for (int i = 0; i < 10; ++i) files_loaded.fetch_add(1, std::memory_order_relaxed);   // just a count
        next_level = new Level{std::vector<int>(1024, 1)};
        ready.store(true, std::memory_order_release);              // publish everything above
    });
    while (!ready.load(std::memory_order_acquire))                 // see everything before the release
        std::this_thread::sleep_for(std::chrono::microseconds(100));
    std::printf("level has %zu tiles, %d files loaded\n", next_level->tiles.size(), files_loaded.load());
    loader.join();
    delete next_level;
}
```
```text
level has 1024 tiles, 10 files loaded
```

TSan is quiet. The **release** store on `ready` and the **acquire** load that reads `true` form a pair: every write the loader made before the release (building the level, setting `next_level`) is visible to the main thread after the acquire. That is the **message-passing** pattern.

![Producer release-store and consumer acquire-load forming a synchronizes-with edge that carries payload=42](/diagrams/cpp-systems/09-concurrency/02-atomics-and-memory-order.png)

The progress counter uses `relaxed`: the main thread only needs a value that is not torn, not any ordering with other data.

## When to use it, and when not

- Use `std::atomic` for single values shared between threads: flags, counters, a pointer to published data.
- Use release/acquire for "I finished writing X, you may read it". Use relaxed only for counters and statistics nobody uses to decide what else to read.
- When unsure, use the default (`seq_cst`). It is never less correct.
- If several values must change together (a position and a velocity), an atomic per value is not enough: use a mutex.
