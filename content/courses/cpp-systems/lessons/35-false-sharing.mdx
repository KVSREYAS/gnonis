## The feature: per-worker statistics

The debug overlay shows how many entities each worker thread processed this frame. Each worker has its own counter slot, so there is no sharing and no lock. Or so it seems.

## The careless version: counters side by side

```cpp
#include <atomic>
#include <chrono>
#include <cstdio>
#include <thread>
#include <vector>

struct Plain  { std::atomic<long> n{0}; };                 // 8 bytes: 8 per cache line
struct alignas(64) Padded { std::atomic<long> n{0}; };     // 64 bytes: one per line

template <class Slot>
double run(int workers) {
    std::vector<Slot> stats(workers);
    auto t0 = std::chrono::steady_clock::now();
    {
        std::vector<std::jthread> ts;
        for (int w = 0; w < workers; ++w)
            ts.emplace_back([&stats, w] {
                for (int i = 0; i < 5'000'000; ++i) stats[w].n.fetch_add(1, std::memory_order_relaxed);
            });
    }
    return std::chrono::duration<double, std::milli>(std::chrono::steady_clock::now() - t0).count();
}

int main() {
    std::printf("1 worker:                %6.1f ms\n", run<Plain>(1));
    std::printf("4 workers, side by side: %6.1f ms\n", run<Plain>(4));
    std::printf("4 workers, padded:       %6.1f ms\n", run<Padded>(4));
}
```
```text
1 worker:                  23.3 ms
4 workers, side by side:  290.1 ms
4 workers, padded:         23.3 ms
```

(One run on the course machine, which has 8 cores. Each worker does the same amount of work in every case.)

## What went wrong

The four `Plain` counters are 8 bytes each, so all four sit in one 64-byte cache line. Caches stay coherent per line: when worker 0 writes its counter, the copies of that line in the other cores' caches are invalidated, and the next write by worker 1 must fetch the line back. The line bounces between cores on nearly every increment. The workers share no data, yet they take turns.

That is **false sharing**. Padding each counter to its own line removes the bouncing, and four workers finish in about the time one worker takes.

## Two fixes

1. **Pad**: `struct alignas(64) Padded { ... };`, or `alignas(std::hardware_destructive_interference_size)`, the portable name for the line size.
2. **Accumulate locally**: count in a local variable inside the worker and write the slot once at the end. This is usually simpler and faster still, since a local lives in a register.

Sources: [cppreference: hardware_destructive_interference_size](https://en.cppreference.com/w/cpp/thread/hardware_destructive_interference_size), Herb Sutter, [Eliminate False Sharing (Dr. Dobb's)](https://www.drdobbs.com/parallel/eliminate-false-sharing/217500206)

## When to care, and when not

- The symptom: adding threads makes a loop slower, or no faster, even though the threads share no data.
- Care for data written often by different threads: counters, per-thread queues' head and tail indices, job system state.
- Data that is only read by several threads is fine on one line: reading does not invalidate other cores' copies.
- Do not pad everything: padding a million-element array to 64 bytes per element wastes memory and cache.
