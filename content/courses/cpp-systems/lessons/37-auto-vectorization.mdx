## The feature: moving every particle

Each frame, every particle moves by its velocity: `x[i] += vx[i] * dt`, over flat arrays from the data-oriented rewrite. There are no branches and no calls. It should be the best case for SIMD.

## The careless version: pointers that might overlap

```cpp
#include <chrono>
#include <cstdio>
#include <vector>

constexpr int N = 4096;

__attribute__((noipa)) void step(float* x, const float* vx, float dt) {
    for (int i = 0; i < N; ++i) x[i] += vx[i] * dt;
}
__attribute__((noipa)) void step_restrict(float* __restrict x, const float* __restrict vx, float dt) {
    for (int i = 0; i < N; ++i) x[i] += vx[i] * dt;
}

int main() {
    std::vector<float> x(N, 0.f), vx(N, 1.f);
    auto ms = [](auto d) { return std::chrono::duration<double, std::milli>(d).count(); };
    auto t0 = std::chrono::steady_clock::now();
    for (int f = 0; f < 100000; ++f) step(x.data(), vx.data(), 0.016f);
    auto t1 = std::chrono::steady_clock::now();
    for (int f = 0; f < 100000; ++f) step_restrict(x.data(), vx.data(), 0.016f);
    auto t2 = std::chrono::steady_clock::now();
    std::printf("float* x, const float* vx: %6.1f ms\n", ms(t1 - t0));
    std::printf("same with __restrict:      %6.1f ms\n", ms(t2 - t1));
}
```
```text
float* x, const float* vx:  118.6 ms
same with __restrict:        30.7 ms
```

(One run on the course machine, GCC at `-O2`.) The two loops are identical except for `__restrict`.

## What went wrong

The compiler must assume `x` and `vx` might point into the same memory: someone could call `step(buf + 1, buf, dt)`. Then writing `x[i]` changes `vx[i + 1]`, and processing four at once would read stale values. To vectorize anyway, the compiler would have to add a runtime overlap check and two versions of the loop. At `-O2`, GCC uses a "very cheap" cost model that refuses to do that, so the loop stays scalar. (At `-O3` it adds the check and both loops run at the fast speed.)

`__restrict` is a promise from you: through this function, the memory behind these pointers does not overlap. With that, the compiler vectorizes at `-O2`. Break the promise and the behaviour is undefined, so only add it when it is true.

## Other things that block vectorization

- **A dependency between iterations**: `x[i] = x[i - 1] * drag` needs the previous result, so lanes cannot run together.
- **Strided or indirect access**: `particles[i].x` in an array of big structs, or `x[index[i]]`. Some can be vectorized with gathers, most are not worth it.
- **Calls the compiler cannot see into**: a function in another file without LTO.
- **Float reductions**: summing into one variable would need the additions reordered.

## When to use it, and when not

- Use `__restrict` on hot loops over separate arrays you own: particle fields, audio buffers, pixel rows.
- Prefer it to hand-written intrinsics: the compiler then also uses AVX when you build with `-mavx2`, with no code change.
- Do not add it to pointers that can overlap, such as an in-place shift `move(buf + 1, buf)`. That is undefined behaviour and the vectorized loop will produce wrong numbers.
- Do not guess. Check with `-fopt-info-vec-missed`, and measure.
