## The feature: when has the explosion faded?

An explosion stays "active" (keeps its light, sound and screen shake) until the total kinetic energy of its particles drops below a threshold. That means summing one float per particle, every frame, for every explosion on screen.

## The careless version: one running total

```cpp
#include <chrono>
#include <cstdio>
#include <vector>

__attribute__((noipa)) float total_1(const float* e, int n) {
    float s = 0;
    for (int i = 0; i < n; ++i) s += e[i];
    return s;
}
__attribute__((noipa)) float total_8(const float* e, int n) {
    float s[8] = {};
    int i = 0;
    for (; i + 8 <= n; i += 8)
        for (int k = 0; k < 8; ++k) s[k] += e[i + k];
    float t = ((s[0] + s[1]) + (s[2] + s[3])) + ((s[4] + s[5]) + (s[6] + s[7]));
    for (; i < n; ++i) t += e[i];
    return t;
}

int main() {
    const int n = 65536;                                  // particles across all explosions
    std::vector<float> energy(n);
    for (int i = 0; i < n; ++i) energy[i] = 0.001f * (i % 1000);
    auto ms = [](auto d) { return std::chrono::duration<double, std::milli>(d).count(); };
    float a = 0, b = 0;
    auto t0 = std::chrono::steady_clock::now();
    for (int f = 0; f < 2000; ++f) a = total_1(energy.data(), n);
    auto t1 = std::chrono::steady_clock::now();
    for (int f = 0; f < 2000; ++f) b = total_8(energy.data(), n);
    auto t2 = std::chrono::steady_clock::now();
    std::printf("1 accumulator:  %6.1f ms  total %.3f\n", ms(t1 - t0), a);
    std::printf("8 accumulators: %6.1f ms  total %.3f\n", ms(t2 - t1), b);
}
```
```text
1 accumulator:    66.2 ms  total 32610.875
8 accumulators:    8.3 ms  total 32610.883
```

(One run on the course machine at `-O2`.) Same data, same adds. Note the totals differ in the last digits: the order of float additions changed.

## What went wrong

In `total_1`, every `s += e[i]` needs the `s` from the previous iteration. A float add takes about 4 cycles to produce its result, so the CPU starts one add every 4 cycles, even though it could start two per cycle. The adder sits mostly idle, waiting on one long chain.

The compiler will not split the chain for you. Float addition is not associative: `(a + b) + c` can round differently from `a + (b + c)`, and the compiler must keep your exact result unless you allow otherwise with `-ffast-math` or `-fassociative-math`.

## The concept: independent accumulators

Keep K running totals that do not depend on each other and combine them once at the end. The CPU overlaps the K chains. With 8 of them, GCC also packs them into two SSE registers, so the loop above is both overlapped and vectorized.

How many do you need? About latency × throughput: 4 cycles × 2 adds per cycle = 8.

## When to use it, and when not

- Use it for big sums, maxima and dot products in hot loops: particle energy, audio levels, physics totals.
- The result changes in the last bits. Fine for "has the explosion faded?". Not fine where two machines must agree bit for bit, such as a lockstep multiplayer simulation or a replay system: there, keep one fixed order everywhere.
- Integer sums do not have this problem (integer addition is associative), and the compiler already vectorizes them.
- Do not bother for a few dozen values: the combine step and the tail cost more than they save.

Sources: Agner Fog, [instruction tables](https://www.agner.org/optimize/instruction_tables.pdf), Travis Downs, [performance blog](https://travisdowns.github.io/)
