## The feature: should the particle buffer be cleared or reallocated?

Between waves, the effects system needs an empty particle buffer of 16 million floats. Someone writes a quick benchmark: time one clear, report it.

## The careless version: one sample

```cpp
#include <chrono>
#include <cstdio>
#include <cstring>
#include <memory>

int main() {
    const std::size_t n = 16 << 20;                          // 16 M floats = 64 MiB
    auto buf = std::make_unique_for_overwrite<float[]>(n);   // fresh memory, never touched
    auto ms = [](auto d) { return std::chrono::duration<double, std::milli>(d).count(); };
    for (int run = 1; run <= 4; ++run) {
        auto t0 = std::chrono::steady_clock::now();
        std::memset(buf.get(), 0, n * sizeof(float));
        auto t1 = std::chrono::steady_clock::now();
        std::printf("clear run %d: %6.2f ms   (buf[123] = %g)\n", run, ms(t1 - t0), buf[123]);
    }
}
```
```text
clear run 1:  32.34 ms   (buf[123] = 0)
clear run 2:   5.05 ms   (buf[123] = 0)
clear run 3:   2.09 ms   (buf[123] = 0)
clear run 4:   2.01 ms   (buf[123] = 0)
```

Same code, same buffer. The first run is several times slower than the others. If the benchmark had stopped after run 1, the team would have rewritten a clear that is actually fast.

## What went wrong

A fresh allocation is only reserved address space. The first write to each 4 KiB page causes a **page fault**: the operating system stops the program, finds a physical page, zeroes it, and maps it. Run 1 paid for the page faults (up to 16,384 of them, fewer if the system uses huge pages); later runs write to memory that is already mapped. Caches, branch predictors and CPU clock speed have similar warm-up effects.

## The concept: a benchmark you can trust

1. **Use the result** so the compiler cannot delete the work (the print of `buf[123]` above does that).
2. **Warm up**: run the code a few times before timing.
3. **Repeat** many times and look at the **distribution**: the median for "typical", the minimum for "best possible", and a high percentile for "how bad it gets".
4. **Match production**: the same input size, the same compiler flags.

For a game, the last point matters most for frame times. A game averaging 60 FPS that drops one frame in fifty to 50 ms feels worse than a steady 50 FPS. Players notice the worst frames, so report the median and the **p99** (the frame time that 99% of frames are faster than).

## When to benchmark, and when not

- Benchmark a small piece of code to compare two versions of it, after a profiler has shown that it matters.
- Do not trust a microbenchmark about caches: a 4 KiB working set stays in L1 in the benchmark but not in the real frame, next to everything else.
- Do not benchmark debug builds. `-O0` timings say nothing about the shipped game.
- For "is the game fast enough?", measure whole frames in the real game, not functions in isolation.

Sources: Chandler Carruth, [Tuning C++: Benchmarks, and CPUs, and Compilers! Oh My! (CppCon 2015)](https://www.youtube.com/watch?v=nXaxk27zwlk), [Google Benchmark user guide](https://github.com/google/benchmark/blob/main/docs/user_guide.md), Andrei Alexandrescu, *Writing Fast Code*

## Coding task: the frame-time report

The debug overlay records every frame's time in milliseconds. Turn a recording into the three numbers the team checks before each release.
