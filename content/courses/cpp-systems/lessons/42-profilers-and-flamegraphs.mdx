## The feature: finding the stutter

Wave 9 puts 2,000 slimes on screen and the frame rate drops. The team's guess: "drawing 2,000 sprites is slow". So they optimize drawing.

## The careless version: optimize the guess

```cpp
#include <chrono>
#include <cmath>
#include <cstdio>
#include <vector>

struct Slime { float x, y; int target; };
std::vector<Slime> slimes(2000);
float checksum = 0;

__attribute__((noinline)) void update_ai() {           // each slime follows its nearest neighbour
    for (auto& a : slimes) {
        float best = 1e30f;
        for (int j = 0; j < (int)slimes.size(); ++j) {
            float dx = slimes[j].x - a.x, dy = slimes[j].y - a.y, d = dx * dx + dy * dy;
            if (d > 0 && d < best) { best = d; a.target = j; }
        }
    }
}
__attribute__((noinline)) void update_physics() {
    for (auto& s : slimes) { s.x += 0.01f; s.y = std::fmod(s.y + 0.02f, 100.f); }
}
__attribute__((noinline)) void draw_old() {            // pretend each sprite costs two passes
    for (int pass = 0; pass < 2; ++pass) for (auto& s : slimes) checksum += s.x * 0.5f + s.y;
}
__attribute__((noinline)) void draw_new() {            // a week of work: twice as fast
    for (auto& s : slimes) checksum += s.x * 0.5f + s.y;
}

template <class Draw> double frame_ms(Draw draw) {
    auto t0 = std::chrono::steady_clock::now();
    for (int f = 0; f < 100; ++f) { update_ai(); update_physics(); draw(); }
    return std::chrono::duration<double, std::milli>(std::chrono::steady_clock::now() - t0).count() / 100;
}

int main() {
    for (int i = 0; i < (int)slimes.size(); ++i) slimes[i] = {float(i % 50), float(i / 50), 0};
    std::printf("frame with old draw: %.2f ms\n", frame_ms(draw_old));
    std::printf("frame with new draw: %.2f ms\n", frame_ms(draw_new));
    std::printf("(checksum %g)\n", checksum);
}
```
```text
frame with old draw: 3.32 ms
frame with new draw: 3.30 ms
(checksum 2.03066e+07)
```

Drawing really did get twice as fast. The frame did not notice, because drawing was never where the time went.

## The concept: measure where the time goes

There are two common ways, and real games use both.

**Zone timers in the game loop.** Wrap each phase of the frame in a small RAII object that adds its elapsed time to a named total. Every frame then reports its own breakdown, in the real game, on the real level. (Engines ship tools for this, such as Tracy or Unreal Insights.)

**A sampling profiler.** Linux `perf record -g ./game` interrupts the program about a thousand times a second and records the call stack. Here is a real flat profile of the same game loop (300 frames, one draw function), made with the older `gprof` (compile with `-pg`, run, then `gprof -b -p ./game`):

```text
  %   cumulative   self              self     total
 time   seconds   seconds    calls  ms/call  ms/call  name
 98.06      0.94     0.94      300     3.14     3.14  update_ai()
  2.09      0.96     0.02      300     0.07     0.07  update_physics()
  0.00      0.96     0.00      300     0.00     0.00  draw()
```

AI is 98% of the time. Each slime scans all 2,000 others: 4 million distance checks per frame. The fix is an algorithm change (the spatial grid from the containers module), not faster drawing.

## Flame graphs

A **flame graph** draws the sampled stacks: width is the share of samples, height is call depth. A wide box with nothing on top is a function spending its own time.

## Hardware counters

`perf stat ./game` prints counts such as instructions and cycles. Their ratio, **IPC**, says what kind of slow it is: well below 1 usually means waiting for memory (cache misses); near 3 to 4 means the CPU is busy computing, so do less work or use SIMD.

## When to use which, and when not

- Use a sampling profiler first when you do not know where to look. It needs no code changes and sees everything, including library calls.
- Use zone timers to watch known phases every frame, and to catch rare spikes that a whole-run profile averages away.
- Profile optimized builds with debug symbols (`-O2 -g`). A `-O0` profile shows costs that do not exist in the shipped game.
- Do not leave fine-grained zones in tight inner loops: reading the clock millions of times per frame costs time itself.

Sources: Brendan Gregg, [CPU Flame Graphs](https://www.brendangregg.com/FlameGraphs/cpuflamegraphs.html), [perf wiki](https://perf.wiki.kernel.org/index.php/Tutorial), Denis Bakhvalov, [*Performance Analysis and Tuning on Modern CPUs*](https://book.easyperf.net/perf_book)
