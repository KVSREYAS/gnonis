## The feature: the tile-map lighting pass

Each frame, the lighting pass visits every tile of the level and needs its (x, y) position. The level width is only known when the level loads.

## The careless version: x and y from one index

```cpp
#include <chrono>
#include <cstdio>
#include <vector>

__attribute__((noipa)) long light_div(const std::vector<int>& tiles, int w) {
    long s = 0;
    for (int i = 0; i < (int)tiles.size(); ++i) {
        int x = i % w, y = i / w;                       // looks cheap
        s += tiles[i] * (x + y);
    }
    return s;
}
__attribute__((noipa)) long light_nested(const std::vector<int>& tiles, int w) {
    long s = 0;
    int h = tiles.size() / w;
    for (int y = 0; y < h; ++y)
        for (int x = 0; x < w; ++x) s += tiles[y * w + x] * (x + y);
    return s;
}

int main(int argc, char**) {
    int w = 250 + argc;                                 // width known only at run time
    std::vector<int> tiles(w * 200, 1);
    long a = 0, b = 0;
    auto t0 = std::chrono::steady_clock::now();
    for (int f = 0; f < 2000; ++f) a += light_div(tiles, w);
    auto t1 = std::chrono::steady_clock::now();
    for (int f = 0; f < 2000; ++f) b += light_nested(tiles, w);
    auto t2 = std::chrono::steady_clock::now();
    auto ms = [](auto d) { return std::chrono::duration<double, std::milli>(d).count(); };
    std::printf("i %% w and i / w: %6.1f ms\n", ms(t1 - t0));
    std::printf("nested loops:    %6.1f ms   (same result: %s)\n", ms(t2 - t1), a == b ? "yes" : "no");
}
```
```text
i % w and i / w:  151.4 ms
nested loops:      49.7 ms   (same result: yes)
```

(One run at `-O2`.) Both functions compute the same sum.

## What went wrong: read the inner loop

Here is the inner loop of each function, from `g++ -O2 -S -masm=intel` (GCC 14.2), with nothing removed:

```text
light_div inner loop:                  light_nested inner loop:
.L3:                                   .L10:
    mov   eax, ecx                         mov   edx, DWORD PTR [rcx]
    cdq                                    add   rcx, 4
    idiv  esi                              imul  edx, eax
    add   edx, eax                         add   eax, 1
    imul  edx, DWORD PTR [r8+rcx*4]        movsx rdx, edx
    mov   rax, rcx                         add   rsi, rdx
    add   rcx, 1                           cmp   edi, eax
    movsx rdx, edx                         jne   .L10
    add   rdi, rdx
    cmp   rax, r9
    jne   .L3
```

`idiv esi` divides by `w` (the second argument, which arrived in `esi`) and produces both `i / w` and `i % w`. An integer division takes tens of cycles, and here it runs once per tile. When `w` is a compile-time constant the compiler replaces the division with a multiply, but our width comes from the level file. The nested version has no division at all: `x` and `y` are just counters.

## The concept: what to look for

- **Calling convention**: the first arguments arrive in `rdi`, `rsi`, `rdx`, `rcx` (or their 32-bit halves `edi`, `esi`...), floats in `xmm0`, `xmm1`...; results return in `rax` or `xmm0`.
- **`div`/`idiv` in a loop**: a division by a value the compiler does not know.
- **`call` in a loop**: a function that was not inlined.
- **`ps` vs `ss`**: `mulps` works on 4 floats (vectorized), `mulss` on one.
- **Many `[rsp+...]` loads and stores**: the loop ran out of registers and spills values to the stack.

## When to read assembly, and when not

- Read it for the few hot loops the profiler pointed at, to confirm that a change did what you meant: vectorized, inlined, no division.
- Read it to settle arguments like "the compiler optimizes that away anyway". It either did or it did not.
- Do not read it for code that is not hot. Most of the game is not.
- Do not hand-write assembly from it. Change the C++ (types, loop shape, `__restrict`, constants) and check again.
