## The feature: the frame arena

The combat system builds temporary records every frame (labels for the combat log, damage events, path nodes) and throws them all away when the frame ends. We give it a frame arena: one buffer, one offset, reset every frame.

## The careless version: bump without aligning

```cpp
#include <cstddef>
#include <cstdio>
#include <new>

struct FrameArena {                              // careless: no alignment
    alignas(16) std::byte buf[1024];
    std::size_t used = 0;
    void* alloc(std::size_t n) { void* p = buf + used; used += n; return p; }
};

struct Damage { double amount; int target; };   // needs 8-byte alignment

int main() {
    FrameArena arena;
    char* tag = static_cast<char*>(arena.alloc(3));          // "hit" label for the combat log
    tag[0] = 'h'; tag[1] = 'i'; tag[2] = 't';
    auto* d = new (arena.alloc(sizeof(Damage))) Damage{12.5, 7};
    std::printf("%.*s: %.1f damage to slime %d\n", 3, tag, d->amount, d->target);
}
```
```text
game.cpp:17:63: runtime error: member access within misaligned address 0x7f98f0a00033 for type 'struct Damage', which requires 8 byte alignment
0x7f98f0a00033: note: pointer points here
 00  68 69 74 00 00 00 00 00  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00 00  00 00 00 00 00 00 00
              ^ 
```

(Built with `-fsanitize=address,undefined`.) The 3-byte label left the offset at 3, so the `Damage` record starts at an address that is not a multiple of 8. A plain `-O2` build prints the right line on x86, which is why this bug survives testing. It is still undefined behaviour: on ARM consoles and phones, and with SIMD loads, misaligned access can crash or tear values.

## The concept: align, then bump

Every type has an alignment (`alignof(T)`): its address must be a multiple of it. An arena rounds the offset up before each allocation:

```cpp
std::size_t p = (off_ + align - 1) & ~(align - 1);   // round up; align is a power of two
if (p + n > cap_) return nullptr;                    // the frame's budget is used up
off_ = p + n;
return buf_ + p;
```

Allocation is a few instructions. Objects from one frame sit next to each other, which helps the cache. Resetting is `off_ = 0`.

## When to use an arena, and when not

- Use it for many objects that die together: per-frame scratch, per-level data (reset when the level unloads), a parsed save file.
- Do not use it for objects with their own lifetimes, like a slime that may die at any moment: freeing one object is impossible, so memory only grows until reset. Use a pool for those (the module test).
- Destructors do not run on reset. Store trivially destructible types (numbers, PODs, pointers into the arena), not `std::string` or `std::vector` that own heap memory.
- Pointers into the arena become dangling at reset. Nothing from the frame arena may be kept past the frame.

Sources: [cppreference: monotonic_buffer_resource](https://en.cppreference.com/w/cpp/memory/monotonic_buffer_resource), Ryan Fleury, [Untangling Lifetimes: The Arena Allocator](https://www.rfleury.com/p/untangling-lifetimes-the-arena-allocator)

## Coding task: scratch marks for the path search

The path search needs scratch memory only while it runs, but other systems allocate from the same frame arena before and after it. A **mark** saves the offset; **rewinding** to it frees only what was allocated since. The debug overlay also wants the **peak** offset, to size the arena.
