## The feature: the audio command queue

The audio thread fills the sound card's buffer every few milliseconds. If it is late even once, the player hears a click. So it must never wait for a lock held by the game thread. The game thread sends commands ("play splat.wav at 50% volume") through a fixed ring of slots: the game thread only pushes, the audio thread only pops.

## The careless version: plain integer indices

```cpp
#include <cstdio>
#include <thread>

struct AudioCmd { int sound; float volume; };

struct AudioQueue {                       // game thread pushes, audio thread pops
    AudioCmd buf[8];
    unsigned head = 0, tail = 0;          // careless: plain integers
    bool try_push(AudioCmd c) {
        if (head - tail == 8) return false;
        buf[head & 7] = c;
        ++head;
        return true;
    }
    bool try_pop(AudioCmd& out) {
        if (tail == head) return false;
        out = buf[tail & 7];
        ++tail;
        return true;
    }
};

AudioQueue q;

int main() {
    std::thread audio([] {
        int played = 0;
        AudioCmd c;
        for (long spins = 0; played < 100 && spins < 100'000'000; ++spins)
            if (q.try_pop(c)) ++played;
        std::printf("audio thread played %d of 100 sounds\n", played);
    });
    int sent = 0;
    for (long spins = 0; sent < 100 && spins < 100'000'000; ++spins)
        if (q.try_push({sent, 0.5f})) ++sent;
    std::printf("game thread sent %d of 100 sounds\n", sent);
    audio.join();
}
```
```text
audio thread played 8 of 100 sounds
game thread sent 16 of 100 sounds
```

(One run at `-O2`; the counts can differ between runs and compilers.) Most of the 100 sounds were never played. Each thread stopped seeing the other's index changes: the game thread believed the ring was full, and the audio thread believed it was empty. ThreadSanitizer names the cause:

```text
WARNING: ThreadSanitizer: data race (pid=1)
SUMMARY: ThreadSanitizer: data race game.cpp:12 in AudioQueue::try_push(AudioCmd)
```

## What went wrong

Two threads read and write `head` and `tail` with no synchronization: a data race, so undefined behaviour. In practice the compiler assumed no other thread changes `tail` inside the game thread's loop, read it once, and kept using that stale value. Even when the loop does re-read, nothing guarantees the audio thread sees the slot's data before it sees the new `head`.

## The concept: two atomic counters, one writer each

- `head_` counts items pushed. Only the producer writes it. `tail_` counts items popped. Only the consumer writes it.
- Empty: `head == tail`. Full: `head - tail == N`. Slot: `counter & (N - 1)` for a power-of-two N. Unsigned subtraction keeps working when the counters wrap.
- Producer: write the slot, then `head_.store(h + 1, release)`. Consumer: `head_.load(acquire)`, then read the slot. Release/acquire makes the slot's data visible before the new count. The same pairing in the other direction tells the producer a slot is free.
- `alignas(64)` on each counter keeps them on separate cache lines (no false sharing).

## When to use it, and when not

- Use it between exactly two threads where one must never block: game to audio, network thread to game, game to render thread.
- It is fixed size. Decide what happens when it is full: drop the command (fine for a footstep sound), or retry next frame (needed for "stop the music").
- With more than one producer or consumer it is wrong: two producers can claim the same slot. Use a mutex queue or an MPMC design.
- If nobody has a hard deadline, a mutex-protected `std::deque` is simpler and fast enough.

Sources: [Rigtorp, SPSCQueue](https://github.com/rigtorp/SPSCQueue), [1024cores: lock-free algorithms](https://www.1024cores.net/home/lock-free-algorithms/queues), Williams ch. 7
