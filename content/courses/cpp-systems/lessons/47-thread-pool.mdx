## The feature: the job system

The profiler showed AI eating most of the frame. Each slime's decision is independent of the others, so the frame splits AI into jobs and runs them on every core. Engines call this the **job system**.

## The careless version: a new thread for every job

```cpp
#include <atomic>
#include <chrono>
#include <condition_variable>
#include <cstdio>
#include <functional>
#include <mutex>
#include <queue>
#include <thread>
#include <vector>

std::atomic<long> decisions{0};
void think(int slime) { decisions.fetch_add(slime % 3, std::memory_order_relaxed); }   // a small AI job

int main() {
    const int frames = 100, jobs = 400, workers = 8;
    auto ms = [](auto d) { return std::chrono::duration<double, std::milli>(d).count(); };

    auto t0 = std::chrono::steady_clock::now();
    for (int f = 0; f < frames; ++f)
        for (int base = 0; base < jobs; base += workers) {        // a new thread per job, 8 at a time
            std::vector<std::jthread> ts;
            for (int k = 0; k < workers; ++k) ts.emplace_back(think, base + k);
        }
    auto t1 = std::chrono::steady_clock::now();

    std::mutex m; std::condition_variable cv, done_cv;
    std::queue<int> q; int pending = 0; bool stop = false;
    {
        std::vector<std::jthread> pool;
        for (int k = 0; k < workers; ++k) pool.emplace_back([&] {
            for (;;) {
                std::unique_lock lk(m);
                cv.wait(lk, [&] { return stop || !q.empty(); });
                if (q.empty()) return;
                int job = q.front(); q.pop();
                lk.unlock();
                think(job);
                lk.lock();
                if (--pending == 0) done_cv.notify_one();
            }
        });
        for (int f = 0; f < frames; ++f) {
            std::unique_lock lk(m);
            for (int j = 0; j < jobs; ++j) q.push(j);
            pending = jobs;
            cv.notify_all();
            done_cv.wait(lk, [&] { return pending == 0; });       // the frame waits for its AI
        }
        { std::scoped_lock lk(m); stop = true; }
        cv.notify_all();
    }
    auto t2 = std::chrono::steady_clock::now();
    std::printf("thread per job: %6.1f ms\n", ms(t1 - t0));
    std::printf("thread pool:    %6.1f ms   (decisions %ld)\n", ms(t2 - t1), decisions.load());
}
```
```text
thread per job:  820.6 ms
thread pool:      17.5 ms   (decisions 79800)
```

(One run at `-O2`, 100 frames of 400 small AI jobs, 8 threads at a time in both versions.) The jobs are the same. In the first version almost all the time goes into creating and joining threads: each one costs tens of microseconds, and a job here takes far less.

## The concept: create workers once, feed them jobs

A **thread pool** starts N worker threads when the game starts and keeps them until it quits. Between jobs they sleep on a condition variable, so idle workers cost nothing.

- **Queue**: `std::queue<std::function<void()>>` protected by a mutex.
- **Worker loop**: wait until there is a job or `stop` is set; pop one; unlock; run it.
- **submit(f)**: wrap `f` in a `std::packaged_task`, push it, `notify_one()`, and return the task's `std::future`. The caller calls `get()` when it needs the result. If the job threw, `get()` rethrows the exception.
- **Shutdown**: set `stop` under the lock, `notify_all()`, join. Workers finish the queue first.

## When to use it, and when not

- Use it for many independent jobs per frame: AI decisions, animation blending, particle batches, decoding.
- Make jobs big enough. A job that takes less time than a queue push and a wake-up (around a microsecond) is cheaper to run inline. Batch slimes, for example 64 per job.
- Use about as many workers as hardware threads, minus the ones the main and audio threads need. More workers than cores add switching without adding speed.
- Do not block inside a job waiting for another job in the same pool: with every worker waiting, nobody runs the job they wait for.

Sources: [cppreference: std::packaged_task](https://en.cppreference.com/w/cpp/thread/packaged_task), Williams ch. 9 (thread pools), Sean Parent, [Better Code: Concurrency](https://www.youtube.com/watch?v=zULU6Hhp42w)

## Coding task: parallel AI over slime ranges

The simplest use of many cores: split the slime array into one contiguous range per worker. Each slime is handled exactly once, and neighbouring slimes stay on the same core's cache.
