## The feature: the boss's view of the arena

Each frame the game fills a table: one row per enemy in the fight, one column per feature (distance to player, health, speed, minions nearby). The network wants it one way, the debug overlay the other way round (one row per feature, to draw a graph of each). Copying the table for each consumer every frame is wasteful, so we describe the same buffer two ways.

## The careless version: a transposed view read as if it were flat

```cpp
#include <cstdio>
#include <vector>

struct View { const float* data; int rows, cols, s0, s1; };

View transpose(View v) { return {v.data, v.cols, v.rows, v.s1, v.s0}; }   // no copy

int main() {
    // 3 enemies x 4 features: distance, health, speed, minions
    std::vector<float> table = {5, 100, 2, 0,
                                9,  40, 3, 1,
                                2,  75, 1, 4};
    View enemies{table.data(), 3, 4, 4, 1};
    View features = transpose(enemies);                         // 4 features x 3 enemies

    std::printf("health of each enemy (careless): ");
    for (int e = 0; e < features.cols; ++e)
        std::printf("%g ", features.data[1 * features.cols + e]);   // assumes a flat row-major layout
    std::printf("\nhealth of each enemy (strides):  ");
    for (int e = 0; e < features.cols; ++e)
        std::printf("%g ", features.data[1 * features.s0 + e * features.s1]);
    std::printf("\n");
}
```
```text
health of each enemy (careless): 0 9 40 
health of each enemy (strides):  100 40 75 
```

The overlay's health graph showed 0, 9 and 40: a minion count, a distance and one real health value. The view's shape said "4 by 3", but the code computed the offset as if the data were laid out that way. It is not: only the strides know where element (feature 1, enemy e) lives.

## The concept: shape plus strides

A tensor is a flat buffer plus:

- **shape**: the size of each dimension, `[3, 4]` here.
- **strides**: how far to move in the buffer to step one along each dimension. Row-major `[3, 4]` has strides `[4, 1]`.

The offset of `(i, j)` is always `i*s0 + j*s1`. A **transpose** swaps both the shape and the strides (`[4, 3]`, `[1, 4]`) and copies nothing. A **slice** (some columns only) changes the start pointer and shape, keeps the strides. Every reader must use the strides; the only layout it may assume is "contiguous", and only after checking.

## When to use views, and when not

- Use views to give several consumers different shapes of the same data without copying: transposes, slices, a single row.
- Before a hot kernel (matmul, SIMD loops), make the input contiguous with one copy. Strided inner loops cannot vectorize and miss the cache.
- A view does not own the buffer. If the table is rebuilt (a vector that reallocates), every view dangles. PyTorch and our exercise share ownership through a `shared_ptr` for this reason.
- For a fixed small table, a plain struct with named fields is clearer than a tensor.

Sources: [PyTorch: tensor views](https://pytorch.org/docs/stable/tensor_view.html), Edward Z. Yang, [PyTorch internals](http://blog.ezyang.com/2019/05/pytorch-internals/)
