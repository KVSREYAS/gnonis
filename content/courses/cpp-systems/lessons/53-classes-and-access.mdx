## The feature: the player's health

Slime Siege needs a player. The player has health (0 to 100), a position, and a score. Many parts of the game touch health: slimes bite, spikes hurt, potions heal, the HUD draws the health bar, and the game-over screen checks if the player is dead.

That is a lot of code changing one number. The rule the game depends on is simple: **health is always between 0 and 100**. The HUD draws a bar 0 to 100 pixels wide, and game over triggers at exactly 0.

Let's see what happens if we write the player the careless way first.

## The careless version: public fields

```cpp
#include <cstdio>

struct Player {          // everything public
    int hp = 100;
    int max_hp = 100;
};

int main() {
    Player p;
    p.hp += 50;                        // potion code forgot the cap
    std::printf("after potion: %d\n", p.hp);
    p.hp -= 200;                       // big slime bite
    std::printf("after bite:   %d\n", p.hp);
    bool game_over = (p.hp == 0);      // game-over code checks for exactly 0
    std::printf("game over?    %d\n", game_over);
}
```
```text
after potion: 150
after bite:   -50
game over?    0
```

## What went wrong

Two bugs, both caused by the same design:

1. The potion pushed health to 150. The health bar now draws past its frame.
2. The bite took health to -50. The game-over check looks for `hp == 0`, so the player is dead but the game keeps running.

Neither line looks wrong on its own. The potion programmer and the game-over programmer each assumed someone else kept health in range. With public fields, **every line in the game is responsible for the rule**, which means no line is.

## The fix: private data, public methods

Make `hp` private. Now the only way to change it is through member functions, and those functions enforce the rule. The rule lives in one place.

```cpp
#include <cstdio>

class Player {
public:
    void heal(int amount) {
        hp_ += amount;
        if (hp_ > max_hp_) hp_ = max_hp_;
    }
    void take_damage(int amount) {
        hp_ -= amount;
        if (hp_ < 0) hp_ = 0;
    }
    int hp() const { return hp_; }
    bool dead() const { return hp_ == 0; }
private:
    int hp_ = 100;
    int max_hp_ = 100;
};

int main() {
    Player p;
    p.heal(50);
    std::printf("after potion: %d\n", p.hp());
    p.take_damage(200);
    std::printf("after bite:   %d\n", p.hp());
    std::printf("game over?    %d\n", p.dead());
    // p.hp_ = 999;   // error: 'int Player::hp_' is private within this context
}
```
```text
after potion: 100
after bite:   0
game over?    1
```

## The words for what you just did

- **Data member**: a variable inside the class (`hp_`). Each object has its own.
- **Member function** or **method**: a function inside the class (`heal`). It reads and writes the members of the object it was called on.
- **Encapsulation**: hiding the data and exposing only operations.
- **Invariant**: the rule that is always true for a valid object (0 ≤ hp ≤ 100).
- **Getter**: a small `const` method that returns a value (`hp()`), so code can read health without being able to write it.

The trailing underscore in `hp_` is a naming habit for private members, not syntax.

## struct vs class

Only one difference matters: the default access level. Members of a `struct` are public until you say otherwise. Members of a `class` are private until you say otherwise.

Convention in game code: use `struct` for plain bundles with no rules (a `Vec2 { float x, y; }`, a color, a config record). Use `class` when there is a rule to protect (a player's health, an inventory's capacity).

## Access in action

Private members are a compile-time lock, not a runtime one. The compiler refuses any code outside the class that names them. It costs nothing when the game runs.

## When to use it, and when not

Use a class with private data when:

- the data has a rule (health range, inventory capacity, a sorted list)
- several fields must change together (a player's position and its tile index)

Do not wrap everything in getters and setters by reflex. A `Vec2` with `get_x()` and `set_x()` that do nothing but read and write adds noise and protects no rule. If any value of every field is valid, a plain `struct` with public fields is the honest choice.
