## The feature: spawning enemies

Every few seconds the spawner creates a slime at the edge of the map. A slime needs a name (for the debug overlay), health, a speed and an `active` flag (inactive enemies are skipped by the update loop).

The careless way is to create an empty object and then fill in the fields one by one. It works until someone forgets a field.

## The careless version: fill it in later

```cpp
#include <cstdio>
#include <string>
#include <vector>

struct Enemy {
    std::string name;
    int hp = 0;
    float speed = 0;
    bool active = false;
};

int main() {
    std::vector<Enemy> enemies;
    for (int i = 0; i < 3; ++i) {
        Enemy e;
        e.name = "slime";
        e.hp = 30;
        e.speed = 1.5f;        // forgot: e.active = true;
        enemies.push_back(e);
    }
    int moving = 0;
    for (const Enemy& e : enemies)
        if (e.active) ++moving;
    std::printf("spawned %zu, moving %d\n", enemies.size(), moving);
}
```
```text
spawned 3, moving 0
```

## What went wrong

Three slimes exist, but none of them move. The player sees statues. There was a short window where each `Enemy` was half-built, and one missing line left it that way forever.

Every place that creates an enemy has to remember all four fields. The boss spawner, the split-slime code, and the save-file loader would all need the same four lines, and the next field someone adds (say `damage`) needs updating in all of them.

## The fix: a constructor

A **constructor** is a member function with the class's name and no return type. It runs when the object is created, so the object is valid from its first moment. You cannot get an `Enemy` without going through it.

```cpp
#include <cstdio>
#include <string>
#include <utility>
#include <vector>

class Enemy {
public:
    Enemy(std::string name, int hp, float speed)
        : name_(std::move(name)), hp_(hp), speed_(speed), active_(true) {}
    bool active() const { return active_; }
private:
    std::string name_;
    int hp_;
    float speed_;
    bool active_;
};

int main() {
    std::vector<Enemy> enemies;
    for (int i = 0; i < 3; ++i) enemies.push_back(Enemy("slime", 30, 1.5f));
    int moving = 0;
    for (const Enemy& e : enemies)
        if (e.active()) ++moving;
    std::printf("spawned %zu, moving %d\n", enemies.size(), moving);
    // Enemy blank;   // error: no matching function for call to 'Enemy::Enemy()'
}
```
```text
spawned 3, moving 3
```

Once you write a constructor with parameters, the compiler no longer gives you a free default one, so a blank `Enemy` cannot be created by accident.

## The member initializer list

The part after the `:` is the **member initializer list**. It builds each member directly with its starting value. The constructor body `{ }` runs afterwards, when all members already exist.

You could write `hp_ = hp;` in the body instead, but then `hp_` is first created and then overwritten. For a `std::string` that is wasted work. For a `const` member or a reference member it is impossible: they can only be set in the list.

One trap: members are initialized in the order they are **declared in the class**, not the order you write them in the list. g++ warns about it with `-Wall`:

```cpp
#include <cstdio>

class Bat {
public:
    explicit Bat(int level) : speed_(base_ * 2), base_(level) {}
    int speed() const { return speed_; }
private:
    int speed_;   // declared first, so built first, from base_ that is not set yet
    int base_;
};

int main() {
    Bat b(3);
    std::printf("bat speed: %d (expected 6)\n", b.speed());
}
```
```text
$ g++ -std=c++20 -O2 -Wall game.cpp
game.cpp:5: warning: member 'Bat::base_' is used uninitialized [-Wuninitialized]
game.cpp:5: warning: '*this.Bat::base_' is used uninitialized [-Wuninitialized]
game.cpp:5: warning: 'b.Bat::base_' is used uninitialized [-Wuninitialized]
$ ./game
bat speed: 0 (expected 6)
```

The speed came out as 0 in this run, but it could be any value: reading an uninitialized `int` is undefined behaviour. Fix: declare `base_` before `speed_`, or compute from the parameter: `speed_(level * 2)`.

## explicit

A constructor that takes one argument can also act as a silent conversion. Without `explicit`, `Bat b = 3;` compiles, and so does passing a plain `3` to a function that expects a `Bat`. The line `spawn(3)` would quietly create a level-3 bat when someone meant "spawn 3 enemies".

Mark one-argument constructors `explicit` unless the conversion is really what you want. `explicit Bat(int level)` turns `spawn(3)` into a compile error, and you write `spawn(Bat(3))` when you mean it.

## Destructors: cleanup when an enemy dies

A **destructor** is `~ClassName()`. It runs automatically when the object's lifetime ends: at the end of its scope for a local, or when the vector holding it is destroyed. The game uses it to update the live-enemy count, so the "wave cleared" check is never wrong.

```cpp
#include <cstdio>

int g_alive = 0;

class Enemy {
public:
    explicit Enemy(char id) : id_(id) { ++g_alive; std::printf("+%c ", id_); }
    ~Enemy() { --g_alive; std::printf("-%c ", id_); }
private:
    char id_;
};

int main() {
    Enemy a('A');
    {
        Enemy b('B');
        Enemy c('C');
        std::printf("[alive %d] ", g_alive);
    }                                   // C dies, then B
    std::printf("[alive %d] ", g_alive);
}                                       // A dies
```
```text
+A +B +C [alive 3] -C -B [alive 1] -A 
```

Destruction runs in **reverse order** of construction. Later objects may depend on earlier ones, so they are torn down first. The lifetime module builds on this rule.

## this

Inside a member function, `this` is a pointer to the object the function was called on. `hp_` and `this->hp_` mean the same thing. You need `this` explicitly in two cases:

- a parameter has the same name as a member: `this->speed = speed;`
- the object must hand itself to someone, for example `grid.register_entity(this);` or `return *this;` so calls can be chained

## const methods: the HUD must not hurt the player

The HUD only reads the player. Here is a real-looking bug: one `=` instead of `==`.

```cpp
#include <cstdio>

class Player {
public:
    int hp() const { return hp_; }
    bool should_flash() { return hp_ = 0; }   // meant ==
private:
    int hp_ = 80;
};

int main() {
    Player p;
    std::printf("hp before draw: %d\n", p.hp());
    if (p.should_flash()) std::printf("flash!\n");
    std::printf("hp after draw:  %d\n", p.hp());
}
```
```text
hp before draw: 80
hp after draw:  0
```

Drawing the HUD killed the player. Marking `should_flash` as `const` (it is meant to only read) turns this into a compile error:

```cpp
class Player {
public:
    bool should_flash() const { return hp_ = 0; }
private:
    int hp_ = 80;
};
int main() { Player p; return p.should_flash(); }
```
```text
game.cpp:3: error: assignment of member 'Player::hp_' in read-only object
```

Mark every method that only reads as `const`. Then a `const Player&` handed to the HUD can call only those.

## When to use it, and when not

- Give a class a constructor whenever some combination of fields would be invalid (an active enemy with 0 hp, a texture with no pixels).
- Use the initializer list for every member, in declaration order.
- Write a destructor only when the object must do something at the end (update a counter, release a resource). For plain data, the compiler-generated one is right.
- Plain data like `Vec2` does not need a constructor. Default member initializers (`float x = 0;`) are enough.
