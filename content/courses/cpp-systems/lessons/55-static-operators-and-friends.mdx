## The feature: entity ids

Every entity in Slime Siege needs a unique id. The save file refers to entities by id ("bat 17 is chasing the player"), and the debug overlay prints it. Ids must never repeat during a run.

The first attempt puts the counter in the class as a normal member.

## The careless version: a counter per object

```cpp
#include <cstdio>

class Entity {
public:
    Entity() : id_(next_id_++) {}
    int id() const { return id_; }
private:
    int next_id_ = 1;   // every Entity gets its OWN counter
    int id_;
};

int main() {
    Entity a, b, c;
    std::printf("ids: %d %d %d\n", a.id(), b.id(), c.id());
}
```
```text
ids: 1 1 1
```

## What went wrong

Every entity got id 1. `next_id_` is a normal data member, so each object has its own copy. Each new entity starts its own counter at 1, takes 1 as its id, and bumps only its own copy to 2. The next entity never sees that 2.

The save file now has three entities called "1". Loading it would attach every bat's path to the same entity.

The counter has to be one value **shared by the whole class**, not one per object.

## The fix: a static member

A `static` data member belongs to the class itself. There is exactly one copy no matter how many objects exist (even zero). Inside the class it is declared; `inline static` (C++17) lets you give it a value right there.

```cpp
#include <cstdio>

class Entity {
public:
    Entity() : id_(next_id_++) {}
    int id() const { return id_; }
    static int spawned() { return next_id_ - 1; }   // static function: no this
private:
    inline static int next_id_ = 1;                 // one copy for the class
    int id_;
};

int main() {
    Entity a, b, c;
    std::printf("ids: %d %d %d, spawned %d\n", a.id(), b.id(), c.id(), Entity::spawned());
}
```
```text
ids: 1 2 3, spawned 3
```

A **static member function** has no `this`, so it can use only static members. You call it on the class: `Entity::spawned()`.

## Encapsulation: setters that keep rules

The settings menu lets the player set the music volume. The audio code needs 0 to 100. A setter is the right tool here, because there is a rule to keep:

```cpp
#include <cstdio>

class AudioSettings {
public:
    void set_volume(int v) { volume_ = v < 0 ? 0 : (v > 100 ? 100 : v); }
    int volume() const { return volume_; }
private:
    int volume_ = 70;
};

int main() {
    AudioSettings s;
    s.set_volume(250);                 // slider bug sends 250
    std::printf("%d\n", s.volume());
}
```
```text
100
```

## The feature: Vec2 maths

Movement is maths: `pos = pos + vel * dt`. Without operators the same line reads `pos = add(pos, scale(vel, dt))`, and a two-line physics step becomes unreadable. **Operator overloading** means `a + b` on your type calls a function named `operator+`.

The rule that matters: `+` must not change its operands. Here is what happens when it does.

## The careless version: + that changes the left side

```cpp
#include <cstdio>

struct Vec2 {
    float x, y;
    Vec2 operator+(Vec2 o) { x += o.x; y += o.y; return *this; }  // changes *this!
};

int main() {
    Vec2 pos{0, 0}, vel{1, 0};
    Vec2 predicted = pos + vel;        // where will the player be next frame?
    std::printf("predicted x=%.0f, actual x=%.0f\n", predicted.x, pos.x);
}
```
```text
predicted x=1, actual x=1
```

Asking "where will the player be?" moved the player. The AI code calls this prediction every frame, so the player runs at double speed whenever an enemy is watching.

## The fix: const operators that return a new value

`operator+` is a `const` member that returns a fresh `Vec2`. If you want "add into this one", that is a different operator, `+=`, which returns a reference to `*this`.

```cpp
#include <cstdio>

struct Vec2 {
    float x = 0, y = 0;
    Vec2 operator+(Vec2 o) const { return {x + o.x, y + o.y}; }
    Vec2 operator*(float s) const { return {x * s, y * s}; }
    Vec2& operator+=(Vec2 o) { x += o.x; y += o.y; return *this; }
    bool operator==(const Vec2&) const = default;
};

int main() {
    Vec2 pos{0, 0}, vel{4, 2};
    Vec2 predicted = pos + vel * 0.5f;     // pos unchanged
    pos += vel * 0.25f;                    // the real move
    std::printf("predicted (%.1f, %.1f), pos (%.1f, %.1f), same=%d\n",
                predicted.x, predicted.y, pos.x, pos.y, predicted == pos);
}
```
```text
predicted (2.0, 1.0), pos (1.0, 0.5), same=0
```

`= default` on `operator==` (C++20) asks the compiler to compare every member in order.

## Friends: printing for the debug overlay

The debug overlay prints entities with `std::cout << enemy`. That calls `operator<<(std::ostream&, const Enemy&)`. It cannot be a member of `Enemy`, because the left operand is the stream. But it needs the private fields.

A **friend** declaration inside the class gives one outside function access to private members:

```cpp
#include <iostream>
#include <string>
#include <utility>

class Enemy {
public:
    Enemy(std::string name, int hp) : name_(std::move(name)), hp_(hp) {}
    friend std::ostream& operator<<(std::ostream& os, const Enemy& e) {
        return os << e.name_ << "[" << e.hp_ << " hp]";
    }
private:
    std::string name_;
    int hp_;
};

int main() {
    Enemy a("slime", 30), b("bat", 12);
    std::cout << a << " " << b << "\n";
}
```
```text
slime[30 hp] bat[12 hp]
```

Returning the stream is what lets `<<` chain.

## When to use it, and when not

- **static**: for things that belong to the type, not one object: id counters, a shared config, a factory function. Avoid static state you must reset between tests or levels; it is a hidden global.
- **Operators**: only where the meaning is obvious. `Vec2 + Vec2`, `Color * float`, `Tile == Tile`: yes. `Enemy + Enemy`: no, nobody knows what that means.
- **friend**: for operators that need private access, mainly `<<`. If many unrelated functions need to be friends, the class's public interface is missing something.
