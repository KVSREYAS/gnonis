## The feature: many kinds of enemy

Slime Siege has slimes (hop toward the player), bats (fly fast, ignore walls) and turrets (stand still and shoot). Next month someone adds ghosts. The game loop should be one line: "update every enemy". Adding ghosts should not mean editing the loop.

## The careless version: a type tag and a switch

```cpp
#include <cstdio>
#include <vector>

enum class Kind { Slime, Bat, Turret, Ghost };   // Ghost added last week
struct Enemy { Kind kind; float x = 0; };

void update(Enemy& e) {
    switch (e.kind) {
        case Kind::Slime:  e.x += 1; break;
        case Kind::Bat:    e.x += 3; break;
        case Kind::Turret: break;
        // whoever added Ghost forgot this switch (one of twelve in the game)
    }
}

int main() {
    std::vector<Enemy> wave = {{Kind::Slime}, {Kind::Bat}, {Kind::Ghost}};
    for (auto& e : wave) update(e);
    for (auto& e : wave) std::printf("%.0f ", e.x);
    std::printf("\n");
}
```
```text
1 3 0 
```

## What went wrong

The ghost never moves. Every function that cares about the enemy type (update, draw, attack, sound, save) has its own `switch`, and adding a type means finding and editing all of them. Miss one and the bug is silent. (g++ `-Wall` warns about an unhandled enum in a switch, but only if there is no `default:`, and real switches usually have one.)

What we want is for the behaviour to live **with the type**: the ghost's movement code is written in the ghost, and the loop just asks "whatever you are, update yourself".

## The fix: a base class and virtual functions

**Inheritance**: `class Slime : public Enemy` makes `Slime` a kind of `Enemy`. It contains all of Enemy's members, and a `Slime&` can be used anywhere an `Enemy&` is expected.

A **virtual** function in the base can be **overridden** in each derived class. When you call it through a base pointer or reference, the program looks at the real type of the object at runtime and calls that type's version.

```cpp
#include <cstdio>
#include <memory>
#include <vector>

class Enemy {
public:
    virtual ~Enemy() = default;
    virtual void update() = 0;               // every enemy must define it
    float x() const { return x_; }
protected:
    float x_ = 0;                            // derived classes may touch it
};
class Slime : public Enemy  { public: void update() override { x_ += 1; } };
class Bat : public Enemy    { public: void update() override { x_ += 3; } };
class Ghost : public Enemy  { public: void update() override { x_ += 2; } };

int main() {
    std::vector<std::unique_ptr<Enemy>> wave;
    wave.push_back(std::make_unique<Slime>());
    wave.push_back(std::make_unique<Bat>());
    wave.push_back(std::make_unique<Ghost>());
    for (auto& e : wave) e->update();        // never changes when types are added
    for (auto& e : wave) std::printf("%.0f ", e->x());
    std::printf("\n");
}
```
```text
1 3 2 
```

## The keywords

- `virtual`: this function can be overridden and is dispatched at runtime.
- `= 0`: **pure virtual**. The base has no version, and the class becomes **abstract**: you cannot create a plain `Enemy`, only concrete kinds.
- `override`: on the derived function, asks the compiler to check that it really overrides a base virtual. A typo or a missing `const` becomes a compile error instead of a silent new function.
- `protected`: like private, but derived classes can use it. Here `x_` is shared with every enemy kind, and still hidden from the rest of the game.
- `virtual ~Enemy()`: explained two cards below; required.

(`std::unique_ptr<Enemy>` holds one heap enemy and deletes it automatically. The ownership module covers it fully; here it just stands in for "pointer that cleans up".)

## Bug 1: forgetting virtual (hiding)

Without `virtual`, a function with the same name in the derived class only **hides** the base one. The call is picked from the type of the pointer or reference at compile time, not from the object.

```cpp
#include <cstdio>

struct Enemy { const char* roar() const { return "(silence)"; } };
struct Dragon : Enemy { const char* roar() const { return "ROAR"; } };

void play_sound(const Enemy& e) { std::printf("%s\n", e.roar()); }

int main() {
    Dragon boss;
    std::printf("direct: %s\n", boss.roar());
    play_sound(boss);                    // through Enemy&
}
```
```text
direct: ROAR
(silence)
```

The boss fight is silent, because the sound system only sees `Enemy&`.

## Bug 2: slicing

The spawner stores enemies **by value** in a `std::vector<Enemy>` (here `Enemy` is not abstract, so this compiles):

```cpp
#include <cstdio>
#include <vector>

struct Enemy {
    virtual ~Enemy() = default;
    virtual const char* name() const { return "generic enemy"; }
    int hp = 10;
};
struct Bat : Enemy {
    const char* name() const override { return "bat"; }
    float wing_speed = 9.5f;
};

int main() {
    std::vector<Enemy> wave;
    wave.push_back(Bat{});               // copies only the Enemy part
    std::printf("%s\n", wave[0].name());
}
```
```text
generic enemy
```

`push_back` copies the `Bat` into a slot that is exactly `sizeof(Enemy)` bytes. Only the `Enemy` part fits, so `wing_speed` and the bat's identity are cut off. This is **object slicing**. The fix: store pointers (`std::vector<std::unique_ptr<Enemy>>`), so each object keeps its real type. Making the base abstract (`= 0`) prevents the mistake entirely, because an abstract `Enemy` cannot be copied into a value.

## Bug 3: the missing virtual destructor

```cpp
#include <string>

struct Enemy { ~Enemy() {} };                       // not virtual
struct Boss : Enemy { std::string title = "The Slime King, Devourer of Tiles"; };

int main() {
    Enemy* e = new Boss;
    delete e;                                       // runs only ~Enemy
}
```
```text
==1==ERROR: AddressSanitizer: new-delete-type-mismatch on 0x503000000040 in thread T0:
  object passed to delete has wrong type:
SUMMARY: AddressSanitizer: new-delete-type-mismatch ../../../../src/libsanitizer/asan/asan_new_delete.cpp:164 in operator delete(void*, unsigned long)
```

`delete e` looks at the static type `Enemy`. Without a virtual destructor it runs only `~Enemy` and frees the wrong size; `~Boss` never runs, so the string leaks. The language calls this undefined behaviour. Rule: **a class meant to be used through base pointers gets `virtual ~Base() = default;`**.

## When to use it, and when not

Use virtual functions when:

- you have a family of types with the same operations but different behaviour, and the set of types grows (enemy kinds, UI widgets, weapons)
- the number of objects is in the hundreds or thousands per frame

Avoid them when:

- the set of types is small and fixed: a `std::variant` (later module) is often simpler
- you process 100,000 identical things per frame (particles): the vptr adds 8 bytes per object and every call is an indirect jump the compiler cannot inline. The data-oriented design module stores those in plain arrays instead
- you only want to share code, not substitute types: a helper function or a member object is simpler than inheritance
