## Milestone 2: engine resources

**What we build this module:** the parts of the engine that hold things the operating system or the GPU lends us: the game window, textures in GPU memory, open level files, audio channels. Then loading a level, which grabs dozens of these at once and can fail halfway.

**Why the game needs it:** every one of those must be given back exactly once. Forget one and the game slowly runs out of GPU memory over a long session. Give one back twice and it crashes. Loading a level can stop at any point (a missing file, a corrupt tile), and everything grabbed so far must still be released. Doing that by hand on every path does not scale. C++ has one rule that makes it automatic: destructors always run.

## Resources, leaks and dangling

A **resource** is anything that must be given back when you are done: heap memory, a texture id, an open file, a locked mutex, a network socket, an audio channel.

- Never giving it back is a **leak**. The game keeps working until the resource runs out.
- Using an object after its lifetime ended is a **dangling** reference or pointer. That is undefined behaviour: it may work, print garbage, or crash.
- Giving it back twice (double free) is also undefined behaviour, and usually a crash.

The **lifetime** of an object is the period during which it exists and is safe to use. This module is about making lifetimes and resources line up exactly.

## Scope, construction, destruction

A **scope** is a block between `{` and `}`. A local variable declared in it lives on the stack.

1. When execution reaches the declaration, the **constructor** runs.
2. When execution leaves the scope, the **destructor** runs. This happens on every way out: reaching `}`, `return`, `break`, `continue`, or an exception passing through.
3. Locals in one scope are destroyed in **reverse order** of construction.

```cpp
#include <cstdio>

struct Asset {
    const char* name;
    explicit Asset(const char* n) : name(n) { std::printf("load %s\n", name); }
    ~Asset() { std::printf("free %s\n", name); }
};

bool load_level(bool music_missing) {
    Asset tiles("tiles.png");
    Asset hero("hero.png");
    if (music_missing) return false;     // early exit: both still freed
    Asset music("level1.ogg");
    return true;
}

int main() { load_level(true); }
```
```text
load tiles.png
load hero.png
free hero.png
free tiles.png
```

You never call a destructor by hand for a local. The compiler inserts the calls at every exit.

## RAII step by step

**RAII** stands for Resource Acquisition Is Initialization. It is a rule for writing classes:

1. The constructor acquires the resource (loads the texture, opens the file).
2. The destructor releases it.
3. Copying and moving are either written correctly or forbidden, so exactly one object owns each resource.

Then using the resource is just declaring a variable. Cleanup can no longer be skipped, because destructors run on every exit. The standard library already works this way: `std::vector` frees its memory, `std::lock_guard` unlocks, `std::unique_ptr` deletes, `std::ifstream` closes the file.

## Exceptions and stack unwinding

An **exception** is a way to report an error that the current function cannot handle. `throw std::runtime_error("missing tile")` stops the function and jumps to the nearest matching `catch` block up the call chain.

On the way, every fully built local in every function it leaves is destroyed, in reverse order. That is **stack unwinding**, and it is why RAII works with errors: a level loader that throws halfway still releases everything it loaded.

```cpp
#include <cstdio>
#include <stdexcept>

struct Asset {
    const char* name;
    explicit Asset(const char* n) : name(n) { std::printf("load %s\n", name); }
    ~Asset() { std::printf("free %s\n", name); }
};

void load_level() {
    Asset tiles("tiles.png");
    Asset hero("hero.png");
    throw std::runtime_error("level1.map: bad tile on row 7");
}

int main() {
    try { load_level(); }
    catch (const std::exception& e) { std::printf("error: %s\n", e.what()); }
}
```
```text
load tiles.png
load hero.png
free hero.png
free tiles.png
error: level1.map: bad tile on row 7
```

## The special member functions

A class has five **special member functions** that control copying, moving and destruction:

1. **Destructor** `~T()`: runs when the lifetime ends. Releases what the object owns.
2. **Copy constructor** `T(const T& other)`: creates a **new** object as an independent duplicate. Runs for `T b = a;` and when passing by value.
3. **Copy assignment** `T& operator=(const T& other)`: makes an **existing** object equal to `other`. It must first release what it already owns. Runs for `b = a;`.
4. **Move constructor** `T(T&& other)`: creates a new object by taking `other`'s resources, leaving `other` empty but valid.
5. **Move assignment** `T& operator=(T&& other)`: releases what it owns, then takes `other`'s resources.

A constructor starts from nothing; an assignment must clean up an old value first. (The move module explains `T&&` and moving in depth.)

## When the compiler writes them

If you do not declare a special member, the compiler may write one that works member by member: it copies, moves or destroys each member in order.

- **Destructor**: always generated if you do not write one.
- **Copy operations**: generated unless you declared a move operation, or a member cannot be copied (a `std::unique_ptr` member). Then they are **deleted**.
- **Move operations**: generated **only if** you declared none of: destructor, copy constructor, copy assignment, the other move.

The last rule surprises people: writing only a destructor silently removes the moves, and moves fall back to copies.

`= delete` means the function exists but any use is a compile error. `= default` asks for the generated version explicitly.

## Rule of zero, three and five

You write special members yourself only when a class **directly owns a raw resource**, such as `unsigned char* pixels_` or a texture id. Then the generated versions are wrong in a predictable way:

- generated copy: copies the pointer, so two objects own one buffer and both free it (double free)
- generated copy assignment: also leaks the target's old buffer
- generated moves: suppressed by your destructor, so every move becomes a deep copy

That gives three rules:

- **Rule of three**: if you need a destructor, copy constructor or copy assignment, you need all three.
- **Rule of five**: the same, plus the two moves.
- **Rule of zero**: better still, put the raw resource inside one small RAII class (or use `std::vector`, `std::unique_ptr`), and every other class writes none of the five.

## Worked example: all five for a pixel buffer

```cpp
#include <algorithm>
#include <cstddef>
#include <utility>

class Pixels {                       // owns w*h RGBA bytes
    std::size_t n_ = 0;
    unsigned char* data_ = nullptr;
public:
    explicit Pixels(std::size_t n) : n_(n), data_(new unsigned char[n]{}) {}
    ~Pixels() { delete[] data_; }                                  // 1
    Pixels(const Pixels& o) : n_(o.n_), data_(new unsigned char[o.n_]) {
        std::copy(o.data_, o.data_ + n_, data_);                   // 2
    }
    Pixels& operator=(const Pixels& o) {                           // 3
        if (this != &o) {
            unsigned char* fresh = new unsigned char[o.n_];        // allocate first
            std::copy(o.data_, o.data_ + o.n_, fresh);
            delete[] data_;                                        // then free old
            data_ = fresh; n_ = o.n_;
        }
        return *this;
    }
    Pixels(Pixels&& o) noexcept                                    // 4
        : n_(std::exchange(o.n_, 0)), data_(std::exchange(o.data_, nullptr)) {}
    Pixels& operator=(Pixels&& o) noexcept {                       // 5
        if (this != &o) {
            delete[] data_;
            n_ = std::exchange(o.n_, 0);
            data_ = std::exchange(o.data_, nullptr);
        }
        return *this;
    }
    std::size_t size() const { return n_; }
    unsigned char* data() const { return data_; }
};

#include <cstdio>
int main() {
    Pixels hero(64 * 64 * 4);
    Pixels tinted = hero;                 // copy: its own buffer
    Pixels moved = std::move(hero);       // move: takes the buffer
    std::printf("tinted %zu bytes, own buffer: %d\n", tinted.size(), tinted.data() != moved.data());
    std::printf("moved %zu bytes, hero left with %zu\n", moved.size(), hero.size());
}
```
```text
tinted 16384 bytes, own buffer: 1
moved 16384 bytes, hero left with 0
```

## Reading the worked example

- Copy assignment allocates **before** freeing, so if `new` throws, the object is unchanged.
- `std::exchange(x, v)` sets `x` to `v` and returns the old value, which makes moves one-liners.
- The moves are `noexcept`, so `std::vector<Pixels>` moves them instead of copying when it grows (move module).
- The `this != &o` checks stop `a = a` from freeing its own data.

**Copy-and-swap** writes both assignments as one function taking its parameter by value: `Pixels& operator=(Pixels other) noexcept { swap(*this, other); return *this; }`. The argument picks copy or move to build `other`; the old data dies with `other`.

The rule-of-zero version of the same class is one line of data: `std::vector<unsigned char> data_;`. All five are generated and correct. Prefer it. Write the five only inside the one class whose job is owning the raw resource.

## Dangling: using an object after it ends

A **reference** or **pointer** does not keep its target alive. If the target dies first, it **dangles**.

```cpp
const std::string& enemy_label() {
    std::string s = "Slime King";
    return s;              // s is destroyed here
}                          // caller gets a reference to nothing
```

Common sources in a game:

- returning a reference or pointer to a local
- a `std::string_view` built from a temporary `std::string`
- a pointer or reference to an element of a `std::vector<Enemy>` that later grows and moves its elements
- a pointer to an enemy that has since been deleted

A **temporary** (an unnamed object such as `std::string("a") + "b"`) normally dies at the end of the full expression, the `;`. Binding it directly to a `const&` local extends its life to that local's scope. That extension does not pass through function returns.
