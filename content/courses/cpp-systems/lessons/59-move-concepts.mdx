## Milestone 3: loading levels fast

**What we build this module:** level loading and streaming. A level is a big object: a 512 by 512 tile grid (256 KB), a list of chunks, spawn points, a name. The loader builds a level, hands it to the world, and the old level is thrown away. While the player explores, new chunks are appended to a growing `std::vector<Chunk>`. Enemies are created with `world.spawn<Bat>(args...)`.

**Why the game needs it:** every one of those steps can copy a quarter of a megabyte or more if written carelessly: returning the level from the loader, giving it to the world, every time the chunk vector grows. Copies happen in the middle of gameplay and show up as frame-time spikes. Moves turn each of those into a few pointer writes.

## Why moving exists

Copying a `std::vector<unsigned char>` of 262,144 tiles allocates a new block and copies 256 KB. Often the source is about to be destroyed anyway: a local level returned from the loader, or the old level after the world switches. Copying it is wasted work.

A **move** takes the source's internal pointer and size, gives them to the destination, and leaves the source empty but valid. For a vector that is three pointer-sized writes instead of a full copy.

```cpp
#include <cstdio>
#include <utility>
#include <vector>

int main() {
    std::vector<unsigned char> loaded(512 * 512, 1);   // the loader's tiles
    const unsigned char* buffer = loaded.data();

    std::vector<unsigned char> copied = loaded;            // new buffer, 256 KB copied
    std::vector<unsigned char> moved = std::move(loaded);  // takes the buffer

    std::printf("copy reused the buffer: %d\n", copied.data() == buffer);
    std::printf("move reused the buffer: %d, source size now %zu\n", moved.data() == buffer, loaded.size());
}
```
```text
copy reused the buffer: 0
move reused the buffer: 1, source size now 0
```

To make this safe, the language needs a way to tell "this object is still needed" from "this object is about to go away". That is what **value categories** are for.

## lvalues and rvalues

Every expression has a **value category**. The two you need:

- **lvalue**: refers to an object with an identity you can name again, such as a variable `level`, `chunks[3]`, or `*p`. You can take its address.
- **rvalue**: a temporary or an object marked as expiring, such as `42`, `a + b`, `load_level("cave")`, or `std::move(level)`.

References bind according to category:

```cpp
Level  lvl;
Level&       r1 = lvl;            // lvalue ref: binds to lvalues
Level&&      r2 = load_level();   // rvalue ref: binds to rvalues
const Level& r3 = load_level();   // const lvalue ref: binds to both
```

Overload resolution uses this. When a class has both `T(const T&)` and `T(T&&)`, an rvalue argument picks the `T&&` version: the move constructor.

## What a move constructor does

```cpp
class TileGrid {
    unsigned char* data_; std::size_t n_;
public:
    TileGrid(TileGrid&& o) noexcept : data_(o.data_), n_(o.n_) {
        o.data_ = nullptr;   // source gives up ownership
        o.n_ = 0;
    }
    ~TileGrid() { delete[] data_; }
};
```

Step by step:

1. Copy the source's pointer and size into the new object.
2. Set the source's pointer to `nullptr`, so its destructor frees nothing.
3. No allocation, no tile copies.

After a move, the source is in a **valid but unspecified state**. You may destroy it or assign a new value to it. Do not read its contents and expect anything particular.

`std::move(x)` only casts `x` to `T&&`. The constructor or assignment that receives the cast value does the moving.

## Why noexcept matters

When the chunk vector runs out of capacity, it allocates a bigger block and transfers the old chunks into it.

If it moved chunks and the fifth move threw an exception, the first four old chunks would already be empty, and the vector could not restore its old state. To keep its **strong exception guarantee**, it uses `std::move_if_noexcept`:

- move constructor marked `noexcept`: chunks are moved (fast)
- not marked: chunks are copied (slow, but recoverable)

So forgetting `noexcept` on a move constructor quietly turns every growth step into a full copy of every chunk. Defaulted move constructors (`= default`) are `noexcept` automatically when all members' moves are.

## prvalue, xvalue and copy elision

C++ splits rvalues further:

- **prvalue** (pure rvalue): a value with no object yet, such as `42` or `load_level("cave")`.
- **xvalue** (expiring value): an existing object marked as movable, such as `std::move(level)`.
- **glvalue**: lvalue or xvalue, anything with an identity.

**Copy elision** means the compiler builds an object directly in its final place, so no copy or move runs at all. Since C++17 it is **guaranteed** when you initialize from a prvalue of the same type: `Level l = load_level("cave");` builds the level straight into `l`.

**NRVO** (named return value optimization) is the same for a named local, `Level lvl; ... return lvl;`. It is allowed but not guaranteed. If it does not happen, the return uses a move automatically. So never write `return std::move(lvl);`: it blocks NRVO. The noexcept lesson measures this.

## Forwarding references and std::forward

In a template, `T&&` where `T` is deduced is a **forwarding reference**. It binds to both lvalues and rvalues, and `T` records which one it got:

- passed an lvalue `std::string`: `T` is `std::string&`
- passed an rvalue `std::string`: `T` is `std::string`

Inside the function the parameter has a name, so it is an lvalue. `std::forward<T>(arg)` casts it back to an rvalue only if the caller passed an rvalue.

```cpp
template <class T, class... Args>
T& spawn(Args&&... args) {
    return entities.emplace_back(std::forward<Args>(args)...);  // keeps each argument's category
}
```

This is how `emplace_back` and `std::make_unique` pass arguments through without extra copies. (`class... Args` is a **variadic template**: any number of types. The templates module explains it.)

## Reference collapsing

`std::forward` works because of **reference collapsing**. When templates produce a reference to a reference, the compiler reduces it:

| written | becomes |
| --- | --- |
| `T& &` | `T&` |
| `T& &&` | `T&` |
| `T&& &` | `T&` |
| `T&& &&` | `T&&` |

Any `&` wins. So with `template <class T> void f(T&& x)`:

- call with an lvalue `int`: `T = int&`, parameter type `int& &&`, collapses to `int&`
- call with an rvalue `int`: `T = int`, parameter type `int&&`

`std::forward<T>(x)` is essentially `static_cast<T&&>(x)`, which by the same table gives `int&` in the first case and `int&&` in the second.
