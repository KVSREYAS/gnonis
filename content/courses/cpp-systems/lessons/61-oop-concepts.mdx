This whole course builds one program: **Slime Siege**, a small 2D top-down game written in C++. ## Milestone 1: entities

**What we build this module:** the things that live in the game world. A `Player` with health, a position and a score. Enemies (`Slime`, `Bat`) that each move and attack in their own way. A `Vec2` type for positions and velocities.

**Why the game needs it:** a game has hundreds of objects that each carry data (position, health) and behaviour (move, take damage). Keeping the data and the functions that change it together in one type stops bugs like "health went to -40" or "the bat moved like a slime". Classes are the C++ tool for that.

This module is the one place in the course that starts from basic syntax. Later modules assume you know it.

## Class, object, member

A **class** is a type you define. It lists **data members** (the variables each object holds) and **member functions** (functions that work on one object).

An **object** is one value of that class, with its own copy of every data member. Two slimes are two objects of class `Slime`: same code, separate health.

```cpp
#include <cstdio>

class Slime {
public:
    void take_hit(int dmg) { hp_ -= dmg; }
    int hp() const { return hp_; }
private:
    int hp_ = 30;   // default member initializer: every new slime starts at 30
};

int main() {
    Slime a, b;
    a.take_hit(10);
    a.take_hit(5);
    b.take_hit(1);
    std::printf("a=%d b=%d\n", a.hp(), b.hp());
}
```
```text
a=15 b=29
```

Inside a member function, `hp_` means "this object's `hp_`". The hidden pointer `this` holds the address of the object the function was called on: `a.take_hit(10)` runs `take_hit` with `this == &a`.

`struct` and `class` are the same thing except for one detail: members of a `struct` are public by default, members of a `class` are private by default.

## Access control and invariants

**Access specifiers** decide which code may use a member:

- `public`: any code
- `private`: only the class's own member functions (and friends)
- `protected`: the class and classes derived from it

The point of `private` is an **invariant**: a rule that is always true for a valid object. For the player, "hp is between 0 and max_hp". If `hp` were public, any line in a 50,000-line game could write `player.hp -= 999` and the rule is gone. With `hp` private, every change goes through `take_damage`, which clamps it.

```cpp
#include <cstdio>

class Player {
public:
    void take_damage(int d) {
        hp_ -= d;
        if (hp_ < 0) hp_ = 0;          // the invariant lives in one place
    }
    bool alive() const { return hp_ > 0; }
    int hp() const { return hp_; }
private:
    int hp_ = 100;
};

int main() {
    Player p;
    p.take_damage(70);
    p.take_damage(70);                 // overkill
    std::printf("hp=%d alive=%d\n", p.hp(), p.alive());
    // p.hp_ = -40;                    // compile error: hp_ is private
}
```
```text
hp=0 alive=0
```

A member function marked `const` after its parameter list promises not to change the object. You can call only `const` functions on a `const` object, so a function that receives `const Player&` can read the player but not hurt it.

## Constructors and destructors

A **constructor** has the class name and no return type. It runs when an object is created and makes it valid. A **destructor** is `~Name()` and runs when the object is destroyed.

Order of events in a constructor:

1. Members are initialized in the order they are **declared** in the class, using the **member initializer list** (after the `:`).
2. Then the constructor body runs.

```cpp
#include <cstdio>
#include <string>
#include <utility>

class Enemy {
public:
    Enemy(std::string name, int hp) : name_(std::move(name)), hp_(hp) {
        if (hp_ <= 0) hp_ = 1;        // body runs after the members exist
        std::printf("spawn %s (%d hp)\n", name_.c_str(), hp_);
    }
    ~Enemy() { std::printf("despawn %s\n", name_.c_str()); }
private:
    std::string name_;
    int hp_;
};

int main() {
    Enemy a("slime", 30);
    {
        Enemy b("bat", 0);            // fixed up to 1 hp
    }                                  // b is destroyed here
    std::printf("wave over\n");
}                                      // a is destroyed here
```
```text
spawn slime (30 hp)
spawn bat (1 hp)
despawn bat
wave over
despawn slime
```

Prefer the initializer list: members that are `const` or references can only be set there. Mark one-argument constructors `explicit` so the compiler does not use them for silent conversions (an `int` quietly turning into an `Enemy`).

## static members, operators, friends

A **static** data member belongs to the class, not to each object: one copy shared by all of them. The game uses one to count live enemies. A static member function has no `this`, so it can only touch static members.

**Operator overloading** lets `a + b` call a function you write. Positions are the classic case: `pos + vel * dt` reads like the maths it is.

```cpp
#include <cstdio>

struct Vec2 {
    float x = 0, y = 0;
    Vec2 operator+(Vec2 o) const { return {x + o.x, y + o.y}; }
    Vec2 operator*(float s) const { return {x * s, y * s}; }
    bool operator==(const Vec2&) const = default;   // compares x and y
};

int main() {
    Vec2 pos{10, 5}, vel{2, -1};
    float dt = 0.5f;                  // half a second
    pos = pos + vel * dt;
    std::printf("(%.1f, %.1f) %d\n", pos.x, pos.y, pos == Vec2{11, 4.5f});
}
```
```text
(11.0, 4.5) 1
```

A **friend** function is declared inside the class with `friend`. It is not a member, but it may read private members. You need one for `operator<<`, because its left operand is `std::ostream`, not your class.

## Pointers, references and the heap (short version)

Two more pieces of basic syntax appear in every later module, and this module teaches each in its own lesson:

- A **pointer** `Enemy* p` holds the address of an object. `p->hp()` calls through it. It can be `nullptr` and can be changed to point elsewhere.
- A **reference** `Enemy& r` is another name for an existing object. It cannot be null and cannot be re-seated.
- A local variable lives on the **stack** and dies at the end of its scope. `new Enemy(...)` creates an object on the **heap**; it lives until someone calls `delete`. Forgetting `delete` leaks; calling it twice crashes.

`const` can be applied to all of them: `const Enemy&` means "read only".

## Inheritance and virtual functions

**Inheritance** builds a **derived** class from a **base** class: `class Slime : public Enemy` gets everything `Enemy` has, plus its own members.

A **virtual** function can be replaced (**overridden**) in a derived class. When you call it through a base pointer or reference, the program checks the object's real type at runtime and calls that type's version. This is **dynamic dispatch**. It lets the game keep every enemy in one list and call `update()` on each, while slimes hop and bats swoop.

```cpp
#include <cstdio>
#include <memory>
#include <vector>

struct Enemy {
    virtual void update() const = 0;  // pure virtual: every enemy must say how it moves
    virtual ~Enemy() = default;       // needed for delete through Enemy*
};
struct Slime : Enemy { void update() const override { std::printf("slime hops\n"); } };
struct Bat : Enemy   { void update() const override { std::printf("bat swoops\n"); } };

int main() {
    std::vector<std::unique_ptr<Enemy>> wave;
    wave.push_back(std::make_unique<Slime>());
    wave.push_back(std::make_unique<Bat>());
    wave.push_back(std::make_unique<Slime>());
    for (const auto& e : wave) e->update();   // one loop, three behaviours
}
```
```text
slime hops
bat swoops
slime hops
```

`= 0` makes the class **abstract**: you cannot create a plain `Enemy`. `override` asks the compiler to check that you really override something. (`std::unique_ptr` is a pointer that deletes its object automatically; the ownership module explains it fully.)

## How virtual calls work: vtables and slicing

Compilers implement virtual functions with a **vtable**: one table per class holding the addresses of its virtual functions. Each object of such a class has a hidden pointer, the **vptr**, to its class's table. That adds 8 bytes to every object on x86-64.

A call `e->update()` becomes: load the vptr from the object, load the function address from the `update` slot, call it. That indirect call usually cannot be inlined, which is the runtime cost of dynamic dispatch. For 300 enemies per frame it does not matter. For 100,000 particles it does, which is why the data-oriented design module stores particles differently.

**Object slicing** happens when you copy a derived object into a base **value**: only the base part is copied, and the derived data and vptr are lost. Store enemies by pointer or reference to keep their real type. The inheritance lesson shows the slicing bug happening in the spawner.
