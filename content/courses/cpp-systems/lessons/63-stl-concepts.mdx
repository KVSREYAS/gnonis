## Milestone 6: entity lists, inventory and events

**What we build this module:** the list of live enemies that grows when the spawner fires and shrinks when enemies die; the targeting code that finds the nearest enemy; the event system ("on enemy killed, add score, play a sound, maybe drop loot"); the inventory, keyed by item name; and a spatial grid so collision checks only look at nearby enemies.

**Why the game needs it:** all of this is collections of things, searched and changed every frame. The standard library already has the containers and algorithms. Using them well is mostly about three questions: where the elements live in memory, when an address into the container stops being valid, and who owns the data a function is looking at.

## The careless version: a pointer into a growing list

```cpp
#include <cstdio>
#include <vector>

struct Enemy { int id; int hp; };

int main() {
    std::vector<Enemy> enemies{{1, 20}, {2, 20}};
    Enemy* target = &enemies[0];              // turret locks on to enemy 1
    enemies.push_back({3, 20});               // a new slime spawns
    target->hp -= 5;                          // turret fires
    std::printf("turret hit enemy %d\n", target->id);
}
```
```text
==1==ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000014 at pc 0x564c6b5ba6f5 bp 0x7ffdcf2191c0 sp 0x7ffdcf2191b8
SUMMARY: AddressSanitizer: heap-use-after-free game.cpp:10 in main
```

The vector was full (capacity 2), so `push_back` allocated a bigger buffer, moved the enemies, and freed the old one. `target` still pointed into the freed buffer. The turret fired at memory that no longer holds an enemy. In a release build, without ASan, this usually "works" for a while and then corrupts something unrelated.

## Containers and their layout

A **container** is a class that owns a group of elements. Its layout decides what is fast:

- `std::vector<T>`: one contiguous heap array, plus size and capacity. Fast index, fast iteration, cheap append at the end.
- `std::deque<T>`: several fixed-size blocks. Cheap insert at both ends.
- `std::list<T>`: separate heap node per element. Insert anywhere without moving others, but slow to iterate.
- `std::map<K,V>`: balanced tree of nodes, sorted by key, O(log n) lookup.
- `std::unordered_map<K,V>`: hash table, average O(1) lookup.

**Size** is how many elements exist. **Capacity** (vector only) is how many fit before it must reallocate. `std::vector` is the right default: contiguous memory suits the CPU cache, and games iterate over everything every frame.

## Iterators and invalidation

An **iterator** refers to one element and can move to the next. For a vector it is basically a pointer. `begin()` is the first element, `end()` is one past the last.

An iterator, pointer or reference into a container is **invalidated** when the element moves or is destroyed. Using it afterwards is undefined behaviour, as in the turret above.

- vector: any reallocation invalidates everything; insert or erase invalidates from that point on
- list and map: only the erased element's iterators die

That is why game code often stores enemy **ids** or **indices** rather than pointers into a vector, and looks them up when needed.

## Algorithms, ranges and lambdas

The `<algorithm>` header has `sort`, `find`, `count_if`, `min_element` and many more. They take a **range** (a begin and end iterator, or in C++20 the container itself), so one `sort` works on any container.

A **lambda** is an unnamed function written inline. The `[...]` part says which local variables it **captures**:

```cpp
#include <algorithm>
#include <cstdio>
#include <vector>

struct Enemy { int id; float dist; int hp; };

int main() {
    std::vector<Enemy> enemies{{1, 9.5f, 20}, {2, 3.0f, 0}, {3, 4.5f, 12}};
    float range = 5.0f;
    auto in_range = [range](const Enemy& e) { return e.hp > 0 && e.dist <= range; };
    auto n = std::ranges::count_if(enemies, in_range);
    auto nearest = std::ranges::min_element(enemies, {}, &Enemy::dist);
    std::printf("live enemies in range: %ld, nearest enemy: %d\n", (long)n, nearest->id);
}
```
```text
live enemies in range: 1, nearest enemy: 2
```

`[range]` copies `range` into the lambda. `[&range]` would refer to it. `&Enemy::dist` is a **projection**: compare enemies by their `dist`. Note the nearest enemy is dead: "nearest" and "nearest live" are different questions.

## optional, variant and maps

- `std::optional<T>` holds a T or nothing. A function that may not find an enemy returns `std::optional<int>` instead of a magic `-1`.
- `std::variant<A, B, C>` holds exactly one of several types, and knows which. Game events (Damage, Heal, Spawn) fit in one queue as a variant.
- `std::map` and `std::unordered_map` look things up by key: item name to count, grid cell to the enemies in it. Watch out: `m[key]` **inserts** a default value when the key is missing.

Each of these gets its own lesson in this module.

## Views: span and string_view

A **view** refers to data owned by something else. It does not allocate and does not free.

- `std::string_view`: a `const char*` and a length.
- `std::span<T>`: a `T*` and a length, for any contiguous array.

```cpp
void apply_damage(std::span<int> hp, int dmg) {
    for (int& h : hp) h -= dmg;
}
apply_damage(slime_hp, 5);      // a std::vector<int>
apply_damage(boss_parts, 5);    // an int[4]: same function, no copy
```

Views are cheap to pass by value (two words). The risk is lifetime: the view must not outlive the owner. A `string_view` made from a temporary `std::string` dangles at the end of the statement.

## Small string optimization

Allocating for every short string would be slow, so major implementations store short strings (up to 15 characters in libstdc++ and MSVC, 22 in libc++) **inside** the `std::string` object. This is the **small string optimization (SSO)**.

- `sizeof(std::string)` is 32 bytes in libstdc++.
- Moving a short string copies its characters.
- A `string_view` into a short string points inside the string object, so it dangles if that object moves, even with no reallocation. Item names like "Potion" are short.
