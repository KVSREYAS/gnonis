## Milestone 8: particles and ECS

**What we build this module:** a particle system that runs 1,000,000 particles (explosions, rain, slime splatter) inside the frame budget, and an **entity-component-system** (ECS): the way most modern engines store game objects, as ids plus arrays of components.

**Why the game needs it:** the OOP module gave every game object a class, a virtual `update()`, and a heap allocation. That is fine for the 50 objects of a menu screen. For a million particles it is the bottleneck: the CPU spends its time fetching scattered objects and jumping through vtables rather than doing the two additions per particle we actually asked for.

## The careless version: one object per particle

```cpp
#include <algorithm>
#include <chrono>
#include <cstdio>
#include <memory>
#include <random>
#include <vector>

struct Particle {                        // the OOP way: a class per particle
    virtual ~Particle() = default;
    virtual void update(float dt) = 0;
};
struct Spark : Particle {
    float x = 0, y = 0, vx = 1, vy = 2, life = 5; char debug_name[32] = "spark";
    void update(float dt) override { x += vx * dt; y += vy * dt; life -= dt; }
};

int main() {
    const int N = 1'000'000;
    std::vector<std::unique_ptr<Particle>> oop;
    std::vector<std::unique_ptr<char[]>> other;          // other allocations in between, as in a real game
    std::mt19937 rng(3);
    for (int i = 0; i < N; ++i) { oop.push_back(std::make_unique<Spark>()); other.push_back(std::make_unique<char[]>(rng() % 200)); }
    std::shuffle(oop.begin(), oop.end(), rng);           // spawn and death order mixes them up

    std::vector<float> x(N), y(N), vx(N, 1), vy(N, 2), life(N, 5);   // the data-oriented way

    auto t0 = std::chrono::steady_clock::now();
    for (auto& p : oop) p->update(0.016f);
    auto t1 = std::chrono::steady_clock::now();
    for (int i = 0; i < N; ++i) { x[i] += vx[i] * 0.016f; y[i] += vy[i] * 0.016f; life[i] -= 0.016f; }
    auto t2 = std::chrono::steady_clock::now();
    auto ms = [](auto d) { return std::chrono::duration<double, std::milli>(d).count(); };
    std::printf("objects + virtual update: %.2f ms\n", ms(t1 - t0));
    std::printf("plain arrays:             %.2f ms\n", ms(t2 - t1));
    std::printf("(check: %.3f)\n", x[N / 2]);
}
```
```text
objects + virtual update: 16.42 ms
plain arrays:             1.44 ms
(check: 0.016)
```

(One run on the course machine. The ratio is what matters, and it grows with N.)

## What went wrong

Same arithmetic, very different time. In the object version, each particle is a separate heap block of 64 bytes, at a scattered address. For each one the CPU loads the pointer, then the object (usually a cache miss), then the vtable pointer, then makes an indirect call. Of the 64 bytes loaded, the update uses 20.

The array version walks five arrays front to back. Every byte loaded is used, the prefetcher keeps up, and the compiler turns the loop into SIMD instructions that process 4 or 8 particles at a time.

## The idea

Object-oriented code groups data by what it **is**: one `Particle` object with every field. **Data-oriented design** groups data by what the code **does** with it.

1. List the hot loops (where frame time goes).
2. For each, list the fields it reads and writes.
3. Lay out memory so those fields are packed together with nothing in between.

"Where there is one, there are many": design for the loop over all particles, not for one particle.

## AoS and SoA

**Array of Structures (AoS)**: `std::vector<Particle>`, each element with all fields. A loop that reads only `x` still loads every other field.

**Structure of Arrays (SoA)**: one array per field, `std::vector<float> x, y, vx, vy`. A loop over `x` uses every byte it loads, and is easy to turn into SIMD.

AoS is still better when every access needs all fields of one item, such as looking up one enemy by index for the inspector panel.

## Hot and cold fields

A **hot** field is read every frame (position, hp). A **cold** field is read rarely (the enemy's display name, its loot table, debug info). **Hot/cold splitting** keeps the hot fields in a compact array and moves the cold ones to a parallel array, linked by index. More enemies fit per cache line, and the hot loop stops loading names it never reads.

## Branches and prediction

A CPU runs many instructions ahead before it knows which way an `if` goes. The **branch predictor** guesses from past behaviour. A correct guess is free; a wrong one throws away the speculative work, roughly 15-20 cycles. A branch on random data (`if (particle.alive)` with alive particles scattered randomly) is mispredicted about half the time. Fixes: keep the data sorted or partitioned (all live particles first), or compute without a branch.

## Entity-component-system

An **ECS** applies all of this to game objects:

- An **entity** is just an id (an integer).
- A **component** is plain data: `Position`, `Velocity`, `Health`, `Sprite`. Each component type is stored in its own dense array.
- A **system** is a loop over every entity that has a given set of components: the movement system reads Position and Velocity.

A "flying, shooting slime" is not a class; it is an entity with Position, Velocity, Flying and Weapon components. The ECS lesson in this module builds the core of one.
