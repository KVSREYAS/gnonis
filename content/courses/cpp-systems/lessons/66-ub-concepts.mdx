## Milestone 9: crash hunting in release

**What we build this module:** nothing new. The game is feature-complete enough for a test build, and the testers report bugs that never happen in the debug build: a score that stops going up, a save file that loads wrong values, a crash on one level after 20 minutes. This module is about finding and fixing them.

**Why the game needs it:** almost every "only in release" bug is **undefined behaviour**. The debug build happens to do what you meant; the optimized build does something else, and both are allowed. Knowing the common kinds, and running the sanitizers, turns hours of guessing into one stack trace.

## The careless version: an overflow check that gets deleted

The score is an `int`. To stop it wrapping around to negative, someone added a check:

```cpp
#include <climits>
#include <cstdio>

__attribute__((noinline)) bool would_overflow(int score, int bonus) {
    int sum = score + bonus;
    return sum < score;                      // "if it wrapped, the sum is smaller"
}

int main() {
    int score = INT_MAX - 10;
    std::printf("overflow check says: %s\n", would_overflow(score, 100) ? "would overflow" : "safe to add");
}
```

Debug build (`-O0`):

```text
overflow check says: would overflow
```


Release build (`-O2`), same source:

```text
overflow check says: safe to add
```

## What went wrong

Signed integer overflow is undefined behaviour. The compiler may assume it never happens. If `score + bonus` never overflows, then for a positive bonus it is always larger than `score`, so `sum < score` simplifies to `bonus < 0`. The check was deleted. In the debug build the addition wrapped (what the hardware does), so the check "worked" by luck.

The fix is to check before adding, without overflowing: `bonus > 0 && score > INT_MAX - bonus`. Or use `__builtin_add_overflow`, or a wider type.

## What UB is

The C++ standard sorts program behaviour into kinds. The dangerous one is **undefined behaviour**: an operation for which the standard sets no rules at all. Anything may happen, including "works in debug, breaks in release".

Common cases:

- signed integer overflow: `INT_MAX + 1`
- out-of-bounds array access
- dereferencing a null or dangling pointer
- reading an uninitialized variable
- data race: two threads access the same memory, one writes, no synchronization
- shifting by the bit width or more: `1 << 32` on a 32-bit int

Unsigned overflow is **not** UB. It wraps modulo 2^N.

## Why the optimizer makes it worse

The compiler uses "no UB happens" as a fact when simplifying. Another example:

```cpp
int hp_of(Enemy* e) {
    int v = e->hp;       // if e were null this is UB
    if (!e) return 0;    // so this check can be deleted
    return v;
}
```

The result is not a crash at the bad line. It is code that does something you never wrote, sometimes far from the cause. That is why UB must be prevented, not just tested for.

## Aliasing and bit_cast

Two pointers **alias** when they refer to the same memory. The **strict aliasing rule** says you may access an object only through its own type, a `char`/`unsigned char`/`std::byte` pointer, or a few related types. So the compiler assumes a `float*` and an `int*` never point to the same bytes.

```cpp
float f = 1.0f;
uint32_t bits = *reinterpret_cast<uint32_t*>(&f);  // UB
uint32_t a = std::bit_cast<uint32_t>(f);           // C++20, legal
uint32_t b; std::memcpy(&b, &f, sizeof b);         // legal, compiles to one move
```

Save files and network packets are full of this: bytes that must become floats and ints. `memcpy` and `bit_cast` are the legal ways.

## Finding UB with sanitizers

A **sanitizer** is a compiler mode that adds runtime checks to your program.

- **AddressSanitizer** (`-fsanitize=address`): out-of-bounds, use after free, double free, leaks.
- **UndefinedBehaviorSanitizer** (`-fsanitize=undefined`): signed overflow, bad shifts, null dereference, misaligned access.
- **ThreadSanitizer** (`-fsanitize=thread`): data races. Cannot be combined with ASan.

```bash
g++ -std=c++20 -g -O1 -fsanitize=address,undefined game.cpp
./a.out   # prints the exact line and a stack trace on the first error
```

They slow the program by roughly 2-15 times, so use them in test builds and CI, not in the shipped game. This site's runner does not enable sanitizers, so run them locally.

## Type punning and std::launder

**Type punning** means reading the bytes of an object as a different type. In C++ the legal methods are `std::memcpy`, `std::bit_cast`, and access through `char`, `unsigned char` or `std::byte`. Writing one member of a `union` and reading another is UB in C++ (GCC allows it as an extension, but do not rely on it).

`std::launder(p)` is a rare tool: when you create a new object with placement `new` in storage that held an old object with `const` or reference members, `std::launder` gives a pointer the compiler must treat as pointing to the new object. You will meet it in custom allocators and containers, almost never elsewhere.
