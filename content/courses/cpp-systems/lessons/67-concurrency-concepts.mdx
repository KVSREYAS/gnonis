## Milestone 10: the asset loading thread

**What we build this module:** a background thread that loads the next level's textures and sounds while the current level keeps running, a progress bar fed by that thread, and per-worker statistics that do not slow each other down.

**Why the game needs it:** loading a level means reading files and decoding images, which takes hundreds of milliseconds. Done on the main thread, the game freezes: no input, no animation, and on consoles a certification failure. Moving the work to another thread fixes the freeze, but two threads touching the same memory is where a new class of bugs starts.

## The careless version: load on the main thread

```cpp
#include <chrono>
#include <cstdio>
#include <thread>

using namespace std::chrono;

void load_next_level() { std::this_thread::sleep_for(milliseconds(150)); }   // stand-in for file reads and decoding

int main() {
    for (int frame = 1; frame <= 6; ++frame) {
        auto t0 = steady_clock::now();
        std::this_thread::sleep_for(milliseconds(5));                       // update + draw
        if (frame == 3) load_next_level();                                  // player reached the exit
        auto ms = duration_cast<milliseconds>(steady_clock::now() - t0).count();
        std::printf("frame %d: %3ld ms%s\n", frame, (long)ms, ms > 17 ? "   <- the game froze" : "");
    }
}
```
```text
frame 1:   5 ms
frame 2:   5 ms
frame 3: 155 ms   <- the game froze
frame 4:   5 ms
frame 5:   5 ms
frame 6:   5 ms
```

At 60 FPS each frame has 16.7 ms. Frame 3 took ten times that: the screen stopped, and the input from those 150 ms was handled late or lost.

## The fix, and the new problem

Start the load on another thread, and keep drawing frames:

```cpp
#include <atomic>
#include <chrono>
#include <cstdio>
#include <thread>

using namespace std::chrono;

std::atomic<bool> level_ready{false};

int main() {
    std::jthread loader;
    long slowest = 0;
    for (int frame = 1; frame <= 100; ++frame) {
        auto t0 = steady_clock::now();
        std::this_thread::sleep_for(milliseconds(5));                       // update + draw
        if (frame == 3) loader = std::jthread([] {                          // start loading, keep going
            std::this_thread::sleep_for(milliseconds(150));
            level_ready.store(true, std::memory_order_release);
        });
        long ms = (long)duration_cast<milliseconds>(steady_clock::now() - t0).count();
        slowest = ms > slowest ? ms : slowest;
        if (level_ready.load(std::memory_order_acquire)) {
            std::printf("level loaded during frame %d; slowest frame: %ld ms\n", frame, slowest);
            break;
        }
    }
}
```
```text
level loaded during frame 33; slowest frame: 5 ms
```

The game kept drawing frames the whole time the level loaded, and no frame went over budget. The new question is how the two threads share data safely: the loader writes the level, the main thread reads it. That is what the rest of the module is about.

## Threads

A **thread** runs its own sequence of instructions with its own stack, but it shares heap and global memory with all other threads in the process. On a multi-core CPU, threads truly run at the same time.

`std::jthread t(f);` starts a thread running `f`. `join()` waits for it to finish. A plain `std::thread` destroyed while still running calls `std::terminate`; `std::jthread` (C++20) joins automatically in its destructor and carries a **stop token**, so the loader can be told to give up when the player quits to the menu.

Starting a thread costs tens of microseconds, so long-running workers are reused (the job system in the building-blocks module).

## Data races and mutexes

A **data race**: two threads access the same memory location at the same time, at least one access is a write, and nothing orders them. It is undefined behaviour.

`textures_loaded++` is really three steps: load, add, store. Two threads can both load 5 and both store 6, losing one.

A **mutex** lets only one thread at a time into a **critical section**:

```cpp
std::mutex m;
std::vector<Texture> loaded;
void add(Texture t) {
    std::lock_guard lock(m);   // lock now, unlock at scope end
    loaded.push_back(std::move(t));
}
```

Mutexes are correct and simple. A contended lock costs time while threads wait, so keep critical sections short.

## Atomics and memory order

`std::atomic<T>` makes each operation on it **indivisible**: no thread sees half of it, and no update is lost. `progress.fetch_add(1)` is safe from any thread.

The harder part is ordering. CPUs and compilers reorder independent memory operations for speed. **Memory orders** limit that:

- `relaxed`: only the atomic itself is safe. Fine for counters like the progress bar.
- `release` (on a store) + `acquire` (on a load that reads that value): everything written before the release is visible after the acquire. Used to publish data, such as "the level is ready".
- `seq_cst` (default): one global order all threads agree on. Simplest, sometimes slower.

## False sharing

Cores keep caches **coherent** per 64-byte cache line. When a core writes to a line, other cores' copies of that whole line become invalid.

If worker A updates `stats[0]` and worker B updates `stats[1]`, and both sit in one line, every write by one forces a reload by the other. They share no data, yet slow each other down. This is **false sharing**. Fix: give each thread's hot data its own line with `alignas(64)`.

## Condition variables and compare-exchange

A **condition variable** lets a thread sleep until another thread says something changed. It always works with a mutex and a condition you check:

```cpp
std::unique_lock lk(m);
cv.wait(lk, [&]{ return !requests.empty(); });  // unlocks while asleep
```

`wait` re-checks the condition after waking, because wake-ups can happen with no notify (**spurious wake-ups**). The other side changes the data under the lock, then calls `cv.notify_one()`.

`compare_exchange_weak(expected, desired)` is the basic lock-free building block: if the atomic equals `expected`, set it to `desired` and return true; otherwise write the current value into `expected` and return false.
