## Milestone 11: particle physics for every explosion

**What we build this module:** the particle step that moves tens of thousands of sparks, slime droplets and smoke puffs every frame, written so the CPU processes four (or eight) particles per instruction. Then the total-energy statistic the effects system uses to fade old explosions, and a damage clamp kernel.

**Why the game needs it:** after the data-oriented rewrite, particles live in flat float arrays. That is exactly the shape SIMD hardware wants. A loop that handles one float per instruction leaves most of each core idle; the same loop written so the compiler can vectorize it runs several times faster without touching the algorithm.

## The careless version: a call per particle

The physics helper lives in another `.cpp` file, so the compiler cannot see inside it when compiling the loop (no link-time optimization). `noipa` below makes that happen in one file.

```cpp
#include <chrono>
#include <cstdio>
#include <vector>

constexpr int N = 4096;                       // particles alive this frame
struct Particles { std::vector<float> x, vx; };

__attribute__((noipa)) float move_one(float x, float vx, float dt) { return x + vx * dt; }   // "in physics.cpp"

__attribute__((noipa)) void step_calls(Particles& p, float dt) {
    for (int i = 0; i < N; ++i) p.x[i] = move_one(p.x[i], p.vx[i], dt);
}
__attribute__((noipa)) void step_simd(float* __restrict x, const float* __restrict vx, float dt) {
    for (int i = 0; i < N; ++i) x[i] += vx[i] * dt;
}

int main() {
    Particles p{std::vector<float>(N, 0.f), std::vector<float>(N, 1.f)};
    auto ms = [](auto d) { return std::chrono::duration<double, std::milli>(d).count(); };
    auto t0 = std::chrono::steady_clock::now();
    for (int frame = 0; frame < 100000; ++frame) step_calls(p, 0.016f);
    auto t1 = std::chrono::steady_clock::now();
    for (int frame = 0; frame < 100000; ++frame) step_simd(p.x.data(), p.vx.data(), 0.016f);
    auto t2 = std::chrono::steady_clock::now();
    std::printf("call per particle: %6.1f ms\n", ms(t1 - t0));
    std::printf("plain SIMD loop:   %6.1f ms\n", ms(t2 - t1));
}
```
```text
call per particle:  710.3 ms
plain SIMD loop:     30.9 ms
```

Same arithmetic, same particles, one run on the course machine at `-O2`. The first loop does one particle per call and per instruction. The second loop compiled to `mulps`/`addps`, which handle four floats each.

## What SIMD is

A normal (scalar) add instruction adds one pair of numbers. A **SIMD** instruction adds several pairs at once, using wide **vector registers**.

On x86-64:

- **SSE**: 128-bit `xmm` registers. 4 floats, 2 doubles, or 4 int32s. Always available on x86-64.
- **AVX/AVX2**: 256-bit `ymm`, 8 floats.
- **AVX-512**: 512-bit `zmm`, 16 floats, on some CPUs.

Each slot in the register is a **lane**. `addps` adds lane 0 to lane 0, lane 1 to lane 1, and so on, in about the same time as one scalar add.

## Auto-vectorization

At `-O2` (GCC 12 and newer) and `-O3`, the compiler tries to turn loops into SIMD code. It succeeds when:

1. Iterations are **independent**: iteration i does not need the result of i-1.
2. Memory is accessed contiguously, ideally one flat array per field.
3. It can prove arrays do not overlap (`__restrict`), or it adds a runtime check. At `-O2` GCC only uses the cheap cases, so the proof matters.
4. There are no function calls it cannot inline.

Check the result with `-fopt-info-vec` (GCC) or by reading the assembly for `ps` (packed single) instructions like `addps`.

## Intrinsics

**Intrinsics** are functions that map one-to-one to specific instructions. They let you write SIMD by hand.

```cpp
#include <immintrin.h>
void add4(float* a, const float* b) {
    __m128 va = _mm_loadu_ps(a);   // load 4 floats (unaligned ok)
    __m128 vb = _mm_loadu_ps(b);
    _mm_storeu_ps(a, _mm_add_ps(va, vb));
}
```

Naming: `_mm_` = 128-bit, `add` = operation, `ps` = packed single-precision. `__m128` is the register type. `_mm_load_ps` (no `u`) requires 16-byte alignment. For a length that is not a multiple of 4, finish the last 0-3 elements with a scalar **tail loop**.

## Reductions

A **reduction** combines many values into one, such as total kinetic energy. `s += x[i]` has a dependency: each add needs the previous `s`. A float add has a latency of about 4 cycles, so the loop is limited to one add per 4 cycles.

Fix: keep several independent **accumulators** and combine them at the end. Floating-point addition is not associative, so this changes the rounding a little. That is why the compiler will not do it for you without `-ffast-math` or `-fassociative-math`.

## FMA and horizontal operations

**FMA** (fused multiply-add) computes `a * b + c` in one instruction with one rounding step. It needs the FMA3 extension (`-mfma` or `-march=native`), not baseline SSE2, so this site's runner does not use it.

A **horizontal** operation combines lanes **within** one register, for example adding the 4 floats of an `__m128` into one float. These are slower than vertical (lane by lane) operations, so SIMD code keeps sums vertical inside the loop and does one horizontal sum at the end.
