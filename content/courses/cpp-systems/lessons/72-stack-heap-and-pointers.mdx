## The feature: fireballs

The player presses a key and casts a fireball. The function `cast_fireball()` runs once, but the fireball must keep flying for the next 2 seconds, long after that function has returned. The game loop updates it every frame.

So the fireball object has to **outlive the function that created it**. To see why that is a problem, you need to know where C++ objects live.

## Two places objects live

- **The stack.** Every function call gets a block of memory for its local variables. When the function returns, the whole block is reused by the next call. Locals are created and destroyed automatically and very fast. Their lifetime is their scope.
- **The heap** (also called the free store). A large pool of memory you request explicitly with `new`. An object made with `new` stays alive until you `delete` it, no matter which function is running. Getting heap memory is slower than the stack, and remembering to give it back is your job.

A fireball made as a local in `cast_fireball()` is on the stack, so it dies when the function returns.

## Pointers in one card

A **pointer** is a variable that holds the address of an object.

```cpp
#include <cstdio>

struct Fireball { float x = 0; int damage = 25; };

int main() {
    Fireball f;
    Fireball* p = &f;          // & takes the address of f
    p->x = 3.5f;               // -> reaches a member through the pointer
    (*p).damage = 40;          // * gives the object itself; same as p->damage
    std::printf("x=%.1f damage=%d\n", f.x, f.damage);
    Fireball* none = nullptr;  // points at nothing
    if (none == nullptr) std::printf("no target\n");
}
```
```text
x=3.5 damage=40
no target
```

A pointer does not own or protect the object. It is only an address. If the object dies, the pointer still holds the old address. That is called a **dangling** pointer.

## The careless version: return a pointer to a local

```cpp
#include <cstdio>

struct Fireball { float x = 0; int damage = 25; };

Fireball* cast_fireball() {
    Fireball f;          // lives on cast_fireball's stack frame
    f.damage = 40;
    return &f;           // address of something about to die
}

int main() {
    Fireball* fb = cast_fireball();
    std::printf("damage %d\n", fb->damage);
}
```

g++ warns: `function returns address of local variable`. It goes further: since using that address is undefined behaviour anyway, GCC compiles `return &f;` as returning a null pointer. Built with the sanitizers, the run stops at the read:

```text
game.cpp:13:16: runtime error: member access within null pointer of type 'struct Fireball'
```

Other compilers, or other optimization levels, return the real dead address instead, and the program may print 40, 0 or garbage depending on what reused that stack memory. It "works" until it doesn't, which is the worst kind of bug.

## The fix: create it on the heap

`new Fireball` creates the object on the heap and returns a pointer to it. It survives the return. Now the game owns it and must `delete` it when the fireball hits something or times out.

```cpp
#include <cstdio>

struct Fireball {
    float x = 0;
    int damage = 25;
    ~Fireball() { std::printf("fireball gone\n"); }
};

Fireball* cast_fireball() {
    Fireball* f = new Fireball;   // heap: lives until delete
    f->damage = 40;
    return f;
}

int main() {
    Fireball* fb = cast_fireball();
    std::printf("damage %d\n", fb->damage);
    delete fb;                    // runs ~Fireball, returns the memory
    fb = nullptr;                 // so nobody uses the old address
}
```
```text
damage 40
fireball gone
```

## Mistake 1: forgetting delete (a leak)

The fireball hits a wall. The collision code removes the pointer from the list but forgets `delete`. Nothing crashes. The memory is just never returned.

```cpp
#include <vector>

struct Fireball { float x = 0, y = 0, vx = 0, vy = 0; int damage = 25; };

int main() {
    std::vector<Fireball*> live;
    for (int frame = 0; frame < 100; ++frame) {
        live.push_back(new Fireball);   // one cast per frame
        live.pop_back();                // "hit a wall": removed, never deleted
    }
}
```
```text
==1==ERROR: LeakSanitizer: detected memory leaks
Direct leak of 2000 byte(s) in 100 object(s) allocated from:
SUMMARY: AddressSanitizer: 2000 byte(s) leaked in 100 allocation(s).
```

100 fireballs, 20 bytes each, gone. A real game casts thousands per level and runs for hours, so a leak like this slowly eats memory until the game stutters or the OS kills it. LeakSanitizer (part of ASan) found it.

## Mistake 2: deleting twice

The fireball hits a slime and a wall in the same frame. Both handlers delete it.

```cpp
struct Fireball { int damage = 25; };

void on_hit_enemy(Fireball* f) { delete f; }
void on_hit_wall(Fireball* f)  { delete f; }

int main() {
    Fireball* f = new Fireball;
    on_hit_enemy(f);
    on_hit_wall(f);      // same address, second delete
}
```
```text
==1==ERROR: AddressSanitizer: attempting double-free on 0x502000000010 in thread T0:
SUMMARY: AddressSanitizer: double-free ../../../../src/libsanitizer/asan/asan_new_delete.cpp:164 in operator delete(void*, unsigned long)
```

Without ASan, glibc often catches this too and aborts with `free(): double free detected`. Sometimes it doesn't, and the heap is silently corrupted until a crash somewhere unrelated.

## Mistake 3: use after delete

The homing missile keeps a raw pointer to its target. The target dies and is deleted. Next frame the missile reads the target's position.

```cpp
#include <cstdio>

struct Bat { float x = 5, y = 7; };

int main() {
    Bat* bat = new Bat;
    Bat* missile_target = bat;   // second pointer to the same bat
    delete bat;                  // the bat dies
    bat = nullptr;               // this pointer is safe now, the other one is not
    std::printf("%.1f\n", missile_target->x);
}
```
```text
==1==ERROR: AddressSanitizer: heap-use-after-free on address 0x502000000010 at pc 0x55a625fa62da bp 0x7ffc234967f0 sp 0x7ffc234967e8
SUMMARY: AddressSanitizer: heap-use-after-free game.cpp:10 in main
```

Setting `bat = nullptr` did nothing for `missile_target`. Every copy of a raw pointer has to know when the object dies. The ownership module fixes this properly with `std::unique_ptr` and `std::weak_ptr`.

## Arrays: new[] needs delete[]

`new Fireball[8]` creates 8 objects in a row and returns a pointer to the first. It must be released with `delete[]`, not `delete`. Mixing them is undefined behaviour. In modern code you almost never write `new[]`: `std::vector<Fireball>` does the same thing and frees itself.

## When to use it, and when not

- Use **stack** objects by default. They are fast and clean themselves up. Most game objects that only live during one function (a temporary `Vec2`, a raycast result) belong there.
- Use the **heap** when an object must outlive its scope, when its size is only known at run time, or when it is too big for the stack (a 4 MB level grid).
- Raw `new` and `delete` are shown here so you understand what goes wrong. Real code wraps heap objects in owners: `std::vector`, `std::unique_ptr`, `std::shared_ptr`. Those come in the next modules.
- Raw pointers are still fine for **non-owning** access: "look at this enemy" without being responsible for deleting it.
