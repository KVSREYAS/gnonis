## The feature: the event bus

When an enemy dies, several systems care: the score goes up, a sound plays, a loot table rolls, the combo counter ticks, an achievement may unlock. The combat code should not know about all of them. Instead it **emits** an "enemy killed" event, and each system **subscribes** a function to run when it happens.

A subscribed function is a **callback**. In C++ we usually write it as a **lambda**.

## Lambdas in one example

```cpp
#include <cstdio>
#include <functional>
#include <vector>

int main() {
    int score = 0;
    std::vector<std::function<void(int)>> on_kill;            // the subscribers

    on_kill.push_back([&score](int xp) { score += xp; });    // capture by reference
    int bonus = 2;
    on_kill.push_back([bonus](int xp) { std::printf("combo x%d for %d xp\n", bonus, xp); });   // by copy

    for (auto& f : on_kill) f(50);                            // an enemy died: emit
    std::printf("score %d\n", score);
}
```
```text
combo x2 for 50 xp
score 50
```

- `[...]` is the **capture list**. `[score]` copies the variable into the lambda when it is created. `[&score]` stores a reference to it.
- `(int xp)` are the parameters, `{ ... }` the body.
- The compiler turns each lambda into a small class: captured variables become members, the body becomes `operator()`.
- `std::function<void(int)>` can hold any callable taking an `int` and returning nothing, so different lambdas fit in one vector.

## The careless version: a callback that outlives what it captured

The combo counter subscribes while a combo is active, using a local:

```cpp
#include <cstdio>
#include <functional>
#include <vector>

std::vector<std::function<void()>> on_kill;

void start_combo() {
    int combo = 0;
    on_kill.push_back([&combo] { ++combo; std::printf("combo %d\n", combo); });
}   // combo dies here; the lambda still refers to it

int main() {
    start_combo();
    for (auto& f : on_kill) f();     // the next enemy dies
}
```
```text
==1==ERROR: AddressSanitizer: stack-use-after-return on address 0x7f922f600030 at pc 0x555a734b73d2 bp 0x7fff356d8a40 sp 0x7fff356d8a38
    [48, 52) 'combo' (line 8) <== Memory access at offset 48 is inside this variable
SUMMARY: AddressSanitizer: stack-use-after-return game.cpp:9 in operator()
```

## What went wrong

`[&combo]` stored a reference to a local of `start_combo`. That function returned, its stack frame was reused, and the stored lambda kept the reference. When the next kill fired the callback, it read and wrote stack memory that now belongs to something else. ASan reports it as a stack-use-after-return and names the variable. In a normal build it might print a random number, or quietly overwrite another function's local.

The same bug happens with `[this]` when an object subscribes and is then destroyed without unsubscribing.

## The fix: capture what the callback needs to own

Either capture by value, so the lambda owns its copy (and mark it `mutable` to change that copy), or keep the state somewhere that lives as long as the subscription:

```cpp
#include <cstdio>
#include <functional>
#include <vector>

std::vector<std::function<void()>> on_kill;

void start_combo() {
    on_kill.push_back([combo = 0]() mutable { ++combo; std::printf("combo %d\n", combo); });
}

int main() {
    start_combo();
    for (int kill = 0; kill < 3; ++kill)
        for (auto& f : on_kill) f();
}
```
```text
combo 1
combo 2
combo 3
```

`[combo = 0]` is an **init capture**: it creates a member named `combo` inside the lambda. `mutable` allows the body to change it (a lambda's `operator()` is `const` by default).

## Unsubscribing

An object that subscribes `[this]` must unsubscribe before it dies. The usual design: `subscribe` returns an id, and the subscriber calls `unsubscribe(id)` in its destructor (or holds an RAII handle that does).

## What std::function costs

`std::function` stores the callable in a small internal buffer, or on the heap if it is too big (libstdc++'s buffer holds 16 bytes). Calling it is an indirect call that the compiler usually cannot inline. For events that fire a few times per frame, that is nothing. For a callback inside a loop over 100,000 particles, pass the lambda as a template parameter instead (`template <class F> void for_each_particle(F f)`), which the compiler inlines.

## When to use it, and when not

- Use lambdas for short logic passed to algorithms (`sort`, `erase_if`) and for callbacks.
- Capture by value (`[=]`, `[x]`, `[x = std::move(y)]`) for anything stored and called later. Capture by reference (`[&]`) only for lambdas used immediately, like an algorithm's predicate.
- Use `std::function` when you must store callables of different types. Use a template parameter when the callable is used right away in hot code.
- Keep event handlers short. A handler that emits another event that emits another is hard to follow and can loop forever.
