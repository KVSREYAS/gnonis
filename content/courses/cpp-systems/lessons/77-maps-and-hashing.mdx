## The feature: the inventory

The inventory maps item names to counts: `"potion" -> 3`, `"key" -> 1`. The shop screen checks whether the player has a dragon egg before offering a trade.

## The careless version: looking with operator[]

```cpp
#include <cstdio>
#include <map>
#include <string>

int main() {
    std::map<std::string, int> inventory{{"potion", 3}, {"key", 1}};
    if (inventory["dragon egg"] > 0) std::printf("trade available\n");   // just checking...
    if (inventory["golden fork"] > 0) std::printf("trade available\n");
    std::printf("inventory screen shows %zu items:\n", inventory.size());
    for (const auto& [name, count] : inventory) std::printf("  %-12s x%d\n", name.c_str(), count);
}
```
```text
inventory screen shows 4 items:
  dragon egg   x0
  golden fork  x0
  key          x1
  potion       x3
```

## What went wrong

`operator[]` returns a reference to the value for that key, so it must have a value to refer to. If the key is missing, it **inserts** one, with a default value (0 for `int`). Two "checks" added two items to the inventory. The inventory screen now lists a dragon egg and a golden fork, both x0, and the save file stores them.

For the same reason, `operator[]` does not compile on a `const std::map`: it might modify it.

## The fix: look without inserting

```cpp
#include <cstdio>
#include <map>
#include <string>

int count_of(const std::map<std::string, int>& inv, const std::string& item) {
    auto it = inv.find(item);
    return it == inv.end() ? 0 : it->second;
}

int main() {
    std::map<std::string, int> inventory{{"potion", 3}, {"key", 1}};
    std::printf("dragon eggs: %d\n", count_of(inventory, "dragon egg"));
    std::printf("has key: %s\n", inventory.contains("key") ? "yes" : "no");
    inventory["potion"] += 2;              // here inserting is what we want: picking up items
    std::printf("inventory has %zu items, potions x%d\n", inventory.size(), inventory.at("potion"));
}
```
```text
dragon eggs: 0
has key: yes
inventory has 2 items, potions x5
```

- `find(key)` returns an iterator, or `end()` if missing.
- `contains(key)` (C++20) returns a bool.
- `at(key)` returns the value, or throws `std::out_of_range`.
- `operator[]` is right when you **want** to create the entry: `inventory[item] += n` when picking something up.

## map or unordered_map

- `std::map` is a balanced binary tree. Lookup is O(log n), and iterating visits keys in sorted order. Each element is a separate heap node.
- `std::unordered_map` is a hash table. A **hash function** turns the key into a number, which picks a bucket. Lookup is O(1) on average. Iteration order is unspecified.

For the inventory screen, sorted order is a feature, so `std::map` is fine. For "entity id to index", with thousands of lookups per frame and no need for order, use `std::unordered_map`.

## The second feature: collisions with a spatial grid

Every frame, each enemy must check for collisions with the enemies near it. Comparing every pair is n·(n-1)/2 checks: 2,000 enemies is about 2 million checks per frame.

A **spatial hash grid** divides the world into cells (say 4x4 world units). Each enemy is put in the bucket for its cell. To find an enemy's neighbours, look only in its own cell and the 8 around it.

![World divided into grid cells; one slime checks only its own cell and the 8 around it](/diagrams/cpp-systems/05-stl/07-maps-and-hashing.png)

The key is a cell coordinate, a pair of ints, which has no built-in hash. We supply one:

```cpp
#include <cmath>
#include <cstdio>
#include <unordered_map>
#include <vector>

struct Cell {
    int x, y;
    bool operator==(const Cell&) const = default;
};
struct CellHash {
    std::size_t operator()(Cell c) const {
        return std::hash<long long>{}((static_cast<long long>(c.x) << 32) ^ static_cast<unsigned>(c.y));
    }
};

int main() {
    const float CELL = 4.0f;
    std::unordered_map<Cell, std::vector<int>, CellHash> grid;
    float pos[][2] = {{1, 1}, {2, 3}, {5, 1}, {30, 30}, {-1, 2}};
    for (int id = 0; id < 5; ++id) {
        Cell c{(int)std::floor(pos[id][0] / CELL), (int)std::floor(pos[id][1] / CELL)};
        grid[c].push_back(id);                  // inserting is what we want here
    }
    Cell me{0, 0};                              // enemy 0's cell
    std::printf("near enemy 0:");
    for (int dx = -1; dx <= 1; ++dx)
        for (int dy = -1; dy <= 1; ++dy)
            if (auto it = grid.find({me.x + dx, me.y + dy}); it != grid.end())
                for (int id : it->second) if (id != 0) std::printf(" %d", id);
    std::printf("\n");
}
```
```text
near enemy 0: 4 1 2
```

Enemy 3 at (30, 30) is never looked at. With enemies spread over the map, each check touches a handful of neighbours instead of all 2,000.

`std::floor` matters: plain `(int)(-1 / 4.0f)` is 0, which would put enemy 4 at x = -1 in the same cell column as x = 1.

## When to use them, and when not

- Use `std::unordered_map` for lookups by key when order does not matter; `std::map` when you need sorted iteration or ordered queries (`lower_bound`).
- Do not use a map when the keys are small dense integers (entity indices 0..n): a `std::vector` indexed directly is far faster.
- For a few dozen items, a sorted `std::vector` of pairs searched with `lower_bound` often beats both, thanks to cache locality.
- A bad hash (say, returning `c.x` only) puts a whole column of cells in one bucket and makes lookups slow. Mix all fields into the hash.
