## The feature: new enemy types without new classes

The designers keep inventing enemies: a slime that flies, a turret that walks, a bat that shoots, a ghost that drops loot. In the OOP module, each enemy kind was a class.

## The careless version: a class per combination

A bat that flies and shoots inherits from both `Flying` and `Shooting`:

```cpp
#include <cstdio>

struct Enemy    { int hp = 30; };
struct Flying   : Enemy { float altitude = 5; };
struct Shooting : Enemy { int ammo = 10; };
struct ShootingBat : Flying, Shooting { };

void hit_by_arrow(Shooting& s) { s.hp -= 30; }               // combat code sees shooters
int  health_bar(const Flying& f) { return f.hp; }           // the UI draws flyers' bars

int main() {
    ShootingBat bat;
    hit_by_arrow(bat);
    std::printf("combat says hp %d, health bar shows hp %d\n",
                static_cast<Shooting&>(bat).hp, health_bar(bat));
    std::printf("sizeof(ShootingBat) = %zu: two Enemy parts inside\n", sizeof(ShootingBat));
}
```
```text
combat says hp 0, health bar shows hp 30
sizeof(ShootingBat) = 16: two Enemy parts inside
```

## What went wrong

`ShootingBat` contains **two** `Enemy` sub-objects, one through each base, each with its own `hp`. The arrow killed one of them; the health bar reads the other. The bat is dead and alive at once. Virtual inheritance fixes the duplicate but adds its own cost and complexity, and the real problem remains: every new combination (a walking turret, a flying turret) needs a new class, and shared behaviour gets copied between branches.

The hierarchy forces one question ("what is it?") when the game cares about another ("what can it do?"). And the update loop is still a scattered, virtual call per object, which the previous lessons showed is slow.

## The fix: entities, components, systems

- An **entity** is an id: `using Entity = std::uint32_t;`.
- A **component** is a plain struct of data: `Position`, `Velocity`, `Health`, `Flying`, `Weapon`.
- Each component type is stored in its own **pool**: a dense array of that component, plus a record of which entity owns each element.
- A **system** is a loop: the movement system visits every entity that has both Position and Velocity.

A flying turret is an entity with `Position`, `Weapon` and `Flying`. The weapon system and the flying system already handle it. No new type.

## The sparse set

A component pool needs: add a component to entity e, remove it, test whether e has one, get it, and iterate all of them quickly. A **sparse set** does each in O(1):

- `dense`: the components, packed with no gaps. Systems iterate this.
- `owner[i]`: which entity owns `dense[i]`.
- `index[e]`: where entity e's component sits in `dense`, or "none". Indexed by entity id, so it has gaps: it is the sparse part.

Removing swaps the last element into the hole and pops, then fixes `index` for the moved entity. The dense array never has gaps.

![Sparse set: index array by entity id pointing into a packed dense array of Health components, with swap-and-pop removal](/diagrams/cpp-systems/07-dod/05-entity-component-system.png)

```cpp
#include <cstdint>
#include <cstdio>
#include <vector>

using Entity = std::uint32_t;
constexpr std::uint32_t NONE = UINT32_MAX;

template <class T>
struct Pool {
    std::vector<T> dense;
    std::vector<Entity> owner;
    std::vector<std::uint32_t> index;          // index[entity] -> position in dense, or NONE

    void add(Entity e, T value) {
        if (e >= index.size()) index.resize(e + 1, NONE);
        index[e] = static_cast<std::uint32_t>(dense.size());
        dense.push_back(value);
        owner.push_back(e);
    }
    bool has(Entity e) const { return e < index.size() && index[e] != NONE; }
    T& get(Entity e) { return dense[index[e]]; }
};

struct Position { float x, y; };
struct Velocity { float dx, dy; };

int main() {
    Pool<Position> pos;
    Pool<Velocity> vel;
    pos.add(0, {0, 0});  vel.add(0, {1, 0});   // entity 0: a slime that moves
    pos.add(1, {5, 5});                        // entity 1: a turret, does not move
    pos.add(2, {9, 1});  vel.add(2, {0, -2});  // entity 2: a bat

    // the movement system: every entity with Velocity and Position
    for (std::size_t i = 0; i < vel.dense.size(); ++i) {
        Entity e = vel.owner[i];
        if (!pos.has(e)) continue;
        pos.get(e).x += vel.dense[i].dx;
        pos.get(e).y += vel.dense[i].dy;
    }
    for (Entity e = 0; e < 3; ++e)
        std::printf("entity %u at %.0f,%.0f%s\n", e, pos.get(e).x, pos.get(e).y, vel.has(e) ? "" : " (no velocity)");
}
```
```text
entity 0 at 1,0
entity 1 at 5,5 (no velocity)
entity 2 at 9,-1
```

The system loops over the smaller pool (`Velocity`) and checks the other. The turret is never visited, and no class decided that: it simply has no `Velocity`.

## When to use it, and when not

- Use an ECS when you have many objects mixing many behaviours, and per-frame loops over them dominate: most action and strategy games.
- For a game with a handful of object kinds and a few hundred objects, plain classes are simpler and fast enough.
- Mature libraries exist (EnTT, flecs). Building the core yourself, as here, is the way to understand what they do and what they cost.
- Entity ids get reused after an entity dies. Real ECS libraries add a **generation** counter to each id so that a stale id cannot refer to the new entity in the same slot.
