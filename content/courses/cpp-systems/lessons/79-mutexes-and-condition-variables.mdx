## The feature: the load queue

The main thread asks for assets ("load bat.png") as the player moves toward new areas. The loader thread takes requests from a queue, loads each one, and appends the result to a list of finished textures that the main thread uploads to the GPU each frame.

Two pieces of shared data: the request queue and the finished list. Both threads touch both.

## The careless version: share the vector

```cpp
#include <cstdio>
#include <string>
#include <thread>
#include <vector>

std::vector<std::string> finished;              // written by loader, read by main

int main() {
    std::thread loader([] {
        for (int i = 0; i < 200; ++i) finished.push_back("tex" + std::to_string(i));
    });
    std::size_t uploaded = 0;
    while (uploaded < 200)                          // main loop: upload whatever is done
        if (uploaded < finished.size()) { std::string s = finished[uploaded]; ++uploaded; }
    loader.join();
    std::printf("uploaded %zu textures\n", uploaded);
}
```

## What went wrong

`push_back` can reallocate the vector: allocate a new buffer, move the strings, free the old buffer, then update the size. The main thread reads `size()` and `finished[uploaded]` at the same time, with nothing ordering the two threads. It can read the old buffer after it was freed, or see the new size before the element is constructed. TSan reports the race on every run; without TSan it crashes or reads garbage rarely, which is the worst kind of bug to track down.

## The fix: a mutex

A `std::mutex` can be held by one thread at a time. `std::lock_guard` locks it in its constructor and unlocks it in its destructor, so every path out of the block unlocks, including exceptions:

```cpp
#include <cstdio>
#include <mutex>
#include <string>
#include <thread>
#include <vector>

std::mutex m;
std::vector<std::string> finished;               // guarded by m

int main() {
    std::jthread loader([] {
        for (int i = 0; i < 200; ++i) {
            std::string tex = "tex" + std::to_string(i);   // slow work outside the lock
            std::lock_guard lock(m);
            finished.push_back(std::move(tex));
        }
    });
    std::size_t uploaded = 0;
    while (uploaded < 200) {
        std::vector<std::string> batch;
        {
            std::lock_guard lock(m);
            batch.swap(finished);                  // take everything, release the lock quickly
        }
        uploaded += batch.size();                  // upload outside the lock
    }
    std::printf("uploaded %zu textures\n", uploaded);
}
```
```text
uploaded 200 textures
```

Two habits shown here: build the texture before taking the lock, and take the whole batch with one `swap` so the main thread holds the lock for a moment, not for the upload.

## Waiting for work: condition variables

The loader also needs to wait for requests. Polling (`while (queue.empty()) {}`) burns a whole core doing nothing. A **condition variable** lets it sleep:

![Main thread pushes a request into a mutex-guarded queue and notifies; the loader thread waits on the condition variable with a predicate](/diagrams/cpp-systems/09-concurrency/05-mutexes-and-condition-variables.png)

```cpp
#include <condition_variable>
#include <cstdio>
#include <deque>
#include <mutex>
#include <string>
#include <thread>

std::mutex m;
std::condition_variable cv;
std::deque<std::string> requests;
bool closing = false;

int main() {
    std::jthread loader([] {
        for (;;) {
            std::unique_lock lk(m);
            cv.wait(lk, [] { return !requests.empty() || closing; });   // sleeps, lock released
            if (requests.empty()) return;                                // closing and nothing left
            std::string name = std::move(requests.front());
            requests.pop_front();
            lk.unlock();                                                 // load without the lock
            std::printf("loaded %s\n", name.c_str());
        }
    });
    for (const char* n : {"bat.png", "ghost.png", "lava.ogg"}) {
        { std::lock_guard g(m); requests.push_back(n); }
        cv.notify_one();
    }
    { std::lock_guard g(m); closing = true; }
    cv.notify_all();
}
```
```text
loaded bat.png
loaded ghost.png
loaded lava.ogg
```

- `cv.wait(lock, predicate)` releases the lock while asleep and re-locks before returning. It loops until the predicate is true, which handles **spurious wake-ups** (waking with no notify).
- The other side changes the data **under the lock**, then calls `notify_one()` (wake one waiter) or `notify_all()`.
- `closing` gives the loader a clean way out at shutdown.

## When to use it, and when not

- Use a mutex for any shared data structure (vectors, maps, queues) and for groups of values that must change together.
- Lock several mutexes at once with `std::scoped_lock lk(a, b);`, which avoids deadlock from opposite locking orders.
- Use a condition variable when a thread must wait for a state change. Never wait without a predicate.
- Do not hold a lock while doing slow work or calling unknown code (callbacks). Copy what you need, unlock, then work.
- For one-producer, one-consumer hot paths (the audio thread), the building-blocks module shows a lock-free ring buffer instead.
