**Mission:** CJ, a shipment of words is headed for the model. Intercept it and swap every word for a numbered crate before it gets there.

## Text in, numbers out

A language model is a function from numbers to numbers. Before it can read your prompt, a
**tokenizer** chops the text into pieces and replaces each piece with an integer id.

```text
"Inference is fun" -> ["In", "ference", " is", " fun"] -> [644, 2251, 374, 2523]
```

The ids here are made up, but the shape is real. Common words get a single token. Rarer words get
split into several pieces. Note the leading spaces: `" is"` and `"is"` are different tokens.

The model never sees the letters. It only sees ids, and it can only ever produce ids too.

## Where the vocabulary comes from

Most modern tokenizers use **byte-pair encoding (BPE)**. Training starts from single bytes, then
repeatedly merges the most frequent adjacent pair into a new token until the vocabulary hits a
target size.

| Model family | Vocabulary size |
| --- | --- |
| Llama 2 | 32,000 |
| GPT-4 (cl100k) | ~100,000 |
| Llama 3 | 128,256 |

A bigger vocabulary packs more text into each token (fewer forward passes per answer), but the
embedding table and the final output layer both grow with it.

## Why you should count tokens

Every forward pass handles tokens, so tokens are the unit of cost. Prompt length drives the
**prefill** time, output length drives **decode** time, and both drive memory. API pricing is per
token for the same reason.

A useful rule of thumb for English is **about 0.75 words per token**. Code, maths and many
non-English languages tokenize less efficiently, sometimes 2 to 3 times worse.
