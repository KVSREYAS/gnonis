## The formula

For every token, every layer stores one key and one value vector per KV head:

$$\text{bytes/token} = 2 \times L \times H_{kv} \times d_{head} \times b$$

- $2$: one K and one V.
- $L$: number of layers.
- $H_{kv}$: KV heads (fewer than query heads with GQA).
- $d_{head}$: head dimension.
- $b$: bytes per element (2 for fp16 and bf16, 1 for fp8). fp16 and bf16 are two 16-bit floating-point formats, and fp8 is an 8-bit format (module 7).

## What the formula leaves out

Notice what is missing from the formula: query heads, the MLP's width and the vocabulary. Queries are
never cached, and the MLP and vocabulary never touch the cache, so only layers, KV heads, head size and
the number format count. For Llama 3 8B in fp16 this comes to roughly a hundred kilobytes per token.

## Comparing real models

The cache per token is set by the attention shape, not by the parameter count:

| Model | Attention | Cache per token |
|---|---|---|
| Llama 2 7B | MHA: a K/V head per query head | Largest of the three |
| Llama 3 8B | GQA: few KV heads | Small |
| Llama 3 70B | GQA, many more layers | Between the two |

Llama 3 70B is far bigger than Llama 3 8B, but its cache per token grows only with its extra layers. Llama 2 7B, the smallest model here, has the biggest cache per token, because it uses MHA.

Parameter count tells you the weight memory. Layers, KV heads, head size and the cache's number format tell you the cache.

## Per sequence

A sequence's cache is that per-token cost times its length, so it grows steadily with every token. A
single long conversation on Llama 3 8B already needs around a gigabyte of cache, and very long
contexts need several. That is why the cache, not the weights, usually decides how many users fit.
