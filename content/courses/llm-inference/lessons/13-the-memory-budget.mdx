## Weights first, cache second

A serving GPU's memory splits into three parts:

1. **Weights**: fixed. 8B parameters in fp16 take 16 GB.
2. **Activations and workspace**: temporary buffers, usually small.
3. **KV cache**: everything that is left.

vLLM, for example, loads the weights, measures what activations and warm-up need, and turns the
remaining memory into the pool of KV blocks. Older versions capped the total at a fraction of the GPU
(`gpu_memory_utilization`, 0.9 by default); recent versions on NVIDIA and AMD GPUs size the pool from
the memory actually left free.

## How vLLM sizes its pool

At startup vLLM loads the weights, runs warm-up passes (including CUDA graph capture) and measures how much memory those need. On NVIDIA and AMD GPUs, recent versions then size the KV cache from the memory that is actually still free, keeping a safety margin. Older versions, and other platforms, instead take a fixed fraction of the GPU set by `gpu_memory_utilization` and give what is left of it to the cache.

The startup log reports how much KV cache it got and how many requests of the maximum length could run at once. If even one sequence of `max_model_len` tokens can't fit, it refuses to start.

A common pitfall is setting `max_model_len` to the model's full advertised context (such as 128k) on a small GPU when users never send more than 8k.

Source: [vLLM docs: optimization](https://docs.vllm.ai/en/latest/configuration/optimization.html)

## Long contexts eat concurrency

At 32k tokens, one Llama 3 8B sequence needs 4.3 GB of fp16 cache. Long-context products hit the
wall fast. The levers are fewer bytes per element, fewer KV heads, shorter contexts, or more
memory.

## Read the config right

Most estimators read a Hugging Face `config.json`. The field names matter: `num_attention_heads`
counts query heads, while `num_key_value_heads` counts KV heads.
