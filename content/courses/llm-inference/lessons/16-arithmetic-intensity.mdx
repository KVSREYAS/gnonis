## FLOPs per byte

Every kernel does some maths and moves some data. Their ratio is the **arithmetic intensity**:

$$I = \frac{\text{FLOPs}}{\text{bytes moved}}$$

High intensity means each byte fetched from HBM feeds lots of maths. Low intensity means the
compute units spend most of their time waiting.

A matmul $[m \times k] \cdot [k \times n]$ does $2mkn$ FLOPs (a multiply and an add per term).

For a square $n \times n$ matmul the FLOPs grow as $n^3$, but the data moved (two inputs and one
output) grows only as $n^2$, so each loaded number is reused about $n$ times. At $n = 4{,}096$ in
fp16 the intensity is about 1,365 FLOP/byte.

## Decode is a matrix-vector product

A matrix-matrix multiply is called a **GEMM** (general matrix multiply), and a matrix-vector multiply
is a **GEMV**. At decode time with batch size 1, each linear layer is a GEMV: it multiplies **one**
token's vector by a big weight matrix. Every weight is read once and used once.

One multiply-add per 2-byte weight works out to about **one FLOP per byte**, whatever the matrix size.
Tensor cores need hundreds of FLOPs per byte to stay busy, so batch-1 decode is firmly memory-bound.

## Element-wise operations

Some kernels do almost no maths per byte. Adding two fp16 tensors element by element reads 2 bytes
from each input and writes 2 bytes of output (6 bytes) to do 1 FLOP, so the intensity is
1/6 ≈ 0.17 FLOP/byte. Activation functions, normalisation and softmax are similar. They are always
memory-bound, which is why engines **fuse** them into the matmul kernel before or after them, so the
data is not written to HBM and read back.

## Batching to the rescue

Decode $B$ sequences together and each weight, loaded once, serves $B$ tokens. The intensity of
the weight matmuls rises to roughly $B$ FLOP/byte in fp16. This is the core reason servers batch.

## Why batching raises intensity

In a weight matmul, the expensive part is loading each weight from HBM. At batch 1 each loaded weight is used for one token. With a batch of users, the engine stacks their vectors into a matrix, so each loaded weight is used for every user in the batch.

So batching raises the FLOPs done per byte read, almost in step with the batch size, without any change to the model. That is the one idea behind batched decode: the weight read is shared.

It doesn't last forever. Each user also brings a KV cache that only that user reads, and those reads grow with every user added. Memory caps the batch, and latency targets cap it too, so real decode servers rarely reach the ridge. Prefill gets there easily, because one prompt already brings many tokens.
