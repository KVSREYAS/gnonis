## Same weights, more sequences

In a memory-bound decode step the GPU streams all the weights from HBM once, whatever the batch size. Each sequence in the batch reuses that same read. So going from batch 1 to batch 16 costs a little extra KV reading and almost nothing else.

Total bytes per step = weights + Σ (context × KV bytes per token).

## The KV cache cost

Long contexts change the maths. At batch 64 with 2k tokens each, the KV cache is bigger than the weights, so step time roughly doubles. Push further and you either run out of memory or cross the roofline ridge into compute-bound territory.

## Picking a batch cap

Every step serves each running sequence one token, so per-user speed is 1 / step time, and total throughput is batch / step time. Step time grows with batch because of the KV cache:

step time ≈ (weight bytes + batch × context × KV bytes per token) / bandwidth

For Llama 3 8B in fp16 on an H100 at 2,048 tokens of context: batch 16 reads about 20.3 GB per step (about 6.1 ms, 165 tokens/s per user), and batch 128 reads about 50 GB (about 15 ms, 67 tokens/s per user).

The cap you want is the largest batch whose step time still meets the per-user target and whose caches still fit in memory. In vLLM it is set with `max_num_seqs`.
