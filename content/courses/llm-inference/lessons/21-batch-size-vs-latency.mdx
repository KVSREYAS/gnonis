## Same weights, more sequences

In a memory-bound decode step the GPU streams all the weights from HBM once, whatever the batch size. Each sequence in the batch reuses that same read. So going from batch 1 to batch 16 costs a little extra KV reading and almost nothing else.

Total bytes per step = weights + Σ (context × KV bytes per token).

## The KV cache cost

Long contexts change the maths. At batch 64 with 2k tokens each, the KV cache is bigger than the weights, so step time roughly doubles. Push further and you either run out of memory or cross the roofline ridge into compute-bound territory.

## Picking a batch cap

Every step serves each running sequence one token, so a user's speed is set by how long a step takes, and total throughput is the batch divided by the step time.

Step time grows with the batch, slowly at first and then faster:

- The **weights** are read once per step, whatever the batch.
- Each user's **KV cache** is read in full every step, so cache traffic grows with batch and context.

So adding users raises total throughput while each user slowly gets slower. The cap you want is the largest batch whose steps still meet the per-user speed target and whose caches still fit in memory. In vLLM it is set with `max_num_seqs`; the memory limit is enforced by the block pool.

## Pick a cap from measurements

Turn the bargain into a decision: given a measured step-time curve and a per-user speed target, how
big can the batch be, and which limit stops it first, the target or memory?
