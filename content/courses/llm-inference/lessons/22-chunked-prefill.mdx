## Prefill and decode, again

A request goes through two phases.

- **Prefill**: the model reads all prompt tokens in one forward pass. It writes the key and value of every prompt token into the KV cache and produces the first output token. A prompt of n tokens means matrix multiplications with n rows, so prefill does a lot of arithmetic and is usually **compute-bound**.
- **Decode**: every later step feeds in one new token per sequence. The step must still read all weights from memory, so decode is **memory-bound**.

With continuous batching (lesson 1 of this module), one forward pass can hold decode tokens from many users plus prefill tokens of new requests. A **scheduler step** (also called an iteration) is one such forward pass. Every user who is decoding gets exactly one new token per step, so the length of a step is the gap between two of their tokens.

## The prefill stall

Suppose 96 users are decoding and each step takes about 10 ms. Now a request arrives with an 8,192-token prompt.

If the scheduler puts the whole prefill into the next step, that step must do 8,192 tokens of compute. For an 8B model that is 2 × 8 × 10^9 × 8,192 ≈ 1.3 × 10^14 FLOPs, about 330 ms on an H100 at a realistic 400 TFLOP/s.

All 96 users get no token during those 330 ms. Their stream pauses for 33 normal step times, then continues. This pause is called a **generation stall** (the Sarathi-Serve paper's term). It shows up as a spike in **inter-token latency** (ITL, the gap between two streamed tokens) and in the p99 of TPOT, even if the average looks fine.

## What chunked prefill does

**Chunked prefill** splits a long prompt's prefill into pieces of a fixed number of tokens, called **chunks**, and runs one chunk per step across several steps.

Each step has a **token budget**: the most tokens the step may process. The scheduler fills it in this order:

1. One token for every running decode.
2. The next chunk of any prefill that is already in progress.
3. Chunks of new waiting requests, while budget is left.

Example: budget 2,048 and 96 decodes. The decodes use 96 tokens, so this step carries a 1,952-token prefill chunk. The 8,192-token prompt finishes after 5 steps (4 × 1,952 + 384). Only the step that processes the last chunk produces the request's first output token.

Sarathi-Serve (OSDI 2024) introduced this "stall-free" schedule. vLLM and SGLang ship it as chunked prefill.

## Why mixing is cheap

A decode-only step is memory-bound: the GPU reads all weights to do a little arithmetic per token. The arithmetic units are mostly idle.

A prefill chunk adds arithmetic but almost no new weight reads, because the same weights are already being read for the decodes. So, up to a point, adding a few hundred prefill tokens to a decode step barely changes its time. Sarathi-Serve measured that the cost of the linear layers for 1 decode token is about the same as for 128 prefill tokens, and that step time stays nearly flat until the step holds a few hundred tokens.

Past that point the step becomes compute-bound and its time grows with every extra token. The token budget decides where on that curve each step sits.

## Chunk size: TTFT against TPOT

Use a simple cost model with round numbers for an 8B model on one H100:

- a step with only the decodes takes **10 ms**
- each prefill token in the step adds **0.04 ms** (16 GFLOPs at 400 TFLOP/s)

The 8,192-token prompt then needs 8,192 × 0.04 = 328 ms of prefill compute, whatever the chunk size. Each chunk also pays the 10 ms step.

## The trade-off in numbers

Same cost model, 8,192-token prompt:

| chunk size | steps for the prompt | step time (decoders' gap) | TTFT of the long prompt |
| --- | --- | --- | --- |
| 8,192 (no chunking) | 1 | 10 + 328 = 338 ms | 338 ms |
| 2,048 | 4 | 10 + 82 = 92 ms | 368 ms |
| 512 | 16 | 10 + 20.5 = 30.5 ms | 488 ms |
| 256 | 32 | 10 + 10.2 = 20.2 ms | 648 ms |

Smaller chunks protect the decoding users (shorter gaps, better TPOT and ITL) but make the long prompt wait longer for its first token (worse TTFT). This model overstates the cost of small chunks, because real steps stay nearly flat for the first few hundred tokens, but the direction is right.

## What happens to the KV cache

Chunking does not change how much KV cache a request needs in the end: 8,192 tokens × 128 KiB is still 1 GiB for Llama 3 8B. It changes when and how that cache is written and read.

1. **Written piece by piece.** Each chunk computes keys and values for its own tokens and appends them to the request's KV blocks. The server only needs blocks for the chunks scheduled so far, so memory for a long prompt is taken step by step.
2. **Earlier chunks are read again.** Chunk k uses causal attention over the whole prompt so far, so its queries must read the keys and values of chunks 1 to k − 1 back from the KV cache in HBM. The first chunk's KV is read by every later chunk, the second by all chunks after it, and so on.
3. **Same arithmetic.** The attention FLOPs are the same as one big prefill. Only the extra KV reads are new.

## How much the extra reads cost

Sarathi-Serve reports that the extra reads cost little: with 2,048-token chunks the overhead is almost zero, and with 512-token chunks the total prefill takes at most about 25% longer.

## How real systems use it

- **Sarathi-Serve** (Agrawal et al., OSDI 2024) builds every batch as: all running decodes, then any partly done prefill, then new prefills, within a token budget picked from the latency target. They used 512 tokens for strict targets and 2,048 for relaxed ones. It served up to 2.6x more load for Mistral-7B on one A100 and up to 3.7x for Yi-34B on two A100s than vLLM at that time, under the same p99 latency targets.
- **vLLM** (V1 engine) turns chunked prefill on by default. It schedules all pending decodes first, then prefills into the budget `max_num_batched_tokens`, chunking any prompt that does not fit. Its docs say smaller values (such as 2,048) give better ITL and larger values give better TTFT.
- **SGLang** exposes the same idea as `--chunked-prefill-size`.

## Two details from the paper

Budgets should be multiples of the GPU's matmul tile size (a 257-token chunk was up to 32% slower than 256), and uniform step sizes also shrink pipeline-parallel bubbles (module 10).

Sources: [Sarathi-Serve](https://arxiv.org/abs/2403.02310), [vLLM optimization and tuning](https://docs.vllm.ai/en/latest/configuration/optimization.html), [SGLang server arguments](https://docs.sglang.io/docs/advanced_features/server_arguments)
