## Two clocks

**TTFT** covers queueing plus prefill. **TPOT** (or inter-token latency) is the gap between later tokens.

## End-to-end latency

Total time is roughly TTFT plus TPOT for every token after the first.

<MCQ
  id="e2e-latency"
  devices={["phone","desktop"]}
  prompt={"TTFT is 200 ms, TPOT is 20 ms, and answers average 500 tokens. Which cuts the average user's total wait more: halving TTFT, or cutting TPOT by 10%?"}
  options={["Halving TTFT, because the first token is what users wait for.", "They save the same time.", "Neither changes total time; only throughput does.", "Cutting TPOT by 10%: it saves about 1 s, while halving TTFT saves 0.1 s."]}

  explanation={"Total ≈ TTFT + 499 × TPOT ≈ 0.2 + 10 s. A 2 ms cut in TPOT is paid back 499 times, about 1 s. Halving TTFT saves 100 ms once. TTFT still matters for how quick the start feels, but for long answers TPOT sets most of the wait."}
/>

## Prefix caching

If many requests start with the same system prompt, keep its KV blocks and skip that part of prefill.

How vLLM finds a match: each **full** KV block gets a hash computed from its own tokens **and** the hash of the block before it. So two blocks have the same hash only if the whole prompt up to and including that block is the same. A new request hashes its prompt block by block, reuses every block already in the cache, and prefills only the rest. Keys and values depend on all earlier tokens, which is why the hash must cover the whole prefix and not just one block.

vLLM calls this automatic prefix caching. SGLang keeps cached prefixes in a radix tree (RadixAttention), where requests with a shared beginning share a path from the root.

<MCQ
  id="prefix-saving"
  devices={["phone","desktop"]}
  prompt={"Prefix caching worked well until someone put the current timestamp at the very start of the system prompt. Now the hit rate is near zero. Why?"}
  options={["Timestamps cannot be tokenized.", "Each block's hash covers all tokens before it, so a change in the first block changes every block's hash and no prompt matches the cache.", "The cache only stores prompts below a fixed length.", "Prefix caching only reuses the last block of a prompt."]}
  answer={1}
  explanation={"Keys and values depend on every earlier token, so the cache can only reuse a block when everything before it matches too. A timestamp in the first block makes every request's prefix unique. Moving the changing part to the end of the prompt restores the hits. Timestamps tokenize like any text, there is no length cutoff, and reuse runs from the first block forward."}
/>

## Summary

Tokens per second alone hides latency. A server can have high total throughput while single users wait
a long time for the first token. Report TTFT and TPOT percentiles together with throughput.
