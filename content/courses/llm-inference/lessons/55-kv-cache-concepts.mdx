## Why cache

In decode step n, attention needs the keys and values of all n previous positions. Without a cache, the model would recompute them by running every previous token through every layer again: about n times the work for step n, and quadratic total work for a whole answer.

Because of the causal mask, k and v for position s depend only on tokens 0..s. They are identical in every later step. So the server computes them once and keeps them in GPU memory: the **KV cache**.

Each decode step then computes q, k, v for just the one new token, appends its k and v to the cache, and attends over the cache.

![Recomputing vs reusing cached K and V](/diagrams/llm-inference/03-kv-cache/01-why-cache.png)

## Sizing it exactly

Per token, every layer stores one key and one value vector for each KV head:

bytes per token = 2 x L x n_kv x d_head x bytes per number

The 2 is for K and V.

**Llama-3-8B** in FP16 (2 bytes): L = 32, n_kv = 8, d_head = 128.
2 x 32 x 8 x 128 x 2 = 131,072 bytes = **128 KiB per token**.

- one 8K-token request: 8,192 x 128 KiB = 1 GiB
- 32 such requests: 32 GiB

For comparison, the weights are about 16 GB. The cache can easily be larger than the model.

![KV size formula with each factor](/diagrams/llm-inference/03-kv-cache/02-sizing-the-cache.png)

## The memory budget

A GPU's main memory (HBM, high-bandwidth memory, covered in module 4) holds three things:

1. **weights**: fixed, e.g. 16 GB for 8B parameters in FP16
2. **activations and workspace**: temporary buffers, a few GB
3. **KV cache**: everything left

On an 80 GB GPU: 80 - 16 - about 4 = about 60 GB for KV. At 128 KiB (131,072 bytes) per token that is 60 × 10^9 / 131,072 ≈ 458,000 tokens of cache, shared by all active requests: about 55 requests at 8K tokens, or 13 at 32K.

That number sets the **maximum batch size**, and batch size sets throughput. So every technique that shrinks KV (GQA, KV quantization, paging to waste less) turns directly into more concurrent users.
