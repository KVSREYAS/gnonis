## Why cache

In decode step n, attention needs the keys and values of all n previous positions. Without a cache, the model would recompute them by running every previous token through every layer again: about n times the work for step n, and quadratic total work for a whole answer.

Because of the causal mask, k and v for position s depend only on tokens 0..s. They are identical in every later step. So the server computes them once and keeps them in GPU memory: the **KV cache**.

Each decode step then computes q, k, v for just the one new token, appends its k and v to the cache, and attends over the cache.

![Recomputing vs reusing cached K and V](/diagrams/llm-inference/03-kv-cache/01-why-cache.png)

## Sizing it exactly

Per token, every layer stores one key and one value vector for each KV head:

bytes per token = 2 x L x n_kv x d_head x bytes per number

The 2 is for K and V. Query heads, the MLP and the vocabulary don't appear, which is why parameter
count is a poor guide to cache size.

For **Llama-3-8B** in FP16 this is roughly a hundred kilobytes per token, so one long request needs
around a gigabyte and a few dozen of them can need more memory than the weights themselves.

![KV size formula with each factor](/diagrams/llm-inference/03-kv-cache/02-sizing-the-cache.png)

## The memory budget

A GPU's main memory (HBM, high-bandwidth memory, covered in module 4) holds three things:

1. **weights**: fixed, set by parameter count and bytes per parameter
2. **activations and workspace**: temporary buffers, usually small
3. **KV cache**: everything left

What is left, divided by the cache each request needs, sets the **maximum batch size**, and batch
size sets throughput. So every technique that shrinks KV (GQA, KV quantization, paging to waste less)
turns directly into more concurrent users.

![HBM split into weights, activations and KV](/diagrams/llm-inference/03-kv-cache/03-the-memory-budget.png)

## Worked scenario: a capacity plan

Every capacity question has the same shape: free memory for the cache divided by the cache each sequence needs.

- **Start**: GPU memory minus the weights minus working space gives the KV pool.
- **Store the cache in fp8**: each token takes half the bytes, so about twice as many sequences fit.
- **Raise the maximum context** for users who really use it: each sequence needs more cache, so fewer fit.
- **Quantize the weights**: the pool grows by the freed memory, but each sequence costs the same, so the gain is smaller than the weight saving suggests.

The cache depends on total tokens held, not on how many users hold them: a few very long conversations can take the same memory as many short ones.
