# C++ course rewrite: Slime Siege (Round 10)

The `cpp-systems` course now follows one running project, **Slime Siege**, a 2D top-down game engine. Each module is one feature milestone. Its `00-concepts` page says what we build and why the game needs it. Every concept lesson uses the same order:

1. the game problem ("The feature: ...")
2. the careless version: code that compiles, with its real output (wrong numbers, sanitizer report, crash or timing)
3. what went wrong, and the concept in plain words
4. the fixed version or a complete worked example, with real output
5. when to use it and when not
6. exercises framed as game tasks

All lesson MDX is generated by `/workspace/gnosis/gdgen/build.py` from `gdgen/src/*.mdx.in`. Every ```` ```cpp run=... ```` block is compiled and run at build time (g++ 14.2, `-std=c++20 -O2`, or ASan+UBSan / TSan / `-O0` where marked), and the output pasted into the lesson is what that run printed. Timings come from one run on the box (8 cores). Every new code exercise is checked at build time: the solution must pass at -O2 and under ASan+UBSan, and the starter must compile and fail with `CHECK failed` (exit 1).

## Rules kept

- **Ids and slugs:** no existing lesson id or exercise id was renamed or removed. `validate:content` checks ids against origin/main.
- **New lessons:** 8 new lessons with new ids, inserted into `course.yaml` next to related lessons.
- **Module order:** the OOP module now comes first (basic syntax, milestone 1: entities).
- **Style:** simple words, no analogies, no GTA theme.
- **Fun rating:**
  - concept pages: 2
  - lessons with a coding task: 5
  - lessons without one: 3
  - module tests: 5
- **Module tests:** one per module, kept, with game-framed briefings.

## Known risks

- **Exercises whose content hash changed** (saved progress may reset for these 11):
  - methods, ctor-dtor, static-count, virtual-honk
  - private-access, const-method, sv-dangle
  - bank-account, money-ops, roster
  - the garage module test
- **OOP first:** this reorders the course, so learners part-way through will see the module order change.
- **Pre-existing starters left unchanged** (changing them would change their hashes):
  - noexcept-moves, forward-wrapper, mini-shared and align-up-fn do not compile as given.
  - The spinlock starter has a data race.
  - The bounded-queue starter would null-deref after a failed CHECK, but CHECK exits first.
  - bench-harness's starter passes its visible test (0 <= 0); the hidden tests fail it.
- **Compiler versions:** examples were built with g++ 14.2 and CI uses g++ 13.3. Code exercises are re-verified by validate:content in CI. Printed example output was not re-run there.
- **Timing outputs** are from one machine and one run. The prose says so next to each one.
- **TSan block output order:** stdout is shown before stderr.
- **The SPSC careless demo is racy by design:** its counts vary between runs. The prose does not depend on the exact numbers.
